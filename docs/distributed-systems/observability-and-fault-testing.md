# 分散式觀測、故障注入與歷程驗證

觀測協助定位故障，歷程驗證則把實際操作對照明訂規格；測試必須保存未知結果，才能正確判斷哪些承諾真的被違反。

前面已討論[原子提交](atomic-commit-and-two-phase-commit.md)、[補償](sagas-and-business-compensation.md)、[訊息交接](delivery-semantics-and-outbox.md)與[收斂](convergence-and-crdts.md)。現在要為文章匯出服務提出可觀察的反例，而不是只因元件名稱齊全便接受設計。

查證日期：2026-11-05。參考 OpenTelemetry、Jepsen 官方文件及 FoundationDB 2021 年原論文 §4。本文歷程、測試矩陣與判準為概念設計，未執行 Jepsen、確定性模擬或真實叢集故障測試。

## 每種證據回答不同問題

| 證據 | 適合回答什麼 | 單靠它缺少什麼 |
| --- | --- | --- |
| 指標（metric） | 工作年齡、重試率、尾端延遲是否異常 | 某一意圖到底建立幾份工作、經過哪些競爭 |
| 日誌（log） | 某程序記錄了哪些內部狀態與決策 | 沒有紀錄不等於沒有發生，跨機時鐘也可能偏移 |
| 追蹤（trace） | 一條呼叫鏈在哪裡等待，跨服務如何關聯 | 抽樣、遺失或未傳播的 span 不能替代完整業務紀錄 |
| 操作歷程（operation history） | 客戶端發起哪些操作，觀察到什麼結果與先後 | 是否符合規格，還需要模型與查核器 |
| 查核器（checker） | 這段歷程是否能被規格接受 | 不能判定未記錄、未測過或模型外的所有執行 |

OpenTelemetry 的 context propagation 透過 Trace ID、Span ID 等上下文串聯服務，可把相關日誌與呼叫對起來；它不是業務操作去重機制，也不能只靠 span 時間戳證明全域線性順序。來源：[OpenTelemetry：Context propagation](https://opentelemetry.io/docs/concepts/context-propagation/)。

匯出測試應同時保存 `operation_id`、單次請求識別、`job_id`、`attempt_id` 與事件識別。一次重送可能有新的請求或 trace，但仍屬於同一意圖；若只看傳輸識別，可能漏掉重複建立工作。

## 先寫規格，再決定記錄哪些歷程

假設契約是「同一有效意圖最多建立一份工作」。可由測試客戶端記錄呼叫、參數、意圖、回應與查詢結果，再以服務的可信工作紀錄核對是否有重複實體。只記 HTTP 狀態碼不足以辨認兩次 `202` 指向同一工作還是兩份不同工作。

若要驗證[線性一致性](consistency-models-and-histories.md)，歷程需表達操作的呼叫與回應區間，並保留已完成操作先於後續呼叫的關係。例如由同一測試協調者在收到寫入回應後才發出讀取，就能建立這段先後；不能直接把不同主機未校正的 wall-clock 日誌排成唯一真實順序。

Jepsen 的 checker 接受歷程與模型，提供有效、無效及某些情況下的未知結果；不同 checker 有自己的前提與資訊需求，不能把任意業務 JSON 丟進線性一致性 checker 就期待它自動知道工作、配額與外部效果的規格。來源：[Jepsen：Checker、check-safe、linearizable](https://jepsen-io.github.io/jepsen/jepsen.checker.html)。

## 操作結果未知，不等於查核結果必然未知

呼叫 timeout 表示呼叫者沒有確認結果，操作可能提交，也可能未生效。測試紀錄不能武斷把它當成無效果的失敗。這與 checker 回傳 `unknown` 是兩個層次：前者是操作的資訊，後者是查核器無法確定歷程是否符合模型。

尤其不能把每一段含有 timeout 的歷程都直接判成違約。考慮一個允許覆寫的單值暫存器：

1. A 發起寫入 `v1`，但回應逾時，完成結果未知。
2. B 之後寫入 `v2` 並成功回應。
3. 後續讀取回傳 `v1`。

這段歷程**不一定違反線性一致性**：A 的未決寫入可能在 B 寫入之後才生效。Timeout 並沒有證明 A 的操作區間已以「無效果」結束；模型若容許這種完成安排，便不能把讀到 `v1` 直接叫作過時讀取。

反過來，如果 A 寫入 `v1` 已成功回應，接著 B 才呼叫並成功寫入 `v2`，之後讀取卻回傳 `v1`，且沒有其他寫入，就形成該暫存器線性一致性的反例。這是依操作區間定義作的概念推演，沒有執行 checker，也不虛構工具的輸出格式。

若應用另有「只有目前世代能發布」的規格，即使暫存器模型接受某個順序，也可能違反業務所有權規格。必須挑對模型，不能讓較弱的查核結果替較強的承諾背書。

## 匯出服務的故障矩陣

| 故障注入位置 | 要觀察的歷程 | 可否證的承諾 |
| --- | --- | --- |
| 工作提交後丟棄回應，再以同一意圖重送 | 受理紀錄、工作對應、配額保留 | 同意圖是否建立兩份工作或重複保留配額 |
| Outbox 發送後、補記前停止 relay | 原事件、重送、各 consumer 本地效果 | 重複事件是否令統計再次累加 |
| 暫停 A，讓 B 接手並發布，再恢復 A | 世代、候選檔案、正式結果指標 | 舊嘗試是否仍能覆寫已選定結果 |
| 切斷副本間連線，再恢復 | 已確認寫入、讀取與切換紀錄 | 是否丟掉承諾保存的工作，或由不合資格節點確認操作 |
| 補償已執行但丟棄回應，再重送 | 保留單據與取消次數 | 是否重複釋放額度、影響別人的保留 |
| 崩潰恢復或延後清理 | 未完成工作、候選物件與恢復者決策 | 工作是否永久無人接續，或有效產物是否被誤刪 |

這些都是待執行的測試設計。要驗證活性，還需要定義故障何時停止、依賴何時恢復、允許多少處理時間，以及有沒有足夠容量。持續切斷所有通訊，不能拿來否定「依賴恢復後能繼續」的條件式承諾。

測試也要保留故障的實際生效證據。發出停止程序的指令不代表程序確已停止；重啟節點不代表已追齊；網路規則若沒有作用，測試通過也沒有涵蓋那次分割。

## 重播需要固定的不只是一個 seed

FoundationDB 把程序、網路與磁碟等行為放進確定性模擬，使用 workload assertions 與其他 test oracle 檢查不變式、恢復與故障影響。來源：[FoundationDB 論文 §4：Simulation Testing](https://www.foundationdb.org/files/fdb-paper.pdf)。

在受控的確定性環境，保存 seed 有助重播；實作版本、測試配置、初始資料、模擬器版本及被控制的非確定性來源也必須對得上。不能對任意容器或實體部署宣稱只給同一 seed 就百分之百重現。

同一論文亦指出模擬無法可靠發現所有效能問題，且不能覆蓋未納入其執行環境的第三方依賴。測試環境外的檔案系統、作業系統或供應者語意，仍需另行驗證；不能把模擬通過當成真實部署驗收。

## 如何解讀結果

- **發現反例**：保存最小必要的歷程、規格、配置與故障證據，指出哪個承諾被違反。
- **通過**：表示該版本、模型、記錄與測試範圍內沒有發現違約，不等於證明所有執行正確。
- **未知或證據不足**：記錄原因，例如 checker 中斷、搜尋資源不足或紀錄不全；不能改成綠燈，也不等於已找到反例。

最後的總計正確，也不一定代表歷程安全：重複扣額後又補償，可能暫時違反限制卻被終態查詢掩蓋。應同時檢查對外可見操作和必要的業務轉移。
