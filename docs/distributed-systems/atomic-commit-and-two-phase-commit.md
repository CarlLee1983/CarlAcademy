# 原子提交與兩階段提交

原子提交協調多個交易參與者對同一筆交易作出一致的提交或放棄決定；兩階段提交用預備承諾與持久決策完成這項工作，也可能因無法得知決策而阻塞。

接續[分片、路由與資料搬遷](partitioning-and-rebalancing.md)，現在假設文章匯出工作和使用者配額已分屬兩個資料庫。只在其中一邊成功，不能滿足「建立工作與保留配額一起成立」的契約。

查證日期：2026-11-05。本文依 Gray、Lamport 的《Consensus on Transaction Commit》技術報告 §2–3 及 PostgreSQL 18 官方文件整理。匯出案例、訊息與故障點為概念推演，未執行資料庫指令或跨節點交易實驗。

## 原子提交、共識與隔離各自回答什麼

| 問題 | 要保證的事情 | 仍需另外處理的事情 |
| --- | --- | --- |
| 原子提交（atomic commit） | 參與者不作出互相矛盾的終態決定；提交必須滿足所有參與者已預備的條件 | 並行交易的讀寫干擾、外部非交易效果 |
| 共識（consensus） | 在指定模型與有效性規則下，對提議的值取得一致決定 | 哪些業務參與者同意提交，以及業務約束是否滿足 |
| 隔離（isolation） | 限制多筆交易並行時可觀察的交錯與相互影響 | 跨資源的提交決策與恢復 |

以多數派運作的 Raft 群組可以在少數副本失效時繼續決定日誌；但 Job DB 與 Quota DB 是不同的業務參與者，不能拿其中一個的贊成票代替另一個。也不能把所有共識協定的定義直接縮成「多數決」。差異見 [Gray、Lamport §2、§4](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-2003-96.pdf)。

原子提交不表示各機器在同一個實體時刻完成，也不自動保證跨資料庫查詢看到一致快照。若讀者先後讀不同資料庫，想避免看見不同進度，還需要相應的讀取與隔離協定。單一資料庫的背景見[交易與隔離](../relational-databases/transactions-and-isolation.md)。

## 先工作、再預備、最後依決策結束

兩階段提交（Two-Phase Commit, 2PC）包含協調者（coordinator／transaction manager）與資源管理器（resource manager）。本例使用同一個交易識別 `tx-42`，參與者集合在決策前已確定：Job DB 建立待處理工作；Quota DB 檢查並保留一次配額。

第一階段是預備（prepare）。參與者執行其交易工作，保存足以恢復的預備狀態，然後回覆贊成；若無法承諾，可在尚未預備時放棄。`Prepared` 的意思是「我能依最終決策完成」，不是「已對使用者提交成功」。

第二階段是決策。協調者收齊所有贊成票後，才可持久記錄提交（commit）決定；若條件未滿足，也可在尚未決定提交前持久決定放棄（abort）。之後傳播同一決定，各參與者按它結束交易。相關狀態必須先可靠保存，再發出依賴該狀態的承諾訊息。來源：[Gray、Lamport §3.1](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-2003-96.pdf)。

持久化方式與具體訊息數依實作及最佳化而異；「兩階段」不是兩次普通 HTTP 呼叫，也不要求一種固定 WAL 格式。參與者必須真的支援預備、恢復與最終決策，不能只在應用程式加一個 `prepared=true` 欄位。

## 已預備之後，逾時不再代表可以自行放棄

參與者保存贊成承諾後，進入決策未明的狀態（in-doubt）。它不能僅憑等待逾時就自行 abort，因為協調者可能已決定 commit，其他參與者甚至已提交。

以下是自創的故障歷程：

| 步驟 | 協調者 | Job DB | Quota DB |
| --- | --- | --- | --- |
| 1 | 對 `tx-42` 發出 prepare | 保存預備狀態並贊成 | 保存預備狀態並贊成 |
| 2 | 收齊選票，持久記錄 commit | 等待決策 | 等待決策 |
| 3 | 傳出決策，部分訊息遺失 | 收到 commit 並提交 | 未收到，仍 in-doubt |
| 4 | 暫時失聯 | 保留已提交工作 | 等待逾時，但無法由此推論 abort |
| 5 | 恢復並重傳持久決策 | 核對既有終態 | 收到 commit，完成配額交易 |

若 Quota DB 在第 4 步自行放棄，便出現「工作成立、配額交易卻放棄」的矛盾終態。即使客戶端早已停止等待，也不能撤回第 2 步已成立的決定。模型與恢復依據見 [Gray、Lamport §3.1、§3.3](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-2003-96.pdf)。

實作要能用 `tx-42` 辨認重送與查詢，不能讓重試重新建立另一筆交易。若參與者已知有效的最終決策，可按恢復協定傳播；未知時，不能把「沒收到 commit」當成「不存在 commit」。

## 故障點不同，恢復方法也不同

| 故障位置 | 可依賴的證據 | 安全處理的邊界 |
| --- | --- | --- |
| 參與者尚未預備 | 尚未交出不可自行撤回的贊成承諾 | 可依協定放棄，不能之後又替同一交易回覆相反承諾 |
| 已預備，但決策不可得 | 本地 prepared 紀錄 | 查詢、等待或恢復；不可只因 timeout 就猜終態 |
| 協調者已持久決定，但傳播不全 | 權威決策紀錄 | 恢復後重傳同一決定，不能重新投票改判 |
| 協調者恢復，尚未形成 commit | 完整且可信的協調狀態與恢復規則 | 可依該協定決定 abort；單憑遺失或不完整日誌的「查不到」不足以判斷 |

經典 2PC 的阻塞是某些故障歷程下無法安全得知決策；不是每次協調者當機都永久停住。若已有決策證據，或原協調者能恢復，便可能繼續；反之，即使只是長時間斷線，in-doubt 狀態也可能持續。活性還依賴參與者與通訊恢復、重傳及資源可用。

將協調狀態複寫可以改善某些失效情境，但不能只說「協調者用了 Raft，所以任何參與者失聯也能完成」。[Gray、Lamport §4](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-2003-96.pdf)討論 Paxos Commit；它不是把任意 2PC 管理程式接上共識服務就自動得到的保證。

## PostgreSQL 的產品邊界

PostgreSQL 18 提供 `PREPARE TRANSACTION`，之後可由外部交易管理器以 `COMMIT PREPARED` 或 `ROLLBACK PREPARED` 結束。預備狀態與原 session 分離，關閉連線不會自動替它完成；`pg_prepared_xacts` 可列出相關交易。來源：[PostgreSQL 18：PREPARE TRANSACTION，Description、Notes](https://www.postgresql.org/docs/18/sql-prepare-transaction.html)。

官方提醒，不應長期留下 prepared 交易：它們會繼續持有鎖，也會妨礙 VACUUM 清理。這些指令是外部交易管理的介面，不是一般應用程式可隨手加入的故障補救。人工處理時也必須查明全域決策，不能為了解鎖就任意 rollback。

## 常見錯誤推論與下一步

- **「某個參與者當機就必須 abort」**：若 commit 早已決定，當機後應恢復並完成該決策；故障不會回溯取消它。
- **「2PC 自動提供可序列化」**：提交決定與並行隔離是不同責任。
- **「寄信和上傳檔案也放進 2PC」**：外部系統必須實際支援共同交易協定，普通 API 呼叫不會自動成為參與者。
