# 租約、分散式鎖與 fencing

租約能讓失聯持有者的權限到期，但無法讓舊程序停止執行；受保護資源還需要辨認並拒絕過時的操作。

接續 [Raft 與複寫日誌](raft-and-replicated-logs.md)，現在把邊界移到外部：即使協調服務一致決定 worker B 接手匯出，暫停中的 worker A 恢復後，仍可能把舊檔案寫回去。

查證日期：2026-11-05。鎖、sequencer 與 session 依 Chubby（2006）原論文整理；世代比較與匯出流程為明訂條件的自創設計，未部署鎖服務或執行程序暫停實驗。

## 鎖、租約與 session 各在處理什麼

分散式鎖（distributed lock）協調誰可進入某段受保護工作。若持有者停止卻沒有釋放，服務就需要一種回收權限的方法。租約（lease）讓授權有期限；session 則可把多個 handle 與續約、失效通知等行為連在一起。

Chubby 以 session 和 KeepAlive 管理客戶端存續；鎖屬於諮詢鎖（advisory lock），主要限制其他取得同一把鎖的嘗試，不會自動阻擋外部服務的所有寫入。其他產品的 lease 與 session API 可能不同，不應直接套用 Chubby 的全部語意。來源：[Chubby §2.4、§2.8](https://storage.googleapis.com/gweb-research2023-media/pubtools/4444.pdf)。

這裡的時效是鎖服務與客戶端協定的一部分，不代表所有機器共享完全準確的時間。續約失敗也不等於 worker 被關閉；即使程式有取消邏輯，已送出的請求仍可能在網路中延遲。

## 故障歷程：持有者恢復後覆蓋新結果

假設匯出服務讓一個 worker 更新 `export-42` 的輸出，所有寫入目前都不檢查世代：

| 步驟 | 事件 | 風險 |
| --- | --- | --- |
| 1 | A 取得租約，算出舊版內容 | A 現在有處理權限 |
| 2 | A 在檢查租約仍有效之後暫停 | 程序無法繼續續約，但尚未停止 |
| 3 | 鎖服務使 A 的租約到期，將鎖授予 B | 協調服務可以正確地只承認 B |
| 4 | B 寫入新版內容 | 外部資源保存 B 的結果 |
| 5 | A 恢復，繼續送出原本準備的寫入 | 若資源無條件接受，B 的結果就被覆蓋 |

這不是兩個同時有效的租約才能造成的錯誤。鎖服務即使沒有重複授權，外部寫入仍可能交錯。Chubby 原文也指出：舊持有者先送出的請求，可能在另一個持有者操作之後才到達。來源：[Chubby §2.4](https://storage.googleapis.com/gweb-research2023-media/pubtools/4444.pdf)。

把步驟 2 的租約檢查再移近寫入，仍然留有檢查後暫停的窗口。單純加長 TTL 可以改變切換速度與誤判機會，不能在容許任意暫停的模型中消除這個問題。

## Fencing 把拒絕權放在資源端

Fencing 是讓受保護資源擋住過時持有者的操作。常見設計在每次有效取得權限時發出遞增的 fencing token；它表示同一資源範圍內的世代順序，不是 wall-clock 時間戳。

Chubby 的 sequencer 是包含鎖名稱、模式與 lock generation number 的不透明資料，持有者把它隨操作交給接收端，由接收端檢查有效性與模式。這是 Chubby 的具體介面，不能簡化成所有鎖服務都回傳同一種整數。來源：[Chubby §2.4、§2.6](https://storage.googleapis.com/gweb-research2023-media/pubtools/4444.pdf)。

以下用單調整數展示一種自創的資源端協定：

1. A 取得 `export-42` 的 token 41，之後暫停。
2. B 取得 token 42，先在資源端完成世代 42 的登記，再把自己視為已啟用的寫入者。
3. 資源端將「檢查 token、提高已接受世代、修改受保護資料」放在同一個原子邊界，持久保存檢查所需的狀態。
4. A 的 token 41 寫入晚到時，因低於資源已登記的 42 而被拒絕；資源重啟後也不能忘記這個門檻。

「先查目前世代，接著另發一次無條件寫入」仍有競爭窗口。不同資源可以用交易、條件寫入或專門協定形成上述原子邊界，但必須核對其實際語意。

## 單調 token 沒有自帶即時撤銷

若資源只保存「目前看過的最大 token」，它保證的是：接受新世代後，不再接受更舊的世代。它不會憑空知道鎖服務剛剛做了什麼。

例如 A 的租約已過期，B 已取得 42，卻還沒把 42 登記到資源端；資源仍只知道 41，此時 A 的請求不一定會被拒絕。新持有者先登記世代，可以建立之後的拒絕門檻，卻不能回溯阻止登記之前的操作。若業務要求「租約一到期就禁止所有舊寫入」，就還需要把有效權限的驗證與資源操作納入可證明的共同協定，不能只說 token 會遞增。

以上是對「最高已見世代」這種設計的推論，不是 Chubby 對任意外部資源提供的全面保證。它也沒有處理同一世代內的重送與先後：同一個 token 可以有多次合法操作，必要時還需操作識別與額外的版本條件。

## 外部儲存不支援檢查時怎麼辦

在物件 metadata 放一個 `token=42`，不代表儲存服務會自動比較數字，或把比較和物件覆寫原子地執行。應先確認目的服務支援哪些條件與競爭控制，不能把描述資料當成已實作的 fencing。

對匯出案例，一種可討論的設計是：每個嘗試使用不同、不可覆寫的物件名稱，再透過能原子檢查世代的中繼資料庫發布「目前有效輸出」指標。這只保護被選中的輸出；舊 worker 仍可能上傳無人引用的檔案，產生成本與清理需求。若任由舊 worker 覆寫已被選中的物件，這個設計的前提就不成立。

Chubby 對不能配合 sequencer 的系統提供 lock-delay：某些失效情況下，延後把鎖重新交給別人，以降低延遲請求造成的風險。原文明確把它視為不完美的機制，不能當成任意延遲下的嚴格保護。來源：[Chubby §2.4](https://storage.googleapis.com/gweb-research2023-media/pubtools/4444.pdf)。

## 常見錯誤推論與下一步

- **「鎖服務很強一致，所以外部寫入安全」**：還要檢查每個外部寫入入口是否執行資源端驗證。
- **「有 fencing 就不必去重」**：世代拒絕不等於同一操作只生效一次；重送契約仍見[冪等副作用](retries-and-idempotent-effects.md)。
- **「fencing token 就是授權憑證」**：順序判斷與身分驗證是不同責任；本文處理的是非惡意程序故障模型。
