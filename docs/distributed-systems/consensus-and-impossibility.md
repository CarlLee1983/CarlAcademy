# 共識、安全性與不可能性邊界

共識讓多個節點對同一個決定取得一致結果，但能否做出決定，以及已做出的決定會不會互相矛盾，是兩個不同問題。

接續[網路分割與 CAP](network-partitions-and-cap.md)，現在要問：文章匯出服務的副本如何共同決定工作狀態？單靠選出 leader 或收到多數回覆，還缺少哪些規則？

查證日期：2026-11-05。本文依 FLP、部分同步與 Raft 原始論文整理；案例為自創概念歷程，未執行分散式部署或故障注入實驗，也未重建完整形式證明。

## 先界定對什麼取得共識

考慮工作 `export-42`：一個節點提出「交給 worker A」，另一個提出「交給 worker B」。若規格要求同一輪指派只有一個結果，就需要所有作出決定的副本接受同一個指派。

常見的共識規格包含下列性質；不同論文對 validity 與故障節點的要求可能不同，引用時必須核對模型：

| 性質 | 在這個指派例子中代表什麼 |
| --- | --- |
| 一致決定（agreement） | 不得有副本決定 A，另一個卻決定 B |
| 有效性（validity） | 決定需符合提案限制；例如必須是某個節點提出的值 |
| 終止性（termination） | 在規格容許的執行與故障條件下，正確節點最終能作出決定 |

前兩項約束哪些結果可接受，屬於安全性（safety）；最後一項要求工作有進展，屬於活性（liveness）。一直等待可以避免矛盾，卻不能滿足終止性。FLP 原文甚至採用較弱的非平凡性要求：不同初始配置必須容許不同決定，並非直接使用上表這個較強的提案有效性定義。來源：[FLP（1985），§1–2](https://groups.csail.mit.edu/tds/papers/Lynch/jacm85.pdf)。

這也不等於業務資料自動正確。即使副本一致接受「配額減一」，仍需由狀態機檢查配額是否足夠；共識不會替應用程式補上遺漏的驗證。

## 選出 leader，不等於決定同一串命令

Leader election 回答誰負責協調；命令共識還要回答哪些命令已確定、順序為何，以及換 leader 後必須保留什麼。

若 A 宣稱自己是 leader，卻與 B、C 失聯，B、C 可能選出新的 leader。A 的程序仍在執行，甚至還能接到客戶端請求。因此「大家曾選過 A」不能證明 A 現在可以獨自確認寫入。協定需要任期、投票限制、日誌與提交規則一起維護決定；[Raft 原文 §5](https://raft.github.io/raft.pdf)正是把這些機制組合起來。

同樣地，「有兩票」只描述某個集合的大小，沒有說明投票者能否對衝突結果再投票，也沒有交代重啟後是否記得承諾。多數派交集有意義，還需要相交節點保留並遵守協定狀態。

## 從單一決定延伸至複寫狀態機

複寫狀態機（replicated state machine）把共同決定延伸為一串有順序的命令，例如：

1. 建立工作 `export-42`。
2. 將工作指派給某次 worker 嘗試。
3. 登記產出的檔案與完成狀態。

在相同初始狀態下，各副本依相同順序執行確定性的狀態轉移，才能得到相同狀態。若執行命令時各自取亂數或讀本機時間，便可能分歧；這些會影響結果的輸入也需要被一致決定。機制依據見 [Raft §2](https://raft.github.io/raft.pdf)，匯出命令是本文的設計例子。

「登記完成」仍不等於外部通知只寄一次。副本狀態之外的檔案與通知，需要另訂副作用契約，不能因日誌有共識就宣稱端到端效果不重複。

## FLP 究竟排除了什麼保證

Fischer、Lynch 與 Paterson 的 1985 年結果，研究的是完全非同步（fully asynchronous）的確定性訊息傳遞模型：程序速度和訊息延遲沒有已知上界，訊息可靠傳遞，至多一個程序可以停止。即使如此，仍不能讓共識協定在所有容許的執行中都保證終止。來源：[FLP，§2–3、Theorem 1](https://groups.csail.mit.edu/tds/papers/Lynch/jacm85.pdf)。

重點是「所有容許執行」的終止性保證。定理沒有說每次執行都失敗，也沒有說安全性無法維持，更沒有給出實際服務的故障機率。

用自創歷程理解其中的困難：

| 步驟 | A、B 看見的現象 | 仍然無法排除的情況 |
| --- | --- | --- |
| 1 | A、B、C 正協調下一個工作指派 | 尚未形成不可撤回的共同決定 |
| 2 | C 的回覆遲遲未到 | C 停止，或只是非常慢 |
| 3 | A、B 的計時器到期 | 在此模型中，逾時仍不能證明 C 已停止 |
| 4 | 協定嘗試繼續交換訊息 | 後續的關鍵訊息也可能再被延後 |

這張表只是幫助辨認不確定性，並非 FLP 證明。完整證明從仍可能導向不同決定的配置出發，構造符合模型卻不決定的執行；不能把「某個簡單協定等不到 C」當成已證明所有協定都不可能。

## 部分同步如何改變進展條件

Dwork、Lynch 與 Stockmeyer 的部分同步（partial synchrony）模型增加時序前提，例如界限存在但事先未知，或已知界限要到某個未知時間後才保證成立。這與「網路通常很快」不同，也不表示節點可以辨認全域穩定時間。來源：[DLS（1988），摘要與 §1](https://groups.csail.mit.edu/tds/papers/Lynch/jacm88.pdf)。

實用協定可以在延遲與分割期間保住安全性，並在多數節點恢復通訊、排程與儲存處理足夠穩定後取得進展。Raft 還以隨機選舉逾時降低反覆分票的機會；這些安排不能解讀為任意非同步排程下都有固定完成期限。參考 [Raft §5.2、§5.6](https://raft.github.io/raft.pdf)。

因此可以清楚區分三種承諾：不出現衝突決定、滿足額外條件後能繼續，以及在某個延遲目標內回覆。它們需要不同證據，不能只用「高可用共識叢集」一句帶過。

## 常見錯誤推論與下一步

- **「FLP 證明共識不能實作」**：它排除特定模型下無條件的終止性保證；增加前提後可研究不同的活性條件。
- **「逾時後排除舊 leader 就安全」**：逾時只是懷疑，舊程序與延遲訊息仍可能存在；協定要限制它們能做出的有效決定。
- **「日誌達成共識，業務就全部正確」**：還要檢查狀態轉移、不變式、讀取方式與外部副作用。
