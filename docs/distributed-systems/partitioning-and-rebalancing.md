# 分片、路由與資料搬遷

分片把不同資料分給不同儲存群組，讓容量與負載可以擴展；資料搬遷則必須同時維持資料完整性與寫入所有權。

接續[租約與 fencing](leases-locks-and-fencing.md)，本文把文章匯出工作的資料按使用者分組，討論分片鍵、路由、熱點，以及從舊位置搬到新位置時如何避免兩邊各自寫入。

查證日期：2026-11-05。分片策略參考 MongoDB 官方文件；搬遷案例是自創的單一寫入者設計，另以官方搬遷流程對照。未建立分片叢集，未驗證產品效能或執行線上搬遷實驗。

## 分片與複寫處理不同問題

複寫（replication）讓同一份狀態有多份副本；分片（partitioning／sharding）則把資料空間拆開，由不同群組負責。兩者可以並存：每個分片內再建立複本群組，以承擔各自的容錯責任。MongoDB 的 sharded cluster 即以 replica set 作為 shard。來源：[MongoDB Sharding](https://www.mongodb.com/docs/manual/sharding/)。

資料分片也不是[網路分割](network-partitions-and-cap.md)。前者是資料配置；後者是節點無法互通的故障情境。把資料拆成更多片，並不消除網路分割下的一致性取捨。

另一個容易混淆的概念是單資料庫內的分割表：它可以改善管理與查詢安排，卻不自動代表跨主機分片。可回查[分割表與連線資源管理](../relational-databases/partitioning-and-connection-management.md)。

## 分片鍵決定哪些工作容易一起完成

假設一位使用者的匯出工作都用 `user_id` 決定位置。依使用者查詢工作可能只需一個分片；跨所有使用者列出最近完成的匯出，則可能需要多片協作。

| 方法 | 有利之處 | 需要承擔的代價 |
| --- | --- | --- |
| 範圍分片（range） | 相鄰鍵值放在相鄰區間，適合相關範圍查詢 | 單調增加的鍵可能把新寫入集中到末端區間 |
| 雜湊分片（hash） | 打散不同鍵值，通常有助分散資料 | 原始鍵的鄰近關係被打散，範圍查詢可能要找多片 |
| 先切邏輯區間，再配置到節點 | 可搬動部分區間，不必直接重算每個鍵的實體節點 | 要維護位置表、版本與搬遷協定 |

前兩者可對照 [MongoDB ranged sharding](https://www.mongodb.com/docs/manual/core/ranged-sharding/) 與 [hashed sharding](https://www.mongodb.com/docs/manual/core/hashed-sharding/)；第三列是通用的設計安排，並非指定產品的完整介面。

Hash 不是負載均衡的保證。如果某一個 `user_id` 產生大半請求，單純對它取 hash 仍會集中到同一片。拆細鍵可以分散負載，卻可能把原本單片內的查詢與不變式拆開，因此要連查詢模式與一致性需求一起選擇。

## 路由規則也需要能安全演進

最簡單的 `hash(key) % 節點數` 在節點數改變時會重新分配許多鍵。例如某鍵的 hash 值為 4，在兩個節點時餘數是 0，三個節點時變成 1；若只修改取餘數的除數，資料不會自行搬到新位置。

自創匯出服務可以先把鍵映射到固定的邏輯區間，再用位置表記錄區間的 owner 與版本。如此擴容時搬的是部分區間，而非直接把每個路由器的節點數改掉。位置表本身仍需要一致更新與恢復規則；路由快取可以晚一些更新，但儲存端不能因此接受已失效的寫入權限。

這裡的版本表示位置或所有權的世代，不是業務資料版本，也不是網路時間。它不能單獨證明新位置已收到全部資料。

## 搬遷案例：先追齊資料，再切換權限

以下明訂為自創設計：每個區間只有一個有效寫入者，寫入與權限檢查共用原子邊界；協調紀錄可持久恢復，使用比較版本的更新決定 owner。資料變更包含新增、更新、刪除，以及同一範圍內需要的去重紀錄。

要把區間 R 從 S1 搬到 S2，可採取以下流程：

| 階段 | 資料處理 | 寫入權限 |
| --- | --- | --- |
| 1. 準備 | 記錄搬遷識別與位置版本 e，建立可對應變更日誌位置 p 的一致快照 | S1 仍是唯一寫入者；S2 不能對外確認寫入 |
| 2. 複製與追趕 | S2 複製快照，再重播 p 之後的所有變更 | S1 持續處理業務，變更紀錄不能在 S2 接到前被清除 |
| 3. 停住舊寫入 | S1 持久關閉 R 的舊寫入入口，排空已受理操作，確定最後位置 p*；S2 持久套用至 p* | 此時暫停 R 的新寫入，不能讓 S1 一邊繼續寫、一邊宣布追齊 |
| 4. 決定新 owner | 協調紀錄以版本條件把 owner 改成 S2、世代 e+1；S2 核對該決定後啟用 | S1 的舊入口繼續封閉，包括重啟後；S2 才開始受理新寫入 |
| 5. 更新與清理 | 路由逐步刷新；確認恢復、讀取與保留條件後才刪 S1 舊副本 | 舊路由的請求會被拒絕，不能靠舊資料繼續確認寫入 |

為什麼快照不夠？假設快照中 `export-42` 還是 `RUNNING`，複製期間 S1 已把它改成 `DONE`。若漏掉這筆增量，切換到 S2 後已完成的工作就會退回舊狀態。若漏掉刪除紀錄，已刪的資料甚至可能重新出現。

上述流程用短暫停止寫入縮小切換邊界，不是唯一解法，也不承諾無停頓。採用雙寫或轉送的設計還需處理順序、重送與失敗確認，不能只把第 3 步刪掉就宣稱零中斷。

## 故障恢復：不要猜測搬到哪一步

若 S1 已封住寫入，但切換決定尚未完成就發生故障，系統可能暫時沒有可用寫入者。這是此設計保住單一所有權的代價；恢復程序要讀持久紀錄，確認最後位置、目的端進度與 owner 決定，才能繼續或安全取消。

若 owner 已改為 S2，回覆卻遺失，重送同一個搬遷操作應讀回既有決定；不能任意把 S1 再啟用，因為 S2 可能已接受新寫入。若兩個協調者競爭切換，版本條件與可恢復的決策紀錄必須防止相互覆蓋。

同時，路由器即使還拿著 e，也不能讓 S1 認可寫入。拒絕舊路由後重新定位，只解決傳送位置；業務請求可能已在回應遺失前成功，因此重試仍需要[冪等契約](retries-and-idempotent-effects.md)。

## 產品對照與常見錯誤推論

MongoDB 官方的 Range Migration Procedure 描述：來源仍承接區間操作、目的端複製資料並同步期間變更、更新位置中繼資料，再清理來源文件。這可用來對照「複製、追增量、改位置、清理」的責任，但本文 e、p* 與入口封閉流程不是 MongoDB 協定的逐步重現；不據此推斷錯誤碼、預設時限或所有版本的內部保證。來源：[MongoDB Sharded Cluster Balancer：Range Migration Procedure](https://www.mongodb.com/docs/manual/core/sharding-balancer-administration/#range-migration-procedure)。

- **「資料量平均就沒有熱點」**：資料大小與請求頻率不同，搬遷本身還會消耗來源與目的端資源。
- **「路由表改完就搬完」**：還要證明資料追齊、舊入口失效與故障後的恢復決定。
- **「每個分片都有共識，所以跨片操作也原子」**：各片的局部順序不會自動形成跨片提交或全域隔離。

第三階段至此把共同決定、日誌安全、舊持有者與搬遷所有權串在一起。下一篇[原子提交與兩階段提交](atomic-commit-and-two-phase-commit.md)開始處理跨越單一原子邊界的工作；可先回查[交易與隔離](../relational-databases/transactions-and-isolation.md)，區分局部交易與跨片保證。
