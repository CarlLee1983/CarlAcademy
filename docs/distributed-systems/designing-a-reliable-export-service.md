# 整合案例：可靠的文章匯出服務

可靠的匯出服務需要把使用者意圖、工作狀態、檔案與通知的保證逐段接起來，並為每一個未知結果留下可恢復的責任。

本篇整合前十七篇，以最小單資料庫版本起步，依需求增加背景工作、事件交接、複寫與分片。這是自創的教學設計，不是本站已部署的功能，也不要求一開始就採用微服務。

查證日期：2026-11-05。冪等與原子交接對照 AWS 官方工程文件；協調與所有權依本系列所列一手來源推導。下列狀態、物件命名與故障矩陣均為概念案例，未執行效能、部署或故障注入實驗。

## 先固定輸入、識別與不變式

使用者要求「把指定版本的文章匯出成一份檔案」。同一項意圖重試應查回同一個工作；重新選文章或變更格式則可能是另一個意圖。若輸入只記錄「文章目前最新版」，重試期間內容改變，兩次嘗試就可能根本沒有處理同一份輸入，因此本例保存文章版本或可重現的快照識別。

| 識別 | 本例用途 | 重試時是否保持不變 |
| --- | --- | --- |
| `operation_id` | 在呼叫者與操作範圍內識別同一業務意圖 | 同一意圖維持相同；同鍵不同參數拒絕 |
| `request_id` | 追蹤一次網路傳送嘗試 | 可以改變，不能替代意圖識別 |
| `job_id` | 已建立的工作實體 | 工作生命週期內不變 |
| `attempt_id` | 一次 worker 計算與其候選產物 | 接手重做時建立新的識別 |
| `event_id` | 一個已成立的完成事實 | relay 重送同一事實時不變 |

意圖紀錄的保留範圍與晚到請求政策是契約的一部分，不能刪掉去重紀錄後仍承諾任何年代的重試都安全。來源：[AWS：Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)。

本例先定義四項安全性條件：

1. 在有效意圖範圍內，同一意圖最多對應一份工作與一筆配額保留。
2. 保留和消耗額度的交易不得超過帳戶上限，重複釋放不得增加額度。
3. 只有工作目前的處理世代能選定正式結果；已成功工作不因舊嘗試回來而改寫結果。
4. 成功狀態必須參照符合約定完整性與保存契約的產物；通知狀態與工作成功分開。

「最終完成或補救」則是活性目標，還需要依賴恢復、足夠容量、持續排程與異常處置。不能把它混進一張沒有前提的不變式清單。

## 最小版本：一個資料庫就能保存工作責任

API 在一筆短交易內完成意圖唯一性檢查、輸入版本保存、配額保留與 `pending` 工作建立；衝突競爭由資料庫約束與交易處理，不能先查不存在再各自插入。提交後才回覆受理，回應遺失則用原意圖核對。原子邊界見[冪等副作用](retries-and-idempotent-effects.md)。

背景 worker 可以先掃描資料庫的待辦工作，不必為了非同步就立刻加入 broker。開始計算前，以原子條件取得工作、增加處理世代、保存 `attempt_id` 與恢復期限。長時間轉檔不包在資料庫交易裡。

| 工作狀態 | 合法推進 | 同時需要保存的證據 |
| --- | --- | --- |
| `pending` | 有資格的 worker 取得工作，進入 `running` | 嘗試識別、目前世代、恢復安排 |
| `running` | 暫時失敗後再試，或由恢復程序條件式接管 | 新世代與新的嘗試；舊嘗試不再有發布資格 |
| `running` | 產物符合契約，由目前世代提交 `succeeded` | 正式結果指標、結算與完成事實 |
| `pending`／`running` | 依明確政策終止為 `failed` | 原因、配額處置、需核對的外部效果 |
| `succeeded`／`failed` | 重送只查回終態；新意圖另建工作 | 不把舊命令當成重開終態工作的授權 |

期限到期只讓恢復者有理由懷疑，不會停止舊 worker。接管與完成更新必須在同一資料庫裁決邊界競爭；「先重設狀態、稍後再增加世代」會留下競爭窗口。背景見[租約與 fencing](leases-locks-and-fencing.md)。

## 檔案先保存，正式結果再由資料庫選定

本例要求每次嘗試寫入不同且不可覆寫的候選位置，例如 `exports/job-42/attempt-B.zip`。這個命名不自帶儲存保護；實作必須真的限制覆寫、驗證完整性，並維持被選定產物的保存與讀取契約。

候選檔案完整後，worker 在短交易內檢查工作仍為 `running`、世代等於自己持有的世代，才選定結果、結算保留與設定成功。這保護資料庫中的發布決定，不會讓物件儲存和 SQL 變成同一筆交易。若先寫檔後停止，允許留下無人引用的候選檔。

以 A 暫停、B 接手的概念歷程檢查：

1. A 取得 `job-42` 的世代 1，之後長時間暫停。
2. 恢復者以版本條件接管，B 取得世代 2。
3. B 寫好自己的候選檔，世代 2 的完成交易選定該檔案。
4. A 恢復並寫好另一份候選檔；不可覆寫規則使它不能改動 B 的產物。
5. A 用世代 1 完成時，資料庫條件不符，不得改狀態、結算或建立另一個完成事實。

使用者在成功後取得被選定的 B 結果，不表示物理檔案只生成一次，也不表示 A 不再消耗 CPU 或儲存。清理需核對引用、活動嘗試與保留政策，不能設定一個任意七天規則，連仍有效的正式結果一起刪掉。

## 有獨立交接需求，再增加 Outbox 與 broker

當工作需要交給獨立 worker 群組，或完成後有多個下游，本例在本地交易加入 Outbox：受理時一起保存待執行命令；完成時一起保存 `ExportCompleted` 事件。relay 重送使用同一應用識別，各 consumer 再保護自己的本地效果。來源：[AWS：Transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)；詳見[投遞語意、Outbox 與 Inbox](delivery-semantics-and-outbox.md)。

broker 的 ack 與工作完成分開。即使一個投遞已結束，持久工作掃描仍需能發現卡住的非終態工作；否則「已接收命令、尚未完成計算」的 crash 會遺失執行責任。

通知 consumer 可在本地交易去重並建立待送通知；真正寄送依供應者的冪等、查詢及保留期契約恢復。未知寄送結果保留為未知，不由工作成功狀態推論通知已到達。搜尋、統計與歷史重播的多下游分工，另見[事件驅動匯出整合](../event-driven-architecture/designing-event-driven-exports.md)，本篇不另維護第二套事件治理規則。

## 只有需求改變，才擴大協調邊界

| 出現的新需求 | 可以評估的機制 | 必須重新檢查的保證 |
| --- | --- | --- |
| 單機故障後仍需保存已確認工作 | 複寫、確認與受控切換 | 哪些確認寫入可能遺失？讀取能否看到最新狀態？見[複寫](replication-and-failover.md)與 [Raft](raft-and-replicated-logs.md) |
| 配額與工作不得不拆到不同服務 | 可支援的原子提交，或業務允許的補償 | [2PC](atomic-commit-and-two-phase-commit.md) 的 in-doubt 成本，或 [Saga](sagas-and-business-compensation.md) 的中間狀態與補償責任 |
| 寫入或容量瓶頸已由測量確認 | 分片、配置與搬遷 | 同使用者資料能否共置？跨片不變式、熱點與舊路由如何處理？見[分片搬遷](partitioning-and-rebalancing.md) |
| 可容許暫時不同的展示統計 | 適合型別的合併或 CRDT | [收斂](convergence-and-crdts.md)不取代配額授權，也不自動去除重複業務事件 |

增加唯讀副本不代表讀己之寫成立；採非同步複寫也不能直接承諾切換後保留所有已確認工作。若完成狀態的讀取必須符合[線性一致性](consistency-models-and-histories.md)，就要選擇能履行它的讀取路徑，而非任意從本地副本查詢。

## 故障矩陣必須能指出證據與下一責任人

| 故障點 | 應保留的證據與恢復 | 不能直接宣稱的結果 |
| --- | --- | --- |
| 受理提交後回應遺失 | 原意圖、參數與工作對應；同鍵核對 | 客戶端 timeout 等於未建立 |
| relay 發出後、補記前停止 | Outbox 與原命令／事件識別；核對後安全重送 | broker 不會重複交付 |
| 檔案保存後，完成交易結果未知 | 工作終態、世代、結果指標與候選檔 | 斷線表示交易 rollback；立刻重做或刪檔一定安全 |
| B 接手後 A 恢復 | 目前世代與完成條件；拒絕 A 的發布 | 舊 worker 已停止、所有外部寫入都被 fence |
| 通知 API 已接受但回應遺失 | 穩定通知識別、供應者查詢結果或未知紀錄 | 本地重試一定不會重寄 |
| 多數副本或權威資料不可用 | 依確認與恢復契約等待、拒絕或轉人工核對 | 用舊快照重建就能保留所有已確認狀態 |

未知不等於永久不處理。人工案件需要 owner、證據、可允許的處置與追蹤結果；自動重試也要有期限、退避及容量控制，避免恢復流量壓垮依賴。回查[過載與背壓](overload-deadlines-and-backpressure.md)。

## 讓承諾可以被否證

測試時按[觀測、故障注入與歷程驗證](observability-and-fault-testing.md)，保存同鍵並行、提交回應遺失、舊 worker 恢復、重複事件與補償重送的操作歷程；同時檢查意圖唯一性、額度、正式結果與未知效果。正常路徑能產檔，並不足以支持這些承諾。

Trace ID 用來關聯呼叫鏈；`operation_id`、`job_id`、`attempt_id` 可作應用紀錄的關聯欄位，不應直接塞進 W3C `traceparent` 的固定格式。完整的業務證據也不能只靠可能被抽樣的 trace 保存。

這份設計可以停留在單資料庫與背景掃描。只有遇到具體需求，才擴大到 broker、多副本或跨片協調；每擴大一次，都要重問原子邊界、故障後的證據、允許的未知狀態與恢復責任。全系列入口見[分散式系統知識索引](README.md)。
