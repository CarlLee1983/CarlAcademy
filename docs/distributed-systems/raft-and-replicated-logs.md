# Raft 與複寫日誌

Raft 透過任期、受限制的選舉與日誌提交規則，讓多個副本依相同順序執行已決定的命令。

接續[共識與不可能性邊界](consensus-and-impossibility.md)，本文追蹤文章匯出服務如何在 leader 故障後保留已確定的工作，並區分收到日誌、提交與實際套用。

查證日期：2026-11-05。以 Ongaro、Ousterhout 的 2014 年 Raft 延伸版論文及 Ongaro 博士論文為依據。以下是固定成員、非拜占庭、持久狀態可正確恢復的概念模型；未實作 Raft，也未執行叢集切換實驗。

## 任期與投票需要留下可恢復的記憶

節點有 follower、candidate、leader 三種角色。Follower 在選舉逾時後可以成為 candidate，增加任期（term）、投自己一票並徵求選票；取得同一任期的多數票才成為 leader。任期是邏輯世代，不是實體時間。收到更高任期的請求或回覆時，節點更新任期並退回 follower。來源：[Raft §5.1–5.2、Figure 2](https://raft.github.io/raft.pdf)。

`currentTerm`、`votedFor` 與日誌是持久狀態，相關更新必須在回覆前保存到可靠儲存。否則節點重啟忘了投過誰，就可能在同一任期替另一個候選人投票，破壞多數票交集的意義。這裡要求持久化語意，不指定所有實作都使用同一個檔案系統呼叫。

「每個任期至多一位當選 leader」也不表示舊任期的 leader 程序已停止。舊 leader 可能還沒聽到新任期，卻無法僅憑本機身分有效提交新決定。

## 日誌新舊不能只看長度

每個日誌條目有位置（index）、建立時的任期與命令。Leader 發送 AppendEntries 時附上前一個位置及其任期，follower 檢查是否匹配，才能接續日誌；遇到衝突時修正未提交的後綴。

日誌匹配性質（Log Matching Property）是：兩份日誌若在同一 index 有相同 term，該處的命令及之前的前綴也相同。它依賴完整協定規則，並非只要替任意資料加上兩個整數就成立。來源：[Raft §5.3](https://raft.github.io/raft.pdf)。

投票還必須檢查候選人的日誌是否至少與自己一樣新：先比較最後條目的 term，term 相同才比較最後 index。例如最後條目是 `(term 8, index 12)` 的日誌，比 `(term 7, index 15)` 新，即使比較短。這項限制與提交規則共同形成 Leader Completeness：後續任期的 leader 保有先前任期已提交的條目。來源：[Raft §5.4.1、§5.4.3](https://raft.github.io/raft.pdf)。

## Replicated、committed 與 applied

| 狀態 | 可以得出什麼結論 | 還不能得出什麼結論 |
| --- | --- | --- |
| 已複寫（replicated） | 某些副本已保存條目 | 不一定符合提交規則；未提交條目可能被替換 |
| 已提交（committed） | 在協定與故障模型內，該命令已確定，不會由後續合法 leader 改寫 | 不代表每個副本都知道提交位置或已執行命令 |
| 已套用（applied） | 某個副本已依序把已提交命令套用至狀態機 | 不代表外部檔案上傳、通知等效果自動只執行一次 |

對固定三節點叢集，多數是兩個節點；但不能把「有兩份」當成完整提交判準。Leader 用副本數直接推進提交位置時，所選位置必須是**自己當前任期**的條目。當它提交後，之前的日誌前綴也被間接提交。來源：[Raft §5.4.2](https://raft.github.io/raft.pdf)。

## 為何舊任期條目有多數副本仍不夠

以下簡化 Raft Figure 8 的五節點反例；所有未提到的位置先假設有相同前綴，X、Y 都位於下一個 index：

1. S1 在 term 2 建立 X，只存於 S1、S2，未達五節點所需的三份。
2. S5 在 term 3 取得 S3、S4、S5 的選票，建立同位置的 Y，但只存於自己，隨後停止。
3. S1 在 term 4 取得選票，恢復複寫 X，讓 S1、S2、S3 都有 X；此時 X 已有三份，但仍屬於 term 2。
4. 如果 S1 未先提交 term 4 的條目就再次停止，S5 可在下一任期取得 S3、S4、S5 的票：S5 最後條目的 term 3 比它們的舊條目新。
5. S5 的 Y 因而可能取代未提交的 X。若第 3 步只因三份副本就宣稱 X 已提交，便會給出錯誤承諾。

若第 3 步之後，S1 把一個 term 4 的新條目複寫至多數並提交，X 就隨此前綴間接提交；後續選舉不能再導致上述覆寫。細節與安全性論證見 [Raft Figure 8、§5.4.2–5.4.3](https://raft.github.io/raft.pdf)。

## 匯出工作：提交後回應遺失

另一個自創三節點歷程用來觀察客戶端行為：

| 步驟 | 叢集事件 | 對使用者的含義 |
| --- | --- | --- |
| 1 | A 是 term 7 leader，將「建立 export-42」寫入 index 11 | 尚不能只因 A 本機寫入就確認成功 |
| 2 | B 持久保存此 term 7 條目，A 取得多數確認並提交、套用 | 工作已確定，但給客戶端的回應遺失 |
| 3 | A 失聯，B 與 C 在 term 8 選出 B | B 保有 index 11；不能將已提交工作當成未發生 |
| 4 | B 提交 term 8 的 no-op，逐序套用前綴 | 即使 B 原先不知道 index 11 已提交，也能建立安全的提交進度 |
| 5 | 客戶端向 B 重送建立請求 | 若缺乏去重，仍可能增加第二個業務工作 |

因此客戶端需要穩定的操作識別，去重紀錄及結果需隨狀態機保存、複寫並納入恢復，不能只存在舊 leader 的記憶體。簡化的「每個客戶端記最後序號」也有順序與會話前提；不能直接套到任意並行或過期重試。參考 [Raft §8](https://raft.github.io/raft.pdf)、[Ongaro 博士論文 §6.3](https://raw.githubusercontent.com/ongardie/dissertation/master/stanford.pdf)，以及本站[冪等副作用](retries-and-idempotent-effects.md)。

## 線性一致讀需要額外的確認

孤立的 A 若直接回覆本地狀態，可能漏掉新 leader 已完成的更新；讀請求沒有修改資料，也仍可能違反線性一致性。

Ongaro 博士論文 §6.4 的讀取方式依序要求：

1. 確認本任期至少有一個已提交條目，新 leader 通常先提交 no-op。
2. 記錄目前提交位置為 `readIndex`。
3. 針對這次讀取或涵蓋它的批次，發起新一輪心跳並取得同任期多數確認。
4. 等待本地狀態機至少套用到 `readIndex`，再查詢並回覆。

不能拿讀請求之前的一次普通心跳，代替上述確認；也不能在只更新 commit index、尚未 apply 時就讀出舊狀態。這是在讀操作區間內建立有效觀測點，並非承諾回應時包含所有並行寫入。來源：[Ongaro 博士論文 §6.4](https://raw.githubusercontent.com/ongardie/dissertation/master/stanford.pdf)。

若改用 lease read 避免逐次通訊，安全性會額外依賴租約設計與時鐘誤差假設；不再能直接沿用基礎日誌協定「安全性不靠時序」的結論。來源：[同論文 §6.4.1](https://raw.githubusercontent.com/ongardie/dissertation/master/stanford.pdf)。

## 保證的邊界與下一步

在固定成員、正確持久化與非拜占庭故障假設下，Raft 保護已提交日誌；它不能承諾多數副本永久毀損後仍恢復資料，或在失去可通訊多數時繼續提交。成員變更、快照與日誌截斷也必須遵守各自協定，不能由「加一台、刪一台」自行推導安全性。

常見錯誤是把多數複寫等同提交、把 leader 本地讀等同線性一致，或把日誌去重等同外部副作用去重。下一篇[租約、分散式鎖與 fencing](leases-locks-and-fencing.md)會處理日誌之外的舊 worker：它已失去所有權，為何仍可能覆蓋新輸出？
