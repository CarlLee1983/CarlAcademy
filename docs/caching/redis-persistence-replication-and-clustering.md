# Redis 持久化、複寫與高可用性

快取服務雖然主要運行於記憶體中，但在生產環境中，資料落地備份、主從複製與水平擴展能力是抵禦節點宕機、維持高可用性（HA）的必備支柱。
理解 RDB 與 AOF 的刷盤代價、主從增量同步機制，以及 Redis Cluster 的 Hash Slots 拓撲，是架構高彈性快取層的核心。

## 兩大持久化機制：RDB 與 AOF

Redis 提供兩種互補的持久化機制，各有其適用邊界與取捨：

### 1. RDB（Redis DataBase 快照）
在指定時間點將記憶體中的所有資料產生一個二進位壓縮快照檔案（`dump.rdb`）。
- **運作核心——Copy-on-Write（寫時複製）**：
  - 主進程呼叫 `bgsave`，作業系統透過 `fork()` 產生一個子進程。
  - 子進程與主進程共享相同的實體記憶體分頁。只有當主進程在後續修改某一分頁時，作業系統才會為該分頁複製一份獨立複本，由主進程寫入新值，子進程繼續讀取舊分頁寫入磁碟。
- **優缺點**：
  - 優點：RDB 檔案緊湊，實例重啟復原速度極快，適合做每日災難備份。
  - 缺點：資料遺失窗口較大（通常遺失最近 5–15 分鐘的變更）；若實例記憶體龐大（如 30GB），`fork()` 系統呼叫複製分頁表的時間可能長達數百毫秒，導致主執行緒短暫凍結。

### 2. AOF（Append-Only File 追加日誌）
以日誌形式記錄伺服器執行的每一個寫入命令（如 `SET`、`INCR`），以純文字通訊協定追加至檔案尾端。
- **刷盤策略（`appendfsync`）**：
  - `always`：每個寫入命令都強制執行作業系統 `fsync` 刷盤。安全但磁碟 I/O 嚴重拖慢吞吐量。
  - `everysec`（預設推薦）：由專門背景執行緒每秒執行一次 `fsync`。在效能與可靠性間取得最佳平衡，遭遇非預期斷電時最多僅遺失 1–2 秒資料。
  - `no`：不主動呼叫 `fsync`，交由作業系統核心自行決定刷盤時機（通常每 30 秒）。吞吐最高，但斷電遺失風險大。
- **AOF 重寫（AOF Rewrite）**：
  隨著時間推移，AOF 檔案會無限膨脹。Redis 在背景分析當前記憶體狀態，將數十次累加指令合併為單一命令（例如 100 次 `INCR` 壓縮為一次 `SET views 100`），產生最小化的全新 AOF 檔案並原子替換舊檔。

| 特性比較 | RDB 快照 | AOF 追加日誌 |
|---|---|---|
| **檔案大小** | 極為緊湊（二進位壓縮） | 較大（記錄操作命令文本） |
| **重啟復原速度** | 極快 | 較慢（需全量重播日誌指令） |
| **資料安全性** | 較低（遺失幾分鐘資料） | 極高（預設最多遺失 1 秒） |
| **系統負載開銷** | `fork()` 時 CPU 與記憶體瞬間飆高 | 均勻平滑的背景磁碟寫入 |

## 主從複製（Replication）與 PSYNC 協定

為了分攤讀取負載並建立容災副本，Redis 採用主從非同步複寫架構：
- **Master（主節點）**：負責處理所有寫入命令，並非同步將命令串流同步給從節點。
- **Replica（從節點）**：唯讀副本，分攤查詢 QPS。

### PSYNC 增量同步機制
當主從節點因網路抖動短暫斷線重連時，Redis 2.8+ 透過 **PSYNC** 協議避免昂貴的全量 RDB 傳輸：
1. **Replication ID**：標記當前主節點的資料歷史世代。
2. **Replication Offset**：主節點與從節點各自維護一個計數位移量，表示已經處理的位元組數。
3. **Replication Backlog Buffer（複製積壓緩衝區）**：主節點在記憶體中維護一個固定大小的環形佇列（預設 1MB，生產環境建議調大）。
- **斷線重連判定**：
  - 從節點傳送自己記錄的 `ReplID` 與 `Offset`。
  - 若 `ReplID` 相符，且從節點落後的 Offset 仍在主節點的環形緩衝區範圍內，主節點**僅需傳送落後的增量資料**即可完成同步。
  - 若落後太多被覆蓋，則退化為昂貴的「主節點產生 RDB → 網路傳送從節點 → 從節點全量重載」全量同步。

## 哨兵模式（Redis Sentinel）：自動故障轉移

單純的主從複製無法自動處理主節點宕機。**Sentinel 哨兵叢集**（至少 3 台獨立部署）負責監控與決策：
1. **主觀下線（sdown）**：單一哨兵節點向主節點發送心跳逾時未回應。
2. **客觀下線（odown）**：當超過法定人數（Quorum，如 3 個哨兵中有 2 個）皆判定主節點主觀下線時，正式宣告主節點客觀下線。
3. **領導者選舉與提升**：哨兵叢集內部以類似 Raft 的演算法選出一名代表哨兵，依據「從節點優先級、複製 Offset 最新者、RunID 最小者」挑選最健康的從節點提升為新主節點，並通知其他從節點切換同步目標，最後向用戶端推播新的連線地址。

## 水平擴展：Redis Cluster（16384 Hash Slots）

當資料總量超過單一伺服器的 RAM 上限（例如需要 500GB 快取）時，必須採用水平分片——**Redis Cluster**。

### 雜湊槽（Hash Slots）路由架構
- Redis Cluster 捨棄了一致性雜湊（Consistent Hashing），而是將整個資料空間固定劃分為 **16,384 個 Hash Slots（雜湊槽，編號 0 至 16383）**。
- 每個叢集節點負責管理其中的一部分槽位（例如節點 A 管理 0–5460，節點 B 管理 5461–10922，節點 C 管理 10923–16383）。
- **Key 的槽位計算**：
  $$\text{Slot} = \text{CRC16}(\text{key}) \pmod{16384}$$
- **Hash Tag 強制路由**：若業務要求多個 Key 必須落在同一分片（以執行 Lua 腳本或多 Key 批次操作），可在 Key 名稱中加上大括號 `{}`，例如 `{user:100}:profile` 與 `{user:100}:orders`，系統將只對括號內字串計算 CRC16，確保兩者分配至同一個 Slot。

### MOVED 與 ASK 重定向
- 用戶端會快取節點與 Slot 的映射表。
- 若槽位已永久搬遷，節點返回 `-MOVED {slot} {target_ip}:{port}`，用戶端更新本機路由快取並轉向新節點。
- 若槽位正在資料搬遷過程中，節點返回 `-ASK`，用戶端僅本次請求臨時轉向目標節點，不更新本機快取。
