# 多層快取整合案例：文章服務實踐

在超大規模流量的現代系統中，單一快取層難以同時兼顧極低存取延遲、龐大儲存容量與高可用容錯。
整合「L1 本機行程內快取 + L2 分散式快取叢集 + L3 關聯式資料庫」的多層快取架構（Multi-Tier Caching），是構建百萬 QPS 穩定應用的完整工程實踐。

## 多層快取架構全景拓撲

在 CarlAcademy 的文章發布與閱讀服務中，三層存取架構的職責劃分如下：

```
[ 用戶端 (Web / App) ]
         │
         ▼
[ 應用伺服器 (Go / Node.js 節點) ]
  ├── L1 Cache (本機行程內記憶體: Caffeine / FreeCache)
  │    └── 存取延遲: 100 ns | 容量預算: 500 MB (僅存 Top 1% 超級熱點)
  │
  └── 透過連線池存取 ───┐
                       ▼
[ L2 Cache (分散式 Redis Cluster 叢集) ]
       └── 存取延遲: 1–2 ms | 容量預算: 64 GB (儲存全站熱門與溫資料)
                       │ (Miss)
                       ▼
[ L3 Database (PostgreSQL 主從資料庫) ]
       └── 存取延遲: 10–50 ms | 權威真實資料源 (System of Record)
```

## L1 本機快取的同步與失效廣播機制

引入 L1 本機快取雖然將延遲壓到了奈秒極限，但帶來了嚴峻的「單機資料孤島」問題：
當某個作者在伺服器節點 A 編輯了文章，伺服器節點 B 的 L1 記憶體中仍保留著舊文章快取。如何讓所有節點的 L1 快取保持同步？

### 方案：Redis Pub/Sub 或訊息佇列廣播失效
1. **變更觸發**：當任一節點更新資料庫並刪除 L2 Redis 快取後，向 Redis 發布一條廣播訊息：
   ```
   PUBLISH cache:invalidate "article:42"
   ```
2. **集體清空**：全站所有應用伺服器節點長連線訂閱該頻道。收到廣播訊息後，立即在各自的本機記憶體中執行 `L1.Evict("article:42")`。
3. **容錯保護（短 TTL）**：為防範網路抖動導致廣播訊息遺失，L1 快取的實體 TTL 必須設得極短（例如 10 秒至 30 秒）。即使漏收廣播，最多 30 秒內本機快取也會自動自然過期，收斂不一致。

## 核心監控指標與可觀測性矩陣

評估快取健康程度不能只憑感覺，必須建立以下四組核心度量指標（Metrics）：

| 監控維度 | 關鍵指標名稱 | 健康基準線 | 異常表徵與處置建議 |
|---|---|---|---|
| **命中率** | Cache Hit Ratio | L1 > 60%, L2 > 90% | 低於 80% 表示存在快取穿透、TTL 設太短或記憶體容量不足提前逐出 |
| **延遲分位數** | P95 / P99 Latency | L1 < 1µs, L2 < 5ms | P99 突增通常意味著發生 BigKey 傳輸、網路壅塞或 Redis 正在執行 Fork/AOF 重寫 |
| **記憶體健康度** | `mem_fragmentation_ratio` | 1.0 – 1.4 | 大於 1.5 表示嚴重碎片，小於 1.0 表示開始 Swap，需立即擴容或重啟 |
| **逐出頻率** | `evicted_keys` 增長率 | 趨近於 0 | 數值急遽上升表示記憶體容量已達上限，正在被迫丟棄可能有價值的資料 |

## 完整故障情境演練矩陣（Failure Mode Analysis）

在架構上線前，必須依據故障歷程推演各層防禦能力：

| 故障情境 | 系統衝擊 | 自動防禦機制 | 最終使用者體驗 |
|---|---|---|---|
| **單一熱點文章過期** | 數萬併發同時請求同一篇失效文章 | L1 行程內 SingleFlight 合併請求；L2 採用邏輯過期或分散式互斥鎖 | 零延遲抖動，僅單一查詢向 DB 回填 |
| **黑客惡意遍歷不存在的 ID** | 海量隨機無效請求直擊底層 | 前置布隆過濾器（Bloom Filter）直接攔截 99% 流量；空值快取兜底 | 毫秒級快速回應 404，資料庫負載平穩 |
| **批量資料設定相同過期時間** | 數萬筆資料在同一秒集體過期 | 寫入時強制加入 `TTL Jitter`（隨機偏移 0–600 秒） | 資料庫負載曲線平緩，無脈衝式尖峰 |
| **Redis 主節點突然硬體斷電** | 集中式快取寫入暫時中斷 | Sentinel / Cluster 在 3–5 秒內自動完成容錯轉移；L1 本機快取維持熱點讀取 | 讀者無感知，少數寫入經歷數秒重試 |
| **底層資料庫發生嚴重逾時** | 資料庫 CPU 100%，回填受阻 | 應用層斷路器（Circuit Breaker）開啟，執行降級回應舊快取或靜態頁 | 網站維持唯讀可用，避免全站白畫面崩潰 |

## 全系列總結：快取架構的工程心法

從硬體物理階層出發，快取以空間換取時間；但架構師的職責，始終是在**延遲、成本與一致性**之間尋求最符合業務價值的精準平衡：
- 不要為不常讀取的資料建快取。
- 永遠為快取資料設定 TTL，並加上隨機抖動。
- 寫入時先更新資料庫、再刪除快取。
- 善用布隆過濾器阻擋穿透，使用互斥鎖或邏輯過期抵禦擊穿。
- 建立端到端的可觀測性監控與熔斷降級機制，守護資料庫底線。
