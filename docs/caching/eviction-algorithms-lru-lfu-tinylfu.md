# 記憶體逐出演算法：LRU 到 W-TinyLFU

快取逐出演算法（Eviction / Replacement Algorithm）決定了當快取記憶體達到上限（Capacity Limit）時，系統該依據何種原則挑選並犧牲特定資料以騰出空間。
演算法的核心挑戰在於：如何以極低的 CPU 與記憶體開銷，準確預測未來的存取機率，同時抵抗突發流量與批次掃描造成的快取污染。

## 四大主流逐出演算法比較

### 1. FIFO（First-In, First-Out，先進先出）
最樸素的隊列模型。最早進入快取的資料最先被剔除。
- **致命弱點**：完全忽略資料的存取頻率與重要性。一筆從系統啟動便持續以每秒千次存取的超級熱點文章，只因建立時間較早，也會被無情剔除，導致嚴重的快取抖動與命中率暴跌。

### 2. LRU（Least Recently Used，最近最少使用）
LRU 建立在**時間局部性**假設上：如果一筆資料最近剛剛被存取過，那麼它在未來被再次存取的機率最高；反之，越久沒被碰過的資料越不可能再被使用。

- **實作架構**：通常以**雜湊表（Hash Table）搭配雙向鏈結串列（Doubly Linked List）**實作：
  - 雜湊表提供 $O(1)$ 的快速尋址定位。
  - 當某一筆資料被讀取或寫入時，將該節點從鏈結串列中拔出，移動至鏈結串列頭部（Head，表示最新使用）。
  - 當記憶體滿額需要淘汰時，直接刪除鏈結串列尾部（Tail，表示最久未用）的節點。
- **致命盲點——快取污染（Cache Pollution）**：
  若後台管理員突然執行了一次「文章全站批次搜尋或資料庫備份掃描」，遍歷了 50 萬篇歷史冷門文章。這批冷門資料只被讀取一次，但會依序排進鏈結串列頭部，將原本真正高頻的熱門文章全數擠出尾部淘汰。掃描結束後，全站快取充斥冷門資料，快取命中率瞬間歸零。

### 3. LFU（Least Frequently Used，最不經常使用）
LFU 建立在**頻率累計**假設上：存取次數越多的資料越有價值，淘汰時優先挑選歷史累計存取次數最少的資料。

- **實作架構**：每個資料節點維護一個存取計數器（Counter）。
- **致命盲點——歷史包袱與頻率飢餓**：
  1. **舊熱點難以退役**：某些歷史爆款新聞在過去一週內累積了 100 萬次存取，但現在已完全不再有人閱讀；由於其累計計數極高，它會長年霸佔快取無法被淘汰。
  2. **新熱點難以准入**：剛剛發布的全新優質文章，初始計數僅為 1；當記憶體滿額時，新文章會因為計數最低而被立即淘汰，永遠無法在快取中累積頻率。
  3. 為了解決此問題，LFU 必須引入複雜的**定期衰減（Decay / Aging）**機制，但衰減係數難以在不同流量特徵下精確調校。

### 4. Window TinyLFU（W-TinyLFU，新一代演算法標竿）
由 Ben Manes 等人在 2017 年 IEEE 論文中提出，並在高效能快取函式庫（如 Java Caffeine Cache）中被證實為現代命中率最高的演算法。W-TinyLFU 成功將 LRU 對突發新流量的敏銳度，與 LFU 對長期高頻資料的篩選能力完美融合。

```
                    ┌─── 淘汰候選 (Victim) ───┐
                    │                         ▼
新進入快取的資料 ──> [ Window Cache (小容量 LRU) ] ──> [ TinyLFU 頻率過濾器 ]
                                                          │
                                ┌────── 勝者晉級 ─────────┴───── 敗者直接淘汰
                                ▼
                    [ Main Cache (主快取: Probation / Protected LRU) ]
```

#### W-TinyLFU 的三大核心架構
1. **Window Cache（小容量 LRU，約佔總容量 1%）**：
   - 所有新進入快取的資料一律先進入 Window Cache。
   - 這一小塊區域專門用來吸收**時間局部性極強的突發流量**，確保新發布的文章不會一進來就被 LFU 計數器秒殺。
2. **TinyLFU 准入過濾器（Admission Policy）**：
   - 當資料從 Window Cache 即將被擠出時，系統不直接淘汰它，而是讓它與主快取中即將被淘汰的候選人（Victim）進行一對一 PK。
   - 透過空間效率極高的 **Count-Min Sketch（結合 4-bit 緊湊計數器與衰減重設機制）**，在僅需數 KB 記憶體的代價下精準估算兩者的歷史存取頻率。
   - **只有當新資料的存取頻率高於舊受害者時，新資料才被准許晉級進入主快取**；否則直接淘汰新資料，保衛主快取不受單次批次掃描污染。
3. **Main Cache（主快取，約佔總容量 99%）**：
   - 主快取內部再劃分為 **Probation（緩衝考察區）** 與 **Protected（受保護核心區）** 兩段，配合頻率提升晉級，達成近乎理論極限（Bélády 演算法）的快取命中率。

| 演算法 | 實作複雜度 | 記憶體開銷 | 抵抗批次掃描污染能力 | 適應歷史熱點過期能力 | 典型代表 |
|---|---|---|---|---|---|
| **FIFO** | 極低 | 極小 | 極差 | 良好（隨時間推移淘汰） | 簡易佇列 |
| **LRU** | 低 | 鏈結串列指標（每節點約 16–24B） | 極差（全盤洗牌） | 良好 | Redis、Memcached |
| **LFU** | 中高 | 計數器開銷與衰減邏輯 | 良好 | 差（需額外衰減機制） | 特殊資料庫 |
| **W-TinyLFU** | 高 | 緊湊 Count-Min Sketch（每 Key 約 8-bit） | **極高（天然免疫）** | **極高（自動衰退）** | Caffeine Cache |

## Redis 中的近似淘汰實踐（Approximated LRU/LFU）

生產環境中的集中式快取（如 Redis）在面對數千萬個 Key 時，出於記憶體極致優化考量，**並沒有採用維護雙向鏈結串列指標的精確 LRU**（因為兩個指標在 64 位元架構下會額外消耗 16 位元組記憶體）。

Redis 採用的是**隨機抽樣近似演算法（Approximated LRU/LFU）**：
1. 每個 Redis 物件（`robj`）只消耗 24 個位元（bits）紀錄最後存取時間戳或頻率估計值。
2. 當需要逐出資料時，Redis 不去遍歷全局鏈結串列，而是從字典中隨機抽取 $N$ 個 Key（預設 $N=5$，可由 `maxmemory-samples` 調整為 10）。
3. 從這 $N$ 個候選人中挑選最久未被存取（空閒時間最長）的那一個進行剔除。
4. 實驗證明：當抽樣數 $N=10$ 時，Redis 近似 LRU 的命中率表現已經極度逼近精確 LRU，但省下了數百 MB 的鏈結串列記憶體空間。
