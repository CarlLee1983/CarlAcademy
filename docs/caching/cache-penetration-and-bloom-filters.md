# 快取穿透、空值快取與布隆過濾器

快取穿透是指查詢一個在快取與底層資料庫中皆不存在的資料，導致每次請求都繞過快取防線直擊資料庫。
當這種無效請求被惡意攻擊者高頻遍歷或隨機產生時，資料庫將承受巨大的無效查詢負載，甚至引發連線池枯竭與服務崩潰。

## 快取穿透的發生場景

在標準的 Cache-Aside 讀取邏輯中：
1. 查詢快取 `GET article:-999` → Miss。
2. 查詢資料庫 `SELECT * FROM articles WHERE id = -999` → 結果為空（Record Not Found）。
3. 因為查無此資料，應用程式通常**不進行快取回填**，直接回傳 404 Not Found 給使用者。

如果攻擊者蓄意利用多個執行緒，以每秒數萬次的速度發送 `id = -1`、`id = -2` 或各類隨機生成的 UUID，由於快取永遠無法命中，每一筆惡意請求都會直接打到後端資料庫。資料庫將被迫在磁碟或 B-Tree 索引中反覆尋道檢索，直至 CPU 100% 或連線數耗盡。

## 防禦方案一：快取空物件（Cache Null Object）

最直觀且實作成本最低的防禦方式是「空值快取」。

### 運作原理
當應用程式查詢資料庫確認該記錄不存在時，仍向快取中寫入一個特殊的「空值佔位標記」（例如 JSON 字串 `"{}"`、`"null"` 或特定的常數值）：

```
SET article:-999 "{}" EX 60
```

當後續相同無效 ID 的請求湧入時，快取會命中該佔位符，應用程式識別為空值後直接回應 404，成功在快取層阻擋了對資料庫的無效查詢。

### 關鍵取捨與注意事項
1. **TTL 必須極短**：空值佔位符的過期時間（TTL）必須設得非常短（通常為 30 秒至 3 分鐘）。若設得太長，假設此時系統正好新發布了該 ID 的新文章，讀者在快取過期前將無法讀取新文章（出現暫態假 404）。
2. **記憶體佔用風險**：若攻擊者每次都使用完全不重複的隨機 ID，快取中將被灌滿大量無意義的空值 Key，可能加速正常資料被逐出（Eviction）。

## 防禦方案二：布隆過濾器（Bloom Filter）

當惡意請求的 ID 呈現大範圍、不重複的隨機分佈時，空值快取會耗盡快取記憶體。此時應在快取前置一層空間效率極高的機率型資料結構——布隆過濾器（Bloom Filter）。

### 運作原理
布隆過濾器由一個長度為 $m$ 位元的二進位向量（Bit Array）和 $k$ 個互相獨立的雜湊函式（Hash Functions）組成：

1. **初始化與寫入（加入有效資料）**：
   - 系統啟動或資料建立時，將所有合法的文章 ID（如 `42`）經過 $k$ 個雜湊函式計算，得到 $k$ 個雜湊值 $h_1, h_2, \dots, h_k$。
   - 將 Bit Array 中對應索引位置的位元全數標記為 `1`。
2. **查詢判定**：
   - 當請求傳入文章 ID 時，同樣經過 $k$ 個雜湊函式計算其索引位元。
   - **若有任何一個位元為 `0`**：該資料**絕對不存在**於資料庫中，直接拒絕請求，無需存取快取或資料庫。
   - **若所有位元皆為 `1`**：該資料**可能存在**於資料庫中，允許放行進行後續的快取與資料庫查詢。

### 布隆過濾器的核心特徵：假陽性（False Positive）

布隆過濾器具備絕對的「假陰性為零（No False Negatives）」特性：**它說不存在的，絕對不存在**；但具備可預期的「假陽性（False Positives）」：**它說存在的，有可能其實不存在**（因為不同 Key 的雜湊值可能恰好碰撞，導致對應的位元全被其他 Key 置為 1）。

假陽性率 $P$ 取決於位元陣列大小 $m$、元素數量 $n$ 與雜湊函式數量 $k$：

$$P \approx \left(1 - e^{-kn/m}\right)^k$$

在工程實踐中，通常給定預期資料量 $n$ 與容許的誤判率 $P$（例如 $P = 0.01$，即 1% 誤判），公式會自動推導所需的位元大小 $m$ 與最佳雜湊函式數量 $k \approx \frac{m}{n} \ln 2$。儲存 1,000,000 個元素並維持 1% 誤判率，僅需約 1.2 MB 記憶體，相比直接儲存 Key 節省了數百倍空間。

| 防禦維度 | 空值快取（Cache Null） | 布隆過濾器（Bloom Filter） |
|---|---|---|
| **實作難度** | 極低（幾行業務程式碼即可） | 中等（需維護位元陣列與雜湊運算） |
| **記憶體佔用** | 視無效 Key 數量而定，攻擊下可能膨脹 | 極低且固定（百萬筆僅需數 MB） |
| **防禦範圍** | 針對重複存取的無效 Key | 針對海量隨機、不重複的無效 Key |
| **資料更新處理** | 自動靠短 TTL 過期 | 標準布隆過濾器無法直接刪除元素 |
| **準確性** | 100% 精準（查到即為空） | 存在極低機率的假陽性（放行少量無效請求） |

## 貫穿案例：文章閱讀服務的雙層防禦鏈

在 CarlAcademy 的文章存取鏈中，建議結合兩種機制構成階層防禦：

```
使用者請求 (GET /articles/{id})
       │
       ▼
[ 1. 基礎參數檢驗 ] ──(格式不符，如 id <= 0)──> 回傳 400 Bad Request
       │
       ▼
[ 2. 布隆過濾器 (Bloom Filter) ] ──(判定不存在)──> 直接回傳 404 Not Found
       │ (判定可能存在)
       ▼
[ 3. 快取層 (Redis) ] ──(命中有效內容)──> 回傳文章正文 (200 OK)
       │ (命中空值標記) ──────────────────> 直接回傳 404 Not Found
       │ (快取 Miss)
       ▼
[ 4. 資料庫 (PostgreSQL) ]
       ├──(查得真實文章)──> 回填快取 (TTL 7天) ──> 回傳 200 OK
       └──(查無此資料)────> 寫入空值快取 (TTL 60秒) ──> 回傳 404 Not Found
```

## 常見誤解與限制

- **誤解：布隆過濾器可以取代快取。**
  布隆過濾器只告訴你「資料有沒有可能存在」，它本身不保存任何文章內容，不能作為讀取資料的快取使用。
- **誤解：文章被作者刪除後，只要在布隆過濾器中把對應的位元改回 0 即可。**
  標準布隆過濾器不支援刪除操作。因為一個位元可能同時被多個不同 ID 的雜湊共用；若將其設為 0，會連帶破壞其他有效資料的存在性判定。若系統有大量刪除需求，需採用計數布隆過濾器（Counting Bloom Filter，每個位置以計數器代替位元，但記憶體佔用多 4 倍）或定期由背景全量重建過濾器。
