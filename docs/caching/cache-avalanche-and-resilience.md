# 快取雪崩與彈性架構

快取雪崩（Cache Avalanche）是指在某一短暫時間區間內，快取層發生大面積集中失效，或快取服務實例整體癱瘓，導致所有原本由快取承擔的龐大流量瞬間灌入底層資料庫。
由於資料庫的設計吞吐量通常遠低於快取，這種暴增的流量會引發資料庫 CPU 100%、連線數暴增與逾時，最終導致整個後端服務群全面崩潰。

## 快取雪崩的兩大觸發誘因

快取雪崩通常由以下兩類情境引發：

### 誘因 A：大批快取設定了相同或相近的過期時間
- **場景**：每日特定時刻（如午夜 00:00），排程任務批量更新商品型錄、熱門文章或使用者推薦清單，並統一把這數十萬筆資料的 TTL 設為 24 小時。
- **結果**：在次日午夜 00:00:00，所有資料在同一秒集體過期。此時若有常態性流量湧入，快取全數未命中，百萬請求直撲資料庫，引發連鎖反應。

### 誘因 B：快取服務叢集遭遇單點故障或網路中斷
- **場景**：Redis 節點因記憶體溢出（OOM）、硬體故障、或網路分區（Network Partition）而發生離線，且缺少可靠的高可用容錯機制。
- **結果**：應用程式無法連線至快取層，所有讀取請求被迫全數降級轉向查詢資料庫。

## 防禦策略一：消除集體過期（TTL Jitter）

對於誘因 A，核心解法是在設定過期時間時引入隨機散佈機制（Jitter），禁止使用均勻固定的常數 TTL。

### 實作方式
假設業務基準有效期限為 2 小時（7200 秒），在寫入快取時隨機疊加一個偏移行距：

```go
// 基準過期時間 2 小時，加上 0 至 600 秒（10分鐘）的隨機偏移
baseTTL := 7200 * time.Second
jitter := time.Duration(rand.Intn(600)) * time.Second
actualTTL := baseTTL + jitter

client.Set(ctx, key, value, actualTTL)
```

透過此方式，數萬筆資料的過期時間會被均勻稀釋在 10 分鐘的平滑時間軸上，使底層資料庫在任何單一秒鐘只承受微量的平穩回填請求，化解雪崩衝擊。

## 防禦策略二：多層快取架構（Multi-Tier Caching）

單純依賴中央 Redis 叢集仍存在單點風險。更彈性的架構是在應用程式內部增加本機記憶體快取（L1 Cache），構建多層防線：

```
使用者請求
   │
   ▼
[ L1 行程內本機快取 (Caffeine / SyncMap) ] ──(命中)──> 回傳 (100ns)
   │ (Miss)
   ▼
[ L2 分散式快取 (Redis Cluster) ] ────────(命中)──> 回傳 (1ms) & 回填 L1
   │ (Miss)
   ▼
[ L3 真實資料庫 (PostgreSQL) ] ──────────(命中)──> 回填 L2 & L1 & 回傳 (20ms)
```

- **彈性保護**：即使 L2 Redis 發生暫態網路中斷或短暫重啟，L1 本機快取仍能阻擋 80% 以上的高頻熱點讀取，給予快取叢集充裕的恢復時間。

## 防禦策略三：快取服務的高可用拓撲

針對誘因 B，快取基礎設施必須具備高可用（High Availability）與自動故障轉移（Failover）能力：

1. **Redis 主從複寫與 Sentinel（哨兵）**：配置至少一主二從三哨兵，當主節點發生硬體故障時，哨兵叢集透過 Raft 類似的 Quorum 投票自動將健康的從節點提升為新主節點。
2. **Redis Cluster 叢集模式**：將 Key 空間分散在多個分片（Shards）上，單一分片故障只影響局部 Slot 的資料，不會導致全站快取同時癱瘓。

## 防禦策略四：資料庫自我防禦——連線池隔離、熔斷與降級

快取崩潰時，資料庫不能任由外部流量予取予求，必須在應用層與資料庫前建立剛性的防禦水壩：

### 1. 嚴格連線池配額（Connection Pool Quota）
應用程式對資料庫的連線池必須設定不可妥協的最大上限（`max_connections`，如單實例最多 20 連線）。當快取失效導致大量並行請求湧入時，超出連線池容量的請求在應用端立即排隊或拋出錯誤，**絕不允許向資料庫開啟無限連線**。

### 2. 斷路器與服務降級（Circuit Breaker & Fallback）
在存取資料庫的調用鏈路上掛載斷路器（如 Netflix Hystrix 或 Resilience4j 原理）：
- **Closed（閉合狀態）**：正常呼叫資料庫。
- **Open（斷路狀態）**：當資料庫逾時率或錯誤率在短時間內超過門檻（例如超過 50% 逾時），斷路器立即切換為 Open。所有後續請求不再存取資料庫，直接執行**降級邏輯（Fallback）**。
- **降級手段**：
  - 回傳靜態兜底資料（如首頁回傳預設的靜態熱門推薦）。
  - 回傳友善提示「系統繁忙，請稍後重試」，避免整個網站白畫面崩潰。
  - 允許暫態讀取舊快取（Stale Cache），即便過期仍放行讀取。

| 防禦維度 | 應對目標 | 實作手段 | 核心效益 |
|---|---|---|---|
| **TTL 隨機抖動 (Jitter)** | 解決批量資料同時過期 | 基礎 TTL + 隨機偏移 | 消除週期性尖峰，平滑化資料庫負載 |
| **多層快取 (L1/L2)** | 解決集中快取服務單點故障 | 本機記憶體 + 分散式 Redis | L1 攔截大部分流量，分散節點壓力 |
| **高可用叢集** | 解決硬體或進程崩潰 | Sentinel 哨兵 / Cluster 分片 | 節點異常時自動容錯與無縫接手 |
| **連線隔離與熔斷降級** | 災難發生時保護資料庫 | 限流排隊 + Circuit Breaker | 守住真實資料庫底線，防止系統全毀 |

## 貫穿案例：文章閱讀系統的雪崩防禦全景

在 CarlAcademy 的文章服務中，雪崩防禦貫徹全鏈路：

1. **文章索引同步**：定時同步程式對 5 萬篇發布文章寫入 Redis 時，採用 `TTL = 86400 + random(0, 7200)` 秒，將過期窗口攤平成 24 至 26 小時。
2. **服務端斷路器配置**：Web 伺服器對 PostgreSQL 查詢設置逾時（`query_timeout = 500ms`）。若在 10 秒內偵測到 30 次逾時，斷路器開啟 15 秒；期間文章頁降級使用邊緣 CDN 快取的備份 HTML 或靜態維護頁，確保資料庫能在無流量衝擊下自我排解並恢復健康。
