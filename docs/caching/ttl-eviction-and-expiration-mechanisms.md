# 過期策略、TTL 與清除機制

過期策略為快取中的資料設定有效期限（Time-To-Live, TTL），以確保陳舊資料能及時淡出並釋放記憶體。
過期（Expiration）與記憶體不足時的逐出（Eviction）是兩個本質不同的概念，理解其觸發機制是建構可靠快取架構的基石。

## 過期（Expiration）與逐出（Eviction）的關鍵差異

在快取系統中，釋放記憶體主要源自兩種不同原因：

| 維度 | 過期（Expiration / Expiry） | 逐出（Eviction / Replacement） |
|---|---|---|
| **觸發原因** | 資料的存在時間超過了預設的 TTL | 記憶體使用量達到上限（`maxmemory`），必須騰出空間 |
| **判定依據** | 時間戳記（Timestamp）與時間長度 | 淘汰演算法（如 LRU、LFU、Random、FIFO） |
| **資料狀態** | 資料在邏輯上已經失效（Stale / Invalid） | 資料在邏輯上可能仍然有效且具備未來的存取價值 |
| **可預測性** | 寫入時即可確定其壽命期限 | 取決於全域記憶體壓力與未來的流量存取模式 |

## TTL 的兩大底層清除機制

快取系統（以 Redis 為代表）如何在海量資料中有效率地清理已過期的 Key，而不會拖垮 CPU？主要依賴兩種機制的協同運作：

### 1. 被動惰性清除（Lazy Expiration）

當用戶端發起讀取或寫入某個 Key 時（如 `GET article:42`），快取伺服器在返回資料前，會先檢查該 Key 是否設定了過期時間以及當前時間是否已超過到期時間戳。
- 若已過期：伺服器立即將該 Key 從記憶體中刪除，並向用戶端返回空值（Miss）。
- 若未過期：正常返回資料。

- **優點**：CPU 開銷極低，只有真正被存取到的 Key 才會消耗 CPU 進行過期判斷。
- **缺點**：若某些 Key 在過期後再也沒有任何用戶端讀取，它們將永久佔用記憶體，形成記憶體洩漏。

### 2. 主動定期抽樣清除（Active Periodic Expiration）

為了避免冷門過期 Key 永久滯留，快取伺服器在背景事件迴圈中定期（例如每秒 10 次）執行主動抽樣清除演算法：

1. 從具有過期時間設定的 Key 集合（`expires` 字典）中，隨機選取一定數量（例如 20 個）的 Key。
2. 檢查這批 Key，並刪除其中所有已經過期的 Key。
3. 若這批抽樣中已過期的 Key 比例超過一定門檻（例如 25%），伺服器將不等待下一個週期，立即重複執行步驟 1 與 2。
4. 為了防止清理過期 Key 佔用過多 CPU 時間而阻塞正常請求，通常會設定嚴格的時間上限（例如單次迴圈最多執行 25ms）。

透過被動惰性清除與主動定期抽樣的結合，系統既保證了 CPU 的即時回應能力，又能在統計上確保絕大多數過期 Key 能在合理時間內被回收。

## TTL 隨機抖動（Jitter）：化解集體過期危機

在大量資料批次寫入快取的場景中，若工程師設定固定的過期時間，會埋下巨大的穩定性隱患。

### 現象與風險
假設每天凌晨 00:00，後台定時任務批次將 100,000 篇推薦文章寫入快取，統一設定 `TTL = 3600`（1 小時）。
在凌晨 01:00:00 的瞬間，這 10 萬篇快取將在同一秒內全數過期。此時若有讀者存取文章，快取將全數 Miss，所有併發流量瞬間直擊資料庫，此現象稱為**快取雪崩**。

### 解法：加入動態隨機抖動
設定 TTL 時，必須在基礎過期時間上加上一個隨機偏移行距（Jitter）：

$$TTL_{actual} = TTL_{base} + \text{random}(0, \text{jitter\_range})$$

例如基礎時間設為 3600 秒，隨機加上 0 至 600 秒的抖動。這會使 10 萬筆資料的過期時間均勻散佈在 1 小時至 1 小時 10 分鐘之間，將資料庫回填的壓力均攤在平滑的時間軸上。

## 貫穿案例：文章閱讀系統的 TTL 分級設計

在文章系統中，不同業務維度的資料適用不同的 TTL 策略：

1. **已發布的經典文章正文（`article:{id}:content`）**：
   - 內容極度穩定，TTL 設為較長週期（如 7 天），並加上 12 小時的隨機抖動。
   - 若作者編輯，依賴主動失效（`DEL`），不依賴 TTL 自然過期。
2. **作者最新動態與簡介（`author:{id}:profile`）**：
   - 設定中等 TTL（如 1 小時 + 5 分鐘抖動）。
3. **即時排行榜與熱門推薦（`ranking:hourly:top10`）**：
   - 時效性極高，TTL 設為 60 秒至 120 秒，無需大範圍抖動。
4. **驗證不存在文章的空值佔位符（`article:{id}:null`）**：
   - 防禦穿透專用，TTL 必須極短（如 30 秒至 60 秒），防止誤封鎖隨後新發布的真實文章。

## 常見誤解與限制

- **誤解：只要為每個 Key 設定了 TTL，記憶體就永遠不會被撐爆。**
  若寫入速度遠大於過期與清理速度，或者大部分 Key 的 TTL 設定過長，在到達過期時間之前，記憶體依然可能達到 `maxmemory` 上限。此時快取將提前觸發逐出機制（Eviction），淘汰未過期的資料。
- **誤解：Redis 的主從複製中，從節點（Replica）會獨立執行過期刪除。**
  在 Redis 主從架構中，從節點不會自行主動淘汰過期 Key。當主節點（Master）透過惰性或主動抽樣發現某個 Key 過期時，主節點會在 AOF / 複寫串流中明確合成一條 `DEL` 指令同步給從節點，確保主從資料的一致性。
- **限制：過期判定依賴本機時間。**
  若伺服器的系統時鐘（Wall Clock）發生大幅度 NTP 跳躍或校時錯誤，可能導致大量原本未過期的 Key 被判定為已過期，引發非預期的集體失效。
