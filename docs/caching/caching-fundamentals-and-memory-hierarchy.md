# 記憶體階層與快取代價

快取是利用存取速度較快但成本較高的儲存媒介，暫存高頻存取的資料複本，以換取系統吞吐量與回應延遲的顯著改善。
然而快取並非萬靈丹；引入快取的同時，也必然引入資料一致性維護、記憶體容量預算、過期失效管理與複雜度成本。

## 為什麼需要快取：記憶體階層的物理現實

現代計算機架構與分散式系統的效能瓶頸，往往不在於 CPU 計算能力，而在於資料傳輸與 I/O 延遲。從 CPU 核心到分散式資料庫，儲存媒介存在巨大的延遲階層差：

| 儲存層級 | 典型硬體與技術 | 典型存取延遲 | 相對 CPU 週期數量級（1 週期 ≈ 0.3ns） |
|---|---|---|---|
| L1 / L2 快取 | CPU 晶片內靜態隨機存取記憶體（SRAM） | 1–4 ns | 數個週期 |
| L3 快取 | 共享晶片內 SRAM | 10–20 ns | 數十個週期 |
| 主記憶體（RAM） | 動態隨機存取記憶體（DRAM，如 DDR5） | 50–100 ns | 約 200 週期 |
| 本機固態硬碟（SSD） | NVMe NAND Flash | 20–100 µs | 數萬至數十萬週期（約記憶體的 1,000 倍） |
| 本機機械硬碟（HDD） | 旋轉磁盤與磁頭尋道 | 5–10 ms | 數千萬週期（約記憶體的 100,000 倍） |
| 跨網路請求 | 同一資料中心內 TCP/IP 呼叫 | 0.5–2 ms | 數百萬週期 |
| 跨區域網路請求 | 跨雲端區域或跨國專線 | 20–150 ms | 數億週期 |

當應用程式每次讀取文章時都向關聯式資料庫執行 SQL 查詢，即使資料庫有記憶體暫存（如 PostgreSQL 的 Buffer Pool），請求仍必須經歷 TCP 封包序列化、網路傳輸、SQL 解析與鎖定機制，耗時約在數毫秒（ms）。
若將查詢結果暫存在行程內記憶體（In-Process Memory）或本機 Redis 實例中，存取延遲可驟降至微秒（µs）等級，系統承載量（QPS）可提升數十至數百倍。

## 快取的理論基礎：局部性原理

快取之所以能發揮效益，仰賴於程式運行時對資料存取的兩大統計特徵：

1. **時間局部性（Temporal Locality）**：如果一筆資料此時被存取，那麼它在近期內極有可能再次被存取。例如：熱門文章發布後，數萬名讀者在幾分鐘內反覆讀取同一篇內容。
2. **空間局部性（Spatial Locality）**：如果一筆資料被存取，與其相鄰或關聯的資料很可能也會被存取。例如：讀者讀完文章正文後，接著讀取該文章的作者簡介與留言列表。

如果系統的存取模式呈現完全均勻隨機分佈，或每筆資料僅被讀取一次且永不再讀，快取的命中率（Cache Hit Rate）將趨近於零，快取反而成為浪費記憶體與增加跳轉開銷的累贅。

## 貫穿案例：文章閱讀服務的存取特徵

在 CarlAcademy 的文章服務中，資料具有明顯的讀寫不對稱性：

- **文章內容**：寫入頻率極低（作者發布或偶爾修改），但讀取頻率極高（千百倍於寫入）。極度符合時間局部性，是快取加速的理想對象。
- **閱讀次數與按讚數**：高頻並行寫入累加，若每次點擊都直接對資料庫執行 `UPDATE articles SET views = views + 1 WHERE id = 42;`，將引發資料庫行鎖競爭（Row Lock Contention）。
- **使用者個人私密草稿**：存取頻率低、僅限特定作者讀取，若將全站所有草稿一律預載入快取，只會無端擠佔寶貴的記憶體空間。

## 引入快取的四項核心代價

決定使用快取前，必須充分評估以下四項架構代價：

1. **資料不一致性（Inconsistency）**：資料同時存在於真實資料庫（System of Record）與快取中，當資料庫被更新時，快取若未及時同步，讀者將讀到過期舊資料（Stale Data）。
2. **系統複雜度激增**：需要處理快取穿透、擊穿、雪崩、熱點 Key 傾斜以及序列化轉換等邊界問題。
3. **記憶體資源昂貴**：DRAM 單位容量的價格是 SSD 的數十倍；若快取未設定合理的容量上限與淘汰策略，記憶體耗盡（OOM）將導致服務崩潰。
4. **程式碼維護成本**：讀寫邏輯必須在應用層手動協調多份狀態，測試與除錯的難度大幅提高。

## 常見誤解與限制

- **誤解：只要加上快取，系統效能就會自動變快。**
  若快取命中率低（例如低於 70%），應用程式在每次讀取時都必須先經歷「查詢快取（Miss）→ 查詢資料庫（Hit）→ 回填快取」的雙重操作，整體延遲反而比沒有快取時更慢。
- **誤解：快取可以用來當作主要資料庫使用。**
  快取元件（如 Redis 或 Memcached）通常預設將資料保存在記憶體中，即使具備非同步持久化機制，也無法提供關聯式資料庫級別的完整 ACID 交易保證。快取資料必須被視為「隨時可能遺失且可從真實來源重建」的暫態資料。
- **限制：非所有資料都適合放入快取。**
  對資料一致性要求極高且存取頻率低的資料（如銀行帳戶餘額結算）、或高度動態變化的單次查詢結果，不應輕易引入快取。
