# 快取擊穿、熱點 Key 與防互斥鎖

快取擊穿（Cache Stampede）是指一個擁有極高併發存取的特定熱點 Key，在過期的瞬間，大量請求同時未命中快取並湧向底層資料庫回填。
這種群湧現象（Thundering Herd）會瞬間打滿資料庫連線池與 CPU，甚至引發相依服務的級聯故障。

## 穿透（Penetration）與擊穿（Stampede）的區別

在工程術語中，兩者經常被混淆，但其本質完全不同：

- **快取穿透（Cache Penetration）**：問題出在**資料本身不存在**（惡意掃描空 ID，快取與 DB 皆無）。
- **快取擊穿（Cache Stampede）**：問題出在**該 Key 是一筆極度熱門的真實資料**（例如首頁重磅新聞），但它的快取**恰好過期或被刪除**，導致高併發請求同時穿過快取層打到資料庫。

## 核心防禦方案一：分散式互斥鎖（Mutex / Lock）

最經典的防禦手段是「限流回填」：在快取未命中時，不允許所有並行請求同時去查資料庫，而是透過互斥鎖保證**只有一個執行緒去查資料庫並回填快取**，其餘執行緒原地等待並重試快取。

### 操作時序與流程
1. 請求進入，查詢快取 `GET article:hot:42` → Miss。
2. 嘗試獲取分散式互斥鎖（例如利用 Redis `SET lock:article:42 {token} NX PX 5000`）。
3. **成功獲得鎖的請求**：
   - 向 PostgreSQL 執行查詢：`SELECT * FROM articles WHERE id = 42`。
   - 將查得的結果寫回快取：`SET article:hot:42 {content} EX 3600`。
   - 釋放互斥鎖（以 Lua 腳本核對 Token 確保安全刪除）。
   - 回傳資料給客戶端。
4. **未獲得鎖的其他數千個請求**：
   - 不向資料庫發起查詢。
   - 短暫休眠（例如 50ms）後，重新嘗試讀取快取 `GET article:hot:42`。
   - 此時獲鎖的請求已完成回填，重試請求順利命中快取並返回。

### 互斥鎖的風險與邊界
- **超時釋放問題**：若獲得鎖的執行緒在查詢資料庫時卡死或發生 GC 停頓，鎖過期自動釋放，可能導致第二個執行緒介入重複查詢。
- **程式阻塞與尾延遲**：等待鎖釋放的請求會經歷額外的等待延遲（Tail Latency），且如果回填失敗，大量請求可能集體超時。

## 核心防禦方案二：邏輯過期與非同步回填（Logical Expiration）

為了徹底消除高併發讀取的等待延遲，可以採用「邏輯過期」方案：**在快取實體中永不設定 TTL，而是將過期時間戳作為資料的一個屬性欄位包進快取 Value 中**。

```json
{
  "expire_at": 1730880000,
  "data": {
    "id": 42,
    "title": "分散式系統架構深度解析",
    "content": "..."
  }
}
```

### 運作流程
1. 讀取快取：由於快取實體不設 TTL，快取**永遠命中**，絕不返回 Miss。
2. 應用層檢查內部 `expire_at` 欄位：
   - 若 `expire_at > 当前时间`：資料未過期，直接回傳 `data`。
   - 若 `expire_at <= 当前时间`：資料已邏輯過期。
3. **發現過期的第一個請求**：
   - 嘗試獲取非同步互斥鎖。
   - 獲鎖成功後，**立刻向背景執行緒池或非同步任務指派資料庫更新工作**。
   - 當前請求**不等更新完成**，直接將現有的舊資料（Stale Data）回傳給使用者。
4. 背景工作查庫完成後，將新資料與新的 `expire_at` 寫入快取，並釋放互斥鎖。

- **優點**：讀取 QPS 極高且延遲恆定為微秒級，徹底杜絕資料庫遭受 Thundering Herd 衝擊。
- **代價**：在背景更新完成前的短暫窗口內，讀者會讀到已過期的舊資料（犧牲暫態一致性換取可用性）。

## 核心防禦方案三：Facebook Memcached 的 Lease 租約機制

Facebook 在其知名論文 *Scaling Memcache at Facebook* (NSDI 2013) 中提出了一種精妙的 Lease 機制，同時解決了 Thundering Herd 與 Stale Set（舊資料覆蓋新資料）問題。

### 運作原理
- 當快取 Miss 時，Memcached 伺服器不會直接只回傳空值，而是回傳一個 64 位元的隨機數（稱為 **Lease Token**）。
- **伺服器端限流**：Memcached 嚴格規定，每隔一段時間（例如 10 秒）對同一個 Key 僅發放一個 Lease Token。
- 在這個時間區間內，隨後其他並行發起查詢的請求將**拿不到 Lease**，伺服器會通知它們稍後重試。
- 只有拿到有效 Lease Token 的客戶端，才能在查完資料庫後向快取執行 `SET` 回填。
- 若在此期間有寫入操作使該 Key 失效（Invalidate），伺服器端會立即將該 Key 先前發放的所有 Lease Token 判定為作廢。即使慢讀取此時拿著舊 Token 前來回填，也會被快取拒絕，徹底防止了 Stale Set。

## 核心防禦方案四：行程內 SingleFlight（請求合併）

若請求是在同一個應用程式服務實例內部並行產生（例如 Go 語言的 `singleflight.Group`），可以在記憶體中建立一個請求調度器：
- 對於相同 Key 的查詢，多個並行協程（Goroutine）共享同一個正在執行的資料庫查詢任務。
- 資料庫只執行一次查詢，結果產生後廣播拷貝給所有等待中的呼叫者。
- 這種機制在單機記憶體內即可攔截絕大多數擊穿流量，無需額外向 Redis 搶分散式鎖。

| 防禦機制 | 適用場景 | 延遲表現 | 一致性 | 依賴與複雜度 |
|---|---|---|---|---|
| **分散式互斥鎖** | 資料一致性要求高，不可容忍舊資料 | 等待鎖的請求延遲增加 | 強 | 需依賴 Redis 分散式鎖，需防死鎖 |
| **邏輯過期非同步回填** | 極高 QPS 熱點，容忍短暫舊資料 | 極低且平穩（恆微秒級） | 弱（最終一致） | 快取不設物理過期，需維護背景任務 |
| **Lease 租約機制** | 大規模快取叢集支援原生 Lease | 取決於重試退避策略 | 極高 | 快取伺服器需具備 Lease 原生協定 |
| **SingleFlight** | 單機內的高併發讀取合併 | 單一實例內無額外等待 | 高 | 僅限單機進程內，無法跨實例合併 |

## 貫穿案例：文章閱讀系統的熱點擊穿防禦

在 CarlAcademy 的文章系統中，熱點文章採取分級策略：

1. **一般文章**：採用 **SingleFlight**，單一 Web 節點內若在 10ms 內湧入 100 個針對 `article:100` 的 Miss 請求，合併為單一資料庫查詢。
2. **首頁推薦與重磅發布文章（Top 1% 熱點）**：採用**邏輯過期 + 背景非同步回填**：
   - 實體 TTL 設為「無限制」（或 30 天超長安全線）。
   - 邏輯過期設定為 10 分鐘。
   - 任何讀者存取時零等待直接取回正文；過期時由 SingleFlight 協程在背景非同步查詢 PostgreSQL 並原子更新快取。
