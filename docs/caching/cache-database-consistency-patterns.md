# 快取與資料存取架構：更新策略與 CDC

快取與資料庫的雙寫一致性（Cache-DB Coherence）是分散式系統架構中最經典且困難的課題。
因為快取與資料庫分屬於兩個獨立的儲存系統，缺少天然的跨系統分散式交易保證；如何在資料變更時協調兩者的更新時序，直接決定了系統是否會陷入資料永久不一致的泥淖。

## 核心問題：更新資料時，該更新快取還是刪除快取？

當業務資料發生變更時，應用程式有兩種選擇：

1. **更新快取（SET）**：
   - **嚴重併發風險**：假設執行緒 A 先發起寫入，執行緒 B 隨後發起寫入。若由於網路抖動，執行緒 B 更新 DB 後先一步更新了快取，隨後執行緒 A 才慢速抵達並更新了快取。此時**資料庫存的是 B 的最新值，而快取卻被 A 的舊值覆蓋**，造成快取與資料庫永久不一致。
   - **浪費運算資源**：若某個資料是複雜關聯計算的結果，頻繁寫入卻鮮少被讀取，每次修改都計算並寫入快取只會浪費 CPU。
2. **刪除快取（DEL，推薦做法）**：
   - 寫入時僅將快取失效（Invalidate）。下一次真正有讀者存取時，才透過 Cache-Aside 讀取真實資料庫並惰性回填。這天然避免了並行寫入順序錯亂導致的長久陳舊值。

## 先刪快取 vs 先更 DB 的並行時序競態分析

決定「刪除快取」後，下一個根本分歧是：**應該「先刪快取再更資料庫」，還是「先更資料庫再刪快取」？**

### 情況一：先刪除快取，再更新資料庫（高風險）

假設有寫入執行緒 A 與讀取執行緒 B 同時並行存取：

```
執行緒 A (寫入)                    執行緒 B (讀取)
─────────────────────────────────────────────────────────────
1. 刪除快取 DEL article:42
                                2. 查詢快取 GET article:42 (Miss)
                                3. 查詢資料庫 SELECT (讀到舊值 V1)
                                4. 回填快取 SET article:42 V1
5. 更新資料庫 UPDATE (寫入新值 V2)
```

- **結果**：資料庫成功更新為最新值 $V2$，但快取卻被執行緒 B 重新填入了舊值 $V1$。在此之後，所有讀者將持續讀取到錯誤的舊值 $V1$，直到快取 TTL 自然過期！
- **結論**：在高併發讀寫環境下，**「先刪快取再改 DB」極易引發嚴重的永久不一致**。

### 情況二：先更新資料庫，再刪除快取（標準 Cache-Aside，推薦）

同樣考慮寫入執行緒 A 與讀取執行緒 B 的極端交錯：

```
執行緒 B (讀取)                    執行緒 A (寫入)
─────────────────────────────────────────────────────────────
1. 查詢快取 (恰好過期 Miss)
2. 查詢資料庫 (讀到舊值 V1)
                                3. 更新資料庫 UPDATE (寫入新值 V2)
                                4. 刪除快取 DEL article:42
5. 回填快取 SET article:42 V1
```

- **分析**：要觸發上述不一致，必須同時滿足三個苛刻條件：
  1. 快取恰好在步驟 1 失效。
  2. 讀取執行緒在查完 DB 舊值後，發生長達數十毫秒的 GC 停頓或調度延遲。
  3. 寫入執行緒要在讀取線程回填快取之前，完整跑完「SQL 磁碟更新 + 網路傳輸 + 快取刪除」所有步驟。
- **結論**：由於記憶體回填快取的速度（微秒級）通常遠快於資料庫磁碟寫入（毫秒級），**先改 DB 再刪快取的競態發生機率極低**。因而在實務工程中被列為標準推薦模式。

## 延遲雙刪（Delayed Double Deletion）的適用與缺點

為了解決「先刪快取」或極端情況下的回填舊值，業界曾廣泛使用「延遲雙刪」：

```go
// 1. 先刪除快取
cache.Del("article:42")
// 2. 更新資料庫
db.UpdateArticle(42, newContent)
// 3. 休眠一段時間（例如 500ms）
time.Sleep(500 * time.Millisecond)
// 4. 再次刪除快取
cache.Del("article:42")
```

### 延遲雙刪的本質缺陷
- **休眠時間無法精確評估**：到底該休眠 200ms 還是 1000ms？這完全取決於主從複製延遲與並行讀取線程的耗時，任何固定常數都只是猜測。
- **阻塞應用執行緒**：在同步 HTTP 處理鏈中執行 `sleep` 會白白佔用連線與線程資源；若改為非同步佇列延時刪除，則額外增加了架構複雜度。

## 終極解法：基於 CDC（Binlog）的非同步可靠失效

當系統對一致性要求極高，且希望將業務程式碼與快取同步完全解耦時，現代雲端架構的最佳實踐是採用 **CDC（Change Data Capture，變更資料捕獲）**。

```
                    ┌──────────── 本地交易 ────────────┐
                    ▼                                  ▼
業務應用程式 ──> [ PostgreSQL / MySQL ] ──────────> [ Binlog / WAL ]
                                                       │
                                                (即時捕獲變更)
                                                       ▼
                                            [ CDC 元件 (Debezium / Canal) ]
                                                       │
                                                (可靠推播事件)
                                                       ▼
                                            [ 訊息佇列 (Kafka / RabbitMQ) ]
                                                       │
                                                (保證至少一次消費)
                                                       ▼
                                            [ 快取失效服務 (Cache Invalidator) ]
                                                       │
                                                (執行 DEL 指令)
                                                       ▼
                                            [ 分散式快取 (Redis Cluster) ]
```

### 運作優勢
1. **業務邏輯純粹**：應用程式只需專注於向資料庫執行標準事務寫入，程式碼中完全不需要關心快取刪除邏輯。
2. **保證至少一次失效（At-least-once）**：CDC 監聽底層已提交的交易日誌，即使快取刪除時 Redis 網路抖動，訊息佇列具備重試（Retry）與死信（DLQ）機制，確保快取最終必然被成功刪除。
3. **天然相容讀寫分離**：CDC 可以設定監聽資料庫的唯讀從節點，確保在從庫同步完成後才發起快取失效，徹底消弭主從延遲引發的舊值回填問題。
