# 讀寫模式：Cache-Aside 到 Write-Behind

快取讀寫模式規範了應用程式、快取元件與真實資料庫在資料查詢與更新時的職責劃分與操作時序。
選定合適的存取模式，是平衡讀取延遲、寫入吞吐量與資料一致性的根本起點。

## 四大主流讀寫模式

依據應用程式與快取之間的互動方式，主流的讀寫架構模式可分為四種：

### 1. Cache-Aside（旁路快取 / Lazy Loading）

這是分散式系統中最廣泛採用的模式。應用程式直接與快取和資料庫兩者對話，快取元件本身不感知底層資料庫的存在。

- **讀取流程**：
  1. 應用程式先嘗試從快取讀取資料。
  2. 若快取命中（Cache Hit），直接返回結果。
  3. 若快取未命中（Cache Miss），應用程式向資料庫查詢真實資料。
  4. 應用程式將查得的資料寫入快取，並返回給呼叫端。
- **寫入流程**：
  1. 應用程式將新資料寫入或更新至資料庫。
  2. 應用程式主動使快取中的對應 Key 失效（Delete / Evict），而非直接更新快取。
- **優缺點**：
  - 優點：只有被實際請求的資料才會進入快取，節省記憶體；快取節點當機不會阻斷資料庫的讀寫。
  - 缺點：首次存取必然 Miss；寫入與失效之間存在暫態視窗，需要精確處理競態條件。

### 2. Read-Through（穿透讀取）

在 Read-Through 模式中，應用程式只與快取介面互動。當快取發生 Miss 時，由快取服務內部自帶的資料外掛程式（Data Loader）透明地向底層資料庫拉取資料、回填自身的記憶體，並回傳給應用端。

- **特點**：簡化了應用層程式碼，業務邏輯不再需要寫滿 `if cache.get() == nil`；但快取層與資料庫緊密耦合，需要針對特定資料庫實作連線載入邏輯。

### 3. Write-Through（直寫快取）

在 Write-Through 模式中，應用程式的所有寫入請求一律發給快取層。快取層收到資料後，以同步（Synchronous）方式先更新快取自身，再同步寫入資料庫，確認兩者皆寫入成功後才向應用程式回傳成功確認。

- **優點**：快取與資料庫永遠保持高度一致，讀取永遠最新。
- **缺點**：寫入延遲顯著增加，因為每次寫入都受限於資料庫的磁碟 I/O 速度；且許多寫入的資料可能後續從未被讀取，造成無效的快取佔用。

### 4. Write-Behind / Write-Back（回寫快取 / 非同步寫入）

Write-Behind 同樣將所有寫入發給快取層。但快取在更新自身記憶體後，便立即向應用端回傳成功；接著由快取系統在背景以非同步（Asynchronous）、批次（Batching）的方式合併寫入底層資料庫。

- **優點**：寫入延遲極低（僅記憶體操作），寫入吞吐量極大；可將連續多次的累加合併為一次資料庫更新。
- **缺點**：資料一致性脆弱。若快取節點在資料刷盤（Flush）到資料庫前斷電或發生不可逆崩潰，尚未持久化的資料將永久遺失。

| 模式 | 誰負責載入與同步 | 讀取延遲 | 寫入延遲 | 一致性與遺失風險 |
|---|---|---|---|---|
| **Cache-Aside** | 應用程式親自調度 | Miss 時較慢，Hit 時極快 | 取決於 DB 寫入與快取刪除 | 弱一致，無遺失風險（DB 先行） |
| **Read-Through** | 快取組件內部透明處理 | 同 Cache-Aside | 不適用（僅規範讀） | 弱一致 |
| **Write-Through** | 快取組件同步雙寫 | 極快（大多 Hit） | 慢（受限於 DB 同步寫） | 強一致，無遺失風險 |
| **Write-Behind** | 快取組件非同步批次回寫 | 極快 | 極快（僅記憶體寫入） | 最終一致，存在宕機遺失風險 |

## 貫穿案例：文章服務的模式選型

在文章閱讀系統中，不同業務資料具有截然不同的價值與吞吐需求：

### 案例 A：文章詳情與作者簡介（採用 Cache-Aside）
文章正文（`article:42:content`）的權威資料嚴格隸屬於 PostgreSQL。更新時：
1. 作者提交修改，應用程式執行 SQL `UPDATE articles SET content = $1 WHERE id = 42;`。
2. 交易提交成功後，執行 `DEL article:42:content`。
3. 下一次讀者閱讀時，Miss 並從資料庫載入最新文章回填快取。
這保證了即使快取掛掉，文章編輯功能仍可正常運作，且不會遺失修改。

### 案例 B：文章瀏覽計數器（採用 Write-Behind 思維）
每秒可能湧入 50,000 次讀者點擊閱讀，若每次都直接 `UPDATE articles SET view_count = view_count + 1`，資料庫將不堪負荷。
- 讀者點擊時，應用程式直接在 Redis 執行 `INCR article:42:views`，立即回應前端。
- 背景 Worker 定期（例如每 10 秒）透過定時工作讀取 Redis 的計數，並批次執行 `UPDATE articles SET view_count = view_count + 100 WHERE id = 42;`。
- 取捨：若 Redis 突然斷電，最多遺失過去 10 秒內的瀏覽點擊計數，這在業務上是完全可容忍的代價。

## 常見誤解與限制

- **誤解：更新資料時，應該同步更新快取的值（SET），而不是刪除快取（DEL）。**
  若兩個並行執行緒同時更新同一個物件，由於網路抖動，執行緒 A 先更新 DB、執行緒 B 後更新 DB，但執行緒 B 的快取寫入先到達、執行緒 A 的快取寫入後到達，快取最終將殘留執行緒 A 的舊資料。直接「刪除快取（DEL）」能大幅降低這種順序錯亂導致的永久不一致。
- **誤解：Write-Behind 只要啟用就等於高效能資料庫。**
  Write-Behind 大幅增加了維護複雜度。若資料庫因為故障或網路中斷而無法寫入，快取記憶體中的待刷盤佇列會持續膨脹直至 OOM，且重啟後必須具備日誌重播機制。
