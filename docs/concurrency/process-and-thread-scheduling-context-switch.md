# 行程 (Process) 與執行緒 (Thread)：排程本質與 Context Switch 代價

在多工作業系統中，多個任務看似能同時運行。然而，在實體 CPU 核心數量有限的情況下，作業系統究竟如何區分「行程（Process）」與「執行緒（Thread）」？排程器如何調配 CPU 時間？當 CPU 在不同任務間頻繁切換（Context Switch）時，底層又付出了哪些不可忽視的硬體代價？

## 行程與執行緒的本質區別

作業系統透過抽象化，將電腦硬體資源與運算能力解耦為兩個不同層級的單元：

| 比較維度 | 行程 (Process) | 執行緒 (Thread) |
|---|---|---|
| **核心定義** | 作業系統**分配系統資源**的最小基本單位 | 作業系統**排程與 CPU 執行**的最小基本單位 |
| **記憶體位址空間** | 擁有獨立、隔離的虛擬位址空間與分頁表 | 同一行程內的所有執行緒**共享**同一份虛擬位址空間與堆積（Heap） |
| **私有專屬資源** | PID、分頁表、檔案描述子表（FD Table）、工作目錄、信號處理常式 | 獨立的程式計數器（PC）、通用暫存器狀態、私有呼叫堆疊（Stack） |
| **通訊成本 (IPC)** | 跨行程通訊（IPC）需透過管道（Pipe）、Socket 或共享記憶體，成本高 | 透過行程內共享記憶體指標直接讀寫，速度極快，但伴隨資料競爭風險 |
| **故障隔離** | 一個行程崩潰（Crash）通常不影響其他行程 | 一個執行緒發生 Segmentation Fault 會導致整個行程及所有同儕執行緒集體終止 |

```
行程 A (PID 1001)                               行程 B (PID 1002)
┌──────────────────────────────────────┐        ┌──────────────────────────────────────┐
│ 私有分頁表 (CR3 指向 Page Directory) │        │ 私有分頁表 (獨立記憶體隔離)          │
├──────────────────────────────────────┤        ├──────────────────────────────────────┤
│ 共享區域 (Text, Data, BSS, Heap)     │        │ 共享區域 (Text, Data, BSS, Heap)     │
│ ┌──────────────┐    ┌──────────────┐ │        │                                      │
│ │ 執行緒 1     │    │ 執行緒 2     │ │        │                                      │
│ │ - 私有 Stack │    │ - 私有 Stack │ │        │                                      │
│ │ - 私有 PC/SP │    │ - 私有 PC/SP │ │        │                                      │
│ └──────────────┘    └──────────────┘ │        │                                      │
└──────────────────────────────────────┘        └──────────────────────────────────────┘
```

## Linux 核心實作真相：一切皆是 task_struct

許多開發者誤以為作業系統核心內部一定有完全不同的資料結構來分別代表行程與執行緒。但在 Linux 核心眼中，兩者本質上都是可排程的任務實體，統一以 `task_struct` 結構體表示。

Linux 建立新實體的主要系統呼叫是 `clone(2)`。當呼叫 `fork(2)` 建立新行程時，底層呼叫的是不帶共享旗標的 `clone()`；而呼叫 `pthread_create(3)` 建立執行緒時，底層傳遞了一組共享旗標：

```c
// 建立執行緒時傳遞的關鍵旗標組合
clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD, stack, ...);
```

- `CLONE_VM`：新任務共享父任務的虛擬記憶體位址空間（共用相同分頁表）。
- `CLONE_FILES`：新任務共享父任務的檔案描述子表（一處 `close(fd)`，全體可見）。
- `CLONE_SIGHAND`：新任務共享信號處理函式對應表。
- `CLONE_THREAD`：將新任務歸入同一個行程群組（Thread Group），共享相同的 TGID（即使用者空間看到的 PID）。

這意味著在 Linux 核心調度器的視角中，執行緒只是「與其他任務共享了記憶體與檔案資源的輕量行程（Lightweight Process）」。

## 排程器 (Scheduler) 與時間片分配

現代作業系統採用**搶佔式排程（Preemptive Scheduling）**。CPU 核心不會任由某個執行緒無限期佔用，而是由硬體定時器中斷（Timer Interrupt）週期性觸發核心排程邏輯。

以 Linux 的完全公平排程器（CFS, Completely Fair Scheduler，或 Linux 6.6+ 引入的 EEVDF）為例：
1. **虛擬運行時間 (vruntime)**：核心為每個任務追蹤其已消耗的 CPU 時間，並根據其優先權（`nice` 值）進行加權計算。優先權越高，`vruntime` 增長越慢。
2. **紅黑樹維護**：所有就緒狀態（Runnable）的任務依 `vruntime` 由小到大排序於紅黑樹中。
3. **選擇下一個任務**：當前任務的時間片耗盡或主動讓出 CPU 時，排程器永遠挑選紅黑樹最左側（`vruntime` 最小，即最飢餓）的任務載入 CPU 執行。

## 上下文切換 (Context Switch) 的代價剖析

當排程器決定暫停任務 A 並切換至任務 B 時，CPU 必須執行**上下文切換 (Context Switch)**。這筆開銷分為兩部分：

### 1. 直接開銷 (Direct Overhead)
- **暫存器保存與復原**：將任務 A 的 CPU 通用暫存器、程式計數器（PC/RIP）、棧頂指針（SP/RSP）、旗標暫存器寫入核心記憶體的 `task_struct`，並將任務 B 的暫存器狀態重新填入 CPU。
- **核心態切換**：引發中斷並進入核心模式執行排程邏輯。
- **分頁表切換（僅限跨行程切換）**：若是跨行程切換，CPU 必須重新載入分頁目錄基底暫存器（x86 的 `CR3`），指向新行程的分頁表。同一行程內的執行緒切換則**不需要**切換 CR3。

### 2. 間接開銷 (Indirect Overhead，真正的效能殺手)
- **TLB (Translation Lookaside Buffer) 快取沖刷**：CR3 暫存器一旦切換，CPU 快取的虛擬位址到實體位址的轉換條目（TLB）全數失效（除非啟用 PCID 特性）。新行程在執行之初，每一次記憶體存取都必須進行昂貴的多層分頁表查表（Page Walk），帶來極大的記憶體延遲。
- **CPU L1/L2 快取行污染 (Cache Pollution)**：任務 B 載入執行後，會將自己的資料寫入 CPU L1/L2 快取，將任務 A 原本熱騰騰的快取資料逐出。當任務 A 稍後被重新切換回來時，面臨嚴重的 Cache Miss，必須重新從慢速的 L3 或 RAM 讀取資料。

一次典型的同行程執行緒切換開銷約在數百奈秒（約 1–2 微秒以內）；而跨行程切換加上快取完全冷卻的代價，往往高達數微秒至數十微秒，耗損數萬個 CPU 週期。

## 常見誤解與架構限制

1. **誤解：執行緒開得越多，高併發吞吐量就越高**
   若伺服器只有 8 個 CPU 核心，但應用程式開啟了 5,000 個原生執行緒，CPU 核心將把 80% 以上的時間浪費在儲存暫存器、排程決策與沖刷快取（Context Switch Thrashing）上，實際用於處理業務邏輯的有效計算時間反而雪崩式下滑。
2. **誤解：執行緒是「完全免費」的並行工具**
   每個 OS 原生執行緒預設佔用 1MB 至 8MB 的私有 Stack 虛擬空間，即使不工作也耗費記憶體。當連線數達到萬級（C10K 問題）時，純靠為每個連線分配一個 OS 執行緒的架構（Thread-per-request）會直接觸發 OOM。這促使了下一代輕量執行模型（協程與非同步 I/O）的誕生。
