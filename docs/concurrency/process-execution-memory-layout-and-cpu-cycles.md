# 程式執行本質：從原始碼、記憶體配置到 CPU 指令週期

高階程式語言寫下的程式碼，在電腦底層究竟如何被轉換並交由硬體執行？理解程式的執行時期（Runtime）行為，必須從二進位執行檔的載入、作業系統為行程劃分的虛擬位址空間佈局，以及 CPU 核心的指令執行週期談起。

## 從原始碼到可執行二進位檔

當我們以 C/C++、Rust 或 Go 撰寫程式碼並執行編譯時，建置管線通常經歷四個階段：

1. **前處理 (Preprocessing)**：展開巨集、解析標頭檔與條件編譯指令。
2. **編譯 (Compilation)**：將原始碼進行語法分析、語意檢查與中介碼（IR）最佳化，轉換為組合語言（Assembly）。
3. **組譯 (Assembly)**：將組合語言轉換為目標機器碼，產生目標檔（Object File，如 `.o`）。
4. **連結 (Linking)**：由連結器（Linker）將多個目標檔與靜態／動態函式庫合併，解析符號參照（Symbol Resolution）並指派記憶體重定位（Relocation），最終產生符合格式的可執行檔（如 Linux 下的 ELF 格式或 macOS 下的 Mach-O）。

```
原始碼 (.c / .rs) ──▶ 編譯器 ──▶ 組合語言 (.s) ──▶ 組譯器 ──▶ 目標檔 (.o) ──▶ 連結器 ──▶ ELF 執行檔
```

當在 Shell 中啟動該二進位檔時，作業系統的核心載入器（Loader）會解析 ELF 標頭，透過系統呼叫建立全新的行程，並為其分配獨立的虛擬記憶體空間。

## 行程虛擬位址空間佈局 (Virtual Address Space)

現代作業系統利用 CPU 的記憶體管理單元（MMU）與分頁機制（Paging），為每個行程提供一個連續且私有的**虛擬位址空間**。在典型的 64 位元 Linux 系統中，使用者空間的標準分佈如下圖所示：

```
高位址  0x7FFFFFFFFFFF ┌──────────────────────────────────────────────┐
                       │ 核心空間 (Kernel Space, 僅限系統呼叫存取)     │
       0x7FFFFFFF0000 ├──────────────────────────────────────────────┤
                       │ 呼叫堆疊 (Stack, 向低位址增長 ⬇)             │
                       │ (區域變數、函式棧幀、返回位址)                │
                       ├──────────────────────────────────────────────┤
                       │ ⬇                                            │
                       │                                              │
                       │ ⬆ 記憶體映射區 (Memory Mapping / Shared Lib) │
                       │ (由 mmap 分配，動態連結庫如 libc.so)         │
                       ├──────────────────────────────────────────────┤
                       │ ⬆ 堆積 (Heap, 向高位址增長)                  │
                       │ (malloc / new 動態分配，由 brk/mmap 擴展)    │
                       ├──────────────────────────────────────────────┤
                       │ BSS 段 (未初始化的全域與靜態變數，系統清零)   │
                       ├──────────────────────────────────────────────┤
                       │ 資料段 (Data Segment, 已初始化的全域/靜態變數)│
                       ├──────────────────────────────────────────────┤
低位址  0x000000400000 │ 程式碼段 (Text/Code, 機器指令，唯讀且可執行)  │
                       └──────────────────────────────────────────────┘
```

各區段的職責與特徵：

| 記憶體區段 | 內容與用途 | 讀寫權限 | 增長方向與生命週期 |
|---|---|---|---|
| **程式碼段 (Text / Code)** | 二進位機器指令碼（Machine Code） | 唯讀、可執行（R-X） | 固定大小；行程存活期間永久存在 |
| **資料段 (Data Segment)** | 原始碼中明確給定初值的全域變數與 `static` 變數 | 可讀、可寫（RW-） | 固定大小；編譯時已確定空間佔用 |
| **BSS 段** | 未給定初值或初始為 0 的全域變數與靜態變數 | 可讀、可寫（RW-） | 執行檔中不佔實際空間，載入時由核心清零 |
| **堆積 (Heap)** | 執行時期動態申請的記憶體（如 `malloc`、`new`） | 可讀、可寫（RW-） | 由低向高增長；由工程師手動或 GC 釋放 |
| **記憶體映射區 (mmap)** | 動態連結共享函式庫（如 `libc.so`）與大塊記憶體分配 | 可讀、可寫、可執行 | 由高向低增長或由核心動態尋找空隙 |
| **呼叫堆疊 (Stack)** | 函式呼叫時的棧幀（區域變數、參數傳遞、返回位址） | 可讀、可寫（RW-） | 由高向低增長；隨函式退出自動出棧釋放 |

## 呼叫堆疊 (Stack) 與棧幀 (Stack Frame)

當一個函式被呼叫時，CPU 會在 Stack 頂部為該函式開闢一塊記憶體區域，稱為**棧幀 (Stack Frame)**：

1. **返回位址 (Return Address)**：呼叫指令（如 x86 `call`）會將下一條指令的記憶體位址壓入堆疊。函式執行完畢遇到 `ret` 指令時，CPU 從堆疊彈出該位址，跳轉回原呼叫處繼續執行。
2. **基底指針 (Frame Pointer, RBP)**：指向當前棧幀的基底位址，用於藉由固定偏移量快速定位參數與區域變數。
3. **棧頂指針 (Stack Pointer, RSP)**：永遠指向當前 Stack 的最頂端（即最低位址處）。
4. **區域變數空間**：編譯器在函式進入序言（Prologue）中透過遞減 RSP 來為局部變數預留空間。

```
                ┌──────────────────────────────────┐
                │ 函式呼叫參數 (引數超出暫存器上限) │
                ├──────────────────────────────────┤
                │ 返回位址 (Return Instruction IP) │
  RBP 指向 ───▶ ├──────────────────────────────────┤
                │ 呼叫者的舊 RBP (Saved Frame Ptr) │
                ├──────────────────────────────────┤
                │ 被呼叫者需保存的暫存器 (RBX, etc)│
                ├──────────────────────────────────┤
                │ 區域變數 (Local Variables)       │
  RSP 指向 ───▶ └──────────────────────────────────┘
```

**棧溢位 (Stack Overflow) 的本質**：作業系統對每個行程（或執行緒）的 Stack 大小設有硬性上限（Linux 預設多為 8MB，可透過 `ulimit -s` 檢視）。若程式發生無限遞迴，或在函式內配置了過大的區域變數陣列，RSP 不斷向下扣減突破了核心分配的分頁保護區（Guard Page），MMU 便會觸發 Page Fault，核心隨即對該行程發送 `SIGSEGV`（Segmentation Fault）信號強制終止。

## CPU 指令週期 (Instruction Cycle)

載入至 Text 段的二進位機器指令，由 CPU 核心依序或亂序讀取並執行。一個最基礎的指令週期包含三個核心步驟：

```
       ┌───────────┐
  ┌───▶│   Fetch   │ (擷取：自記憶體/L1指令快取讀取 PC 指向的指令)
  │    └─────┬─────┘
  │          ▼
  │    ┌───────────┐
  │    │  Decode   │ (解碼：控制單元解析運算碼 Opcode 與運算元)
  │    └─────┬─────┘
  │          ▼
  │    ┌───────────┐
  │    │  Execute  │ (執行：算術邏輯單元 ALU 計算、暫存器存取或寫回)
  └─── └───────────┘
```

- **PC 暫存器 (Program Counter / RIP)**：儲存 CPU 即將擷取的下一條指令所在的記憶體虛擬位址。每擷取一條指令，PC 自動遞增該指令長度，或在遇到分支／跳轉（Jump/Call）指令時被重寫。
- **管線化 (Pipelining)**：現代 CPU 為了提高吞吐量，將上述步驟切分為十幾個細微階段（如 IF, ID, EX, MEM, WB）。當前一條指令在執行時，後一條指令正在解碼，再後一條正在擷取，大幅提升時脈利用率。

## 常見誤解與實際限制

1. **誤解：宣告一塊變數或呼叫 `malloc(1GB)` 就會立即耗用 1GB 實體 RAM**
   作業系統採用**惰性分頁（Demand Paging）**。呼叫 `malloc` 只是在行程的虛擬位址空間劃定合法範圍；只有當 CPU 首次對該位址進行讀寫操作時，MMU 發現分頁表項不存在，觸發硬體缺頁異常（Page Fault），核心才會真正分配實體記憶體分頁（Page Frame）並建立映射。
2. **誤解：堆積（Heap）與堆疊（Stack）的存取速度差在硬體材質**
   Heap 與 Stack 的實體資料都存放在同一條 RAM 晶片與相同的 CPU 快取階層中。Stack 之所以比 Heap 快，是因為：(1) Stack 配置與釋放僅需一條指令遞增／遞減 RSP 指針，而 Heap 分配器（如 ptmalloc, jemalloc）必須搜尋記憶體可用空隙並處理碎片；(2) Stack 的記憶體存取具備極高的高時空局部性（Locality），資料高機率早已被命中在 CPU L1/L2 快取中。
