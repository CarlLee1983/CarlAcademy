# I/O 多工模型演進：從阻塞 I/O、epoll/kqueue 到 io_uring

在網際網路服務早期，伺服器大多採用「一個連線分配一個執行緒」（Thread-per-connection）的阻塞 I/O 模型。然而，當連線規模從千級躍升至萬級甚至百萬級（C10K 至 C1000K 問題）時，作業系統因執行緒數量暴增、記憶體堆疊耗盡與排程開銷而癱瘓。

為了解決這個根本矛盾，作業系統的 I/O 模型經歷了三十餘年的深刻演進：從傳統的阻塞 I/O、`select`/`poll` 輪詢，到基於事件驅動的現代標竿 **`epoll` / `kqueue`**，再到 Linux 次世代的真非同步原生框架 **`io_uring`**。

## 阻塞 I/O (BIO) 與非阻塞 I/O (NIO) 的瓶頸

在理解多工模型之前，需先釐清網路 Socket 的基本讀取行為。一次標準的網路資料讀取分為兩個階段：
1. **階段一：等待資料抵達 (Waiting for data)**：網卡接收封包，經過 TCP 協定棧處理，搬移至核心 Socket 接收緩衝區。
2. **階段二：拷貝資料至使用者空間 (Copying data)**：CPU 將資料由核心緩衝區拷貝到應用程式的使用者記憶體緩衝區。

```
階段一：等待資料就緒              階段二：拷貝資料
[ 網路封包 ──▶ 核心接收緩衝區 ] ──▶ [ 核心緩衝區 ──▶ 使用者記憶體 (應用程式) ]
```

- **阻塞 I/O (BIO, Blocking I/O)**：
  應用程式發起 `read()` 系統呼叫後，若核心緩衝區尚無資料，當前執行緒被作業系統強制掛起休眠，直到兩個階段全數完成才返回。若有 10,000 個連線大部分處於待命（Keep-Alive）狀態，就必須有 10,000 個執行緒處於休眠，浪費大量記憶體與排程資源。
- **非阻塞 I/O (NIO, Non-blocking I/O)**：
  透過 `fcntl` 將 Socket 設定為 `O_NONBLOCK`。當呼叫 `read()` 且無資料時，系統呼叫**不休眠，立即返回錯誤碼 `EWOULDBLOCK` 或 `EAGAIN`**。
  - **致命缺陷**：若僅靠應用程式自行以迴圈輪詢所有 Socket，CPU 會因為不斷發起無意義的系統呼叫而飆升至 100% 滿載，徒勞無功。

## 第一代 I/O 多工：select(2) 與 poll(2)

為了解決忙碌輪詢的浪費，核心提供了 **I/O 多工（I/O Multiplexing）**：由單一執行緒同時監聽成千上萬個 Socket 的狀態變化。

- **`select(2)` 機制**：
  應用程式將多個檔案描述子（FD）組裝成一個位元陣列（`fd_set`），傳入核心。核心將該執行緒休眠，並在內部輪詢檢查這批 FD；一旦有任何一個 FD 有資料可讀，核心喚醒執行緒。
- **`poll(2)` 改進**：
  以結構體陣列（`struct pollfd`）取代了 `fd_set`，打破了 `select` 預設最多只能監聽 1024 個檔案描述子的硬性上限（`FD_SETSIZE`）。

### select / poll 的效能致命傷：$O(N)$ 輪詢
1. **每次呼叫重複記憶體拷貝**：每次呼叫 `select` 或 `poll`，都必須將全部幾千個 FD 從使用者空間完整拷貝進核心空間，返回時又必須再次拷貝出來。
2. **核心內部線性掃描**：核心內部必須以 $O(N)$ 複雜度遍歷每一個 FD，逐一檢查是否有封包抵達。
3. **使用者空間二度掃描**：當 `select` 返回時，它只告訴應用程式「這批 FD 中有 $M$ 個就緒了」，**但沒有指明具體是哪幾個**！應用程式必須在使用者空間再次以 $O(N)$ 迴圈遍歷所有人，找出是誰就緒。

當監聽 50,000 個連線但同一時刻只有 10 個連線有資料時，`select` 與 `poll` 依然在不斷進行 50,000 次無謂檢查，效能隨著連線數線性崩跌。

## 現代高併發基石：Linux epoll(7) 架構

Linux 2.6 正式引入 **`epoll`**（FreeBSD/macOS 則對應 **`kqueue`**），以事件驅動徹底顛覆了輪詢模型，將複雜度降至 **$O(1)$**。

```
使用者空間 (User Space)                           Linux 核心空間 (Kernel Space)
┌──────────────────────────────────────┐        ┌──────────────────────────────────────┐
│ 1. epoll_create: 建立實例            │ ────▶  │ 建立 eventpoll 核心物件              │
├──────────────────────────────────────┤        ├──────────────────────────────────────┤
│ 2. epoll_ctl (EPOLL_CTL_ADD):        │ ────▶  │ 紅黑樹 (Red-Black Tree):             │
│    註冊感興趣的 FD 與事件 (僅拷貝一次)│        │ 存放所有被監聽的 Socket (O(log N))   │
│                                      │        ├──────────────────────────────────────┤
│                                      │        │ 就緒雙向鏈結串列 (Ready List):       │
├──────────────────────────────────────┤        │ 僅存放真正有資料抵達的 Socket        │
│ 3. epoll_wait: 等待就緒事件          │ ◀────  │                                      │
│    (直接拿到就緒清單，零無謂輪詢!)   │        │ 網卡中斷 ──▶ ep_poll_callback 回呼   │
└──────────────────────────────────────┘        └──────────────────────────────────────┘
```

`epoll` 的三大神級設計：

### 1. 紅黑樹維護監聽清單（避免重複拷貝）
透過 `epoll_ctl` 註冊 FD，核心在內部以**紅黑樹 (Red-Black Tree)** 長期保存監聽清單。FD 只需註冊一次，後續呼叫 `epoll_wait` **完全不需要重複將幾萬個 FD 傳入核心**。

### 2. 硬體中斷與回呼驅動（消除 $O(N)$ 輪詢）
當網卡接收到網路封包時，觸發 CPU 硬體中斷。核心在處理封包並寫入 Socket 接收緩衝區後，會**自動觸發註冊的回呼函式（`ep_poll_callback`）**。該回呼函式直接將該 Socket 掛入核心的**就緒雙向鏈結串列（Ready List）**中。

### 3. epoll_wait 只返回就緒事件（$O(1)$ 精準打擊）
當執行緒呼叫 `epoll_wait` 甦醒時，核心**只拷貝並返回 Ready List 中的就緒項目**。若 50,000 個連線中只有 10 個有資料，`epoll_wait` 就只精確返回 10 個事件，應用程式直接處理，無任何無謂輪詢。

Nginx、Node.js（libuv）、Redis、Netty 等百萬並發引擎，底層全部架構在 `epoll` 的 **Reactor 事件驅動模式** 之上。

## 邊緣觸發 (ET) vs 水平觸發 (LT)

`epoll` 支援兩種事件通知模式：

| 模式 | 運作行為 | 優缺點與防護規範 |
|---|---|---|
| **水平觸發 (Level-Triggered, LT)** (預設) | 只要 Socket 緩衝區內**還有資料未讀完**，每次呼叫 `epoll_wait` 都會重複通知該事件。 | **容錯性高**；程式碼直觀不易漏封包。但頻繁重複觸發會增加少量系統呼叫開銷。 |
| **邊緣觸發 (Edge-Triggered, ET)** | 只有當 Socket 狀態**從「無資料」跳變為「有資料」的邊沿瞬間**，通知唯一的一次！ | **極致效能**，避免重複通知。但**風險極高**：若一次沒有把緩衝區資料讀乾淨，剩餘資料將永久滯留！ |

> **邊緣觸發 (ET) 鐵律**：
> 1. Socket 必須設定為非阻塞模式（`O_NONBLOCK`）。
> 2. 收到讀取事件時，**必須以 `while` 迴圈不斷讀取，直到 `read()` 返回 `EAGAIN` 或 `EWOULDBLOCK`**，確保緩衝區徹底排空！

## 次世代真非同步原生：Linux io_uring (2019)

雖然 `epoll` 極其高效，但它本質上依然是**同步 I/O 多工**：`epoll` 負責通知「資料就緒了」，但最後把資料從核心拷貝到使用者記憶體的 `read(fd, buf)`，依然是同步阻塞當前執行緒的系統呼叫。

Linux 5.1 由 Jens Axboe 推出的 **`io_uring`**，被譽為 Linux 近十年來最激進的系統架構革新，實現了真正的**非同步原生 I/O**：

```
使用者空間 (User Space)                        Linux 核心空間 (Kernel Space)
┌──────────────────────────────────────┐      ┌──────────────────────────────────────┐
│ 提交佇列 (Submission Queue, SQ)     │ ──▶  │ 核心直接消費 SQ 中的 I/O 請求        │
│ ┌──────────────────────────────────┐ │ (mmap│ (支援核心 Polling 執行緒 SQPOLL，    │
│ │ 描述: 讀取 fd=5 到 buffer 位址   │ │ 共享│  應用程式與核心皆「零系統呼叫」!)   │
│ └──────────────────────────────────┘ │ 記憶 │                                      │
├──────────────────────────────────────┤ 體)  ├──────────────────────────────────────┤
│ 完成佇列 (Completion Queue, CQ)     │ ◀──  │ 核心處理完畢，直接將結果推入 CQ      │
│ ┌──────────────────────────────────┐ │      │                                      │
│ │ 結果: fd=5 已讀入 4096 位元組    │ │      │                                      │
│ └──────────────────────────────────┘ │      │                                      │
└──────────────────────────────────────┘      └──────────────────────────────────────┘
```

`io_uring` 的三大突破：
1. **雙環狀緩衝共享記憶體 (Zero Syscall)**：使用者空間與核心透過 `mmap` 共享一對無鎖環狀佇列（SQ 與 CQ）。應用程式向 SQ 填入 I/O 請求，直接轉身去做其他事；核心完成 I/O 後將結果填入 CQ。在啟用 `IORING_SETUP_SQPOLL` 模式下，**全程零系統呼叫**。
2. **真正的全能非同步**：`epoll` 只能高效監聽網路 Socket，對一般磁碟檔案 I/O（Disk I/O）無法實現真正的非阻塞（因為磁碟檔案永遠處於「就緒」狀態，`read` 依舊會卡在 Page Cache 磁碟讀取上）。`io_uring` 統一了網路與磁碟 I/O，全路徑完全非同步。
3. **暫存緩衝區與零拷貝 (Fixed Buffers / Zero-copy)**：預先向核心註冊固定記憶體頁，網路封包直接從網卡 DMA 寫入該頁，徹底消除核心到使用者空間的記憶體複製。
