# 讀寫鎖 (RWLock)、條件變數與執行緒通訊協作

互斥鎖（Mutex）雖然能安全防禦競態條件，但其「任何時刻僅允許一人存取」的一刀切策略，在許多真實業務情境下顯得過於笨重。在文章內容快取、設定讀取等「讀多寫少」的高頻查詢場景中，多個讀取操作彼此並無衝突；此外，當執行緒需要等待特定條件（如任務佇列非空）成立時，忙碌輪詢只會白白燃燒 CPU。

本篇將深入拆解**讀寫鎖 (RWLock)** 的共享與互斥語意，剖析寫者飢餓的權衡，並解析**條件變數 (Condition Variable)** 與互斥鎖配合協作的底層契約及**虛假喚醒 (Spurious Wakeup)** 的防護法則。

## 讀寫鎖 (Read-Write Lock) 的設計語意

在許多後端系統中，資料的存取模式呈現極端的非對稱性：99% 的請求是讀取操作，僅有 1% 是變更寫入。若使用標準 Mutex，所有讀取請求都必須串列排隊，系統的多核心平行運算優勢被徹底抹煞。

讀寫鎖（如 POSIX `pthread_rwlock_t`、C++ `std::shared_mutex`、Java `ReentrantReadWriteLock`）將鎖的語意細分為兩組：

- **共享讀鎖 (Shared Read Lock)**：允許**多個讀者執行緒同時獲取**並平行存取資料。只要沒有人持有寫鎖，任何讀取者都可以直接拿到讀鎖。
- **獨佔寫鎖 (Exclusive Write Lock)**：**完全排他**。當寫者持有寫鎖時，禁止任何其他讀者或寫者進入；反之，若有任何讀者正在讀取，寫者必須阻塞等待。

```
當前鎖狀態           新到讀取請求 (Read)          新到寫入請求 (Write)
─────────────────────────────────────────────────────────────────────────────
空閒 (Unlocked)     ✅ 立即獲取讀鎖 (變為 ReadLocked) ✅ 立即獲取寫鎖 (變為 WriteLocked)
已獲取讀鎖 (ReadLocked) ✅ 累加讀者計數，平行讀取  ⏳ 阻塞等待所有讀者退鎖
已獲取寫鎖 (WriteLocked) ⏳ 阻塞等待寫者釋放      ⏳ 阻塞等待寫者釋放
```

## 偏向策略與寫者飢餓 (Writer Starvation)

讀寫鎖看似完美，但在極高並發環境下存在嚴重的策略難題：**當讀者連綿不絕時，寫者該怎麼辦？**

### 1. 讀者優先 (Reader-Preference)
- **規則**：只要當前有讀者持有讀鎖，後續新抵達的讀取請求都可以直接進入。
- **後果**：在高流量讀取情境下，讀者計數器可能永遠大於 0。寫入請求將長時間被迫掛起，產生嚴重的**寫者飢餓 (Writer Starvation)**，甚至導致資料過期無法更新。

### 2. 寫者優先 (Writer-Preference)
- **規則**：一旦有寫入請求正在排隊等待，**立刻阻斷後續新讀者的進入**。新抵達的讀者必須跟在寫者後面排隊，直到寫者完成寫入並釋放鎖。
- **代價**：保護了資料的及時更新與寫入吞吐，但在寫入頻繁時會顯著降低讀取端的整體並行度。

> **架構警語：讀寫鎖不一定是效能銀彈！**
> 讀寫鎖內部必須維護原子性的「讀者計數器」與等待佇列。每次讀者加鎖解鎖，都必須透過原子 CAS 操作修改該計數器。在多核心高頻率並發下，這會引發嚴重的 CPU Cache Line 顛簸（快取行偽共享）。**在讀取延遲極短（例如僅讀取單一記憶體變數）的情境中，RWLock 的吞吐量甚至可能比簡單的 Spinlock 或 Mutex 還慢。** 只有當臨界區讀取時間較長時，RWLock 的並行優勢才能體現。

## 條件變數 (Condition Variable) 與協同通訊

在生產者-消費者模型中，消費者執行緒從佇列取任務時，若佇列為空，消費者應該怎麼做？
若寫成迴圈輪詢：
```c
// 錯誤示範：忙碌輪詢，榨乾 CPU
while (queue.isEmpty()) {
    // 毫無意義地燃燒 CPU 週期
}
```
若加上 `sleep(10ms)`，則會帶來高達數毫秒的無謂延遲。

**條件變數 (Condition Variable)** 提供了一種**事件驅動的掛起與喚醒機制**：讓執行緒在特定條件不滿足時主動休眠讓出 CPU，當其他執行緒使條件成立時，再精準喚醒它。

### 條件變數與 Mutex 的不可分契約
條件變數**絕不能單獨使用，必須始終與一個互斥鎖緊密綁定**。

```
消費者 (等待資料)                               生產者 (產生資料)
┌──────────────────────────────────────┐        ┌──────────────────────────────────────┐
│ 1. pthread_mutex_lock(&mutex);       │        │                                      │
│ 2. while (queue.empty()) {           │        │                                      │
│      pthread_cond_wait(&cond, &mutex)│        │                                      │
│      // 內部自動做三件事：          │        │                                      │
│      // a. 原子性釋放 mutex!         │        │ 1. pthread_mutex_lock(&mutex);       │
│      // b. 執行緒掛起並進入等待佇列   │        │ 2. queue.push(item);                 │
│      // c. 被喚醒後重新搶回 mutex    │ ◀───── │ 3. pthread_cond_signal(&cond); // 喚醒│
│    }                                 │        │ 4. pthread_mutex_unlock(&mutex);     │
│ 3. item = queue.pop();               │        └──────────────────────────────────────┘
│ 4. pthread_mutex_unlock(&mutex);     │
└──────────────────────────────────────┘
```

`pthread_cond_wait` 函式在內部原子性地完成「釋放鎖」與「休眠排隊」，消除了「釋放鎖後但尚未休眠前，生產者剛好發送信號」的競態時序窗口（Lost Wakeup 漏洞）。

## 虛假喚醒 (Spurious Wakeup) 的防禦鐵律

在條件變數的使用中，有一個至關重要的跨平台程式設計規範：

> **防守鐵律：檢查等待條件時，永遠使用 `while` 迴圈，絕不可使用 `if` 判斷！**

### 為什麼會發生虛假喚醒？
1. **多消費者競爭**：生產者只放入了一個元素並呼叫 `signal()` 喚醒一個等待者，但同時有另一個剛剛抵達的消費者未經休眠直接搶走了 Mutex 與該元素。當被喚醒的執行緒重新拿到 Mutex 時，佇列早已再次變空。
2. **廣播喚醒 (Broadcast)**：生產者使用 `pthread_cond_broadcast()` 喚醒了全體 10 個等待執行緒，但佇列中只有 1 個任務，其餘 9 個被喚醒的執行緒面臨空佇列。
3. **作業系統核心信號中斷**：在 Linux 與 POSIX 核心實作中，即使沒有任何執行緒發送信號，處於核心等待狀態的執行緒也可能因為收到 Linux 信號（如 `SIGCHLD` 或除錯中斷）而自發性喚醒。

若使用 `if (queue.empty()) wait()`，當執行緒從 `wait()` 返回時不會再次檢查條件，直接執行 `queue.pop()`，立刻引發記憶體指標錯誤或程式崩潰。**以 `while` 迴圈包覆，確保執行緒在任何情況下甦醒後，都必須重新檢驗條件是否真正成立**。

## 信號量 (Semaphore)：計數型資源管控

與條件變數類似但具備內建計數器的同步工具是**信號量 (Semaphore)**，由計算機科學家 Edsger Dijkstra 提出：

- **P 操作 (`wait` / `acquire`)**：若信號量計數值 $> 0$，則將計數遞減 1 並立即返回；若計數值 $= 0$，則將執行緒掛起等待。
- **V 操作 (`post` / `release`)**：將信號量計數遞增 1；若有執行緒正在等待，喚醒其中一個。

信號量常被用於**並行容量限制（Rate Limiting / Resource Pool）**，例如限制資料庫連線池最多只允許 20 個執行緒同時佔用連線。

## 常見誤解與架構限制

1. **誤解：讀寫鎖可以自動防止讀到過期資料（Stale Read）**
   讀寫鎖只保證在讀取的「瞬間」，沒有寫者在修改資料。一旦讀者釋放讀鎖，寫者立刻就能更新資料。若業務需要跨多個步驟維持資料長週期一致，需要更高層級的事務機制或版本控制（如 MVCC），而非單靠讀寫鎖。
2. **誤解：信號量等於可重入的互斥鎖**
   二元信號量（計數最大為 1）看似能實現互斥，但它**沒有所有權概念（No Ownership）**。執行緒 A 獲取的信號量，執行緒 B 可以直接呼叫 `post()` 將其釋放。這使得信號量適合做跨執行緒的通知與同步，但若用於臨界區互斥，極易引發所有權錯亂。
