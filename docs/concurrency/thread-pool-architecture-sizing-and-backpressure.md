# 執行緒池 (Thread Pool) 架構與背壓防護：極限負載實務案例

在多工系統中，硬體運算資源是有限的。如果不加節制地為每一個抵達的請求動態建立作業系統原生執行緒，系統會迅速因記憶體堆疊（Stack）耗盡引發 OOM，或因數千個執行緒激烈競爭 CPU 引發上下文切換風暴（Context Switch Thrashing）。

**執行緒池 (Thread Pool)** 不僅是為了複用執行緒以省去建立與銷毀的微觀開銷，更本質的職責是作為系統的**資源配額管理器與背壓防禦屏障 (Backpressure Barrier)**。

## 執行緒池核心架構與任務推進生命週期

一個標準的工業級執行緒池（以經典模型 `ThreadPoolExecutor` 為代表），由六大核心要素構成：

```
                   客戶端提交新任務 (Submit Task)
                               │
                               ▼
            ┌─────────────────────────────────────┐
            │ 當前執行緒數 < Core Pool Size (核心數)? │
            └──────────────────┬──────────────────┘
                            是 │      │ 否
                               ▼      ▼
                  【 建立新核心執行緒執行 】  ┌───────────────────────────────┐
                                          │ 工作阻塞佇列 (Work Queue) 是否有空位? │
                                          └──────────────┬────────────────┘
                                                      是 │      │ 否 (佇列已滿!)
                                                         ▼      ▼
                                                 【 推入佇列排隊 】 ┌───────────────────────────┐
                                                                    │ 當前執行緒數 < Max Pool Size? │
                                                                    └─────────────┬─────────────┘
                                                                               是 │      │ 否 (已達極限!)
                                                                                  ▼      ▼
                                                                        【 建立非核心執行緒 】 【 觸發飽和拒絕策略! 】
```

### 任務生命週期的四個防禦梯隊：

1. **第一梯隊：常駐核心執行緒 (Core Pool)**
   當新任務抵達且當前運行中的執行緒數小於 `corePoolSize` 時，執行緒池會直接建立一個新的核心執行緒立即處理任務，即使其他核心執行緒處於空閒狀態。核心執行緒預設會永久常駐，等待新工作。
2. **第二梯隊：緩衝工作佇列 (Work Queue)**
   當核心執行緒已全數被佔滿時，新任務不會立即觸發新執行緒建立，而是被**推入有界阻塞佇列（Bounded Blocking Queue）排隊緩衝**，由核心執行緒在處理完手頭任務後依序取出執行。
3. **第三梯隊：突發彈性執行緒 (Non-core Threads)**
   若外部流量持續攀升，導致工作佇列也被徹底塞滿，執行緒池才會緊急啟動**非核心執行緒**（總執行緒數擴展至 `maxPoolSize`）來加速消化突發洪峰。當流量回落、佇列排空後，非核心執行緒在閒置超過 `keepAliveTime` 後會被核心自動銷毀回收。
4. **第四梯隊：飽和拒絕策略 (Rejected Execution Handler)**
   當總執行緒數已達到 `maxPoolSize` 且工作佇列依然處於全滿狀態，說明系統的處理能力已達到硬體物理極限。執行緒池立即啟動防禦機制，依據預設策略處置無法承載的溢出任務。

## 核心執行緒數該設多少？Brian Goetz 容量公式

執行緒池容量的設定絕非盲目猜測，必須根據任務的物理特徵（CPU 密集型 vs I/O 密集型）進行數學推導。

### 1. CPU 密集型任務 (Compute-Bound)
任務主要消耗 CPU 算力進行密集的運算（如加解密、排序演算法、影片編碼、大數據序列化），幾乎不發生 I/O 阻塞：
$$N_{\text{threads}} = N_{\text{cpu}} + 1$$
- **為什麼加 1？**
  在實務中，即使是純計算任務，偶爾也可能遭遇硬體缺頁中斷（Page Fault）或其他微小核心停頓。額外配置一個備用執行緒，能確保當其中一個執行緒短暫暫停時，CPU 核心依然能被其他計算任務 100% 填滿，不浪費時脈。

### 2. I/O 密集型任務 (I/O-Bound)
任務大部分時間都在等待外部回應（如資料庫 SQL 查詢、微服務 RPC 調用、磁碟讀寫），執行緒在發起請求後會進入核心掛起狀態：

Java 並行計算先鋒 Brian Goetz 在《Java Concurrency in Practice》中給出了經典的理論公式：
$$N_{\text{threads}} = N_{\text{cpu}} \times U_{\text{cpu}} \times \left(1 + \frac{W}{C}\right)$$

- $N_{\text{cpu}}$：伺服器可用的實體 CPU 核心數。
- $U_{\text{cpu}}$：目標 CPU 利用率（$0 \le U_{\text{cpu}} \le 1$，若希望 CPU 滿載可設為 1）。
- $W$：任務的**等待時間 (Wait Time)**，即阻塞在網路或磁碟 I/O 的時間。
- $C$：任務的**實際計算時間 (Compute Time)**，即真正消耗 CPU 進行資料反序列化或邏輯處理的時間。

> **實例試算**：
> 假設一台 8 核心的 API 伺服器，單個請求的平均總耗時為 100 毫秒。其中 90 毫秒都在等待資料庫網路回應（$W = 90$ms），只有 10 毫秒在消耗 CPU 進行 JSON 序列化（$C = 10$ms），則 $W/C = 9$。
> 最佳執行緒數為：
> $$N = 8 \times 1 \times (1 + 9) = 80$$
> 配置 80 個執行緒能夠完美填補 I/O 等待的空白，既不引發 CPU 閒置，也不會過度排程崩潰。

## 背壓防護 (Backpressure) 與四大飽和拒絕策略

當伺服器遭遇極限負載時，如何優雅地保護自己不被打垮？這取決於執行緒池的拒絕策略（Rejection Policy）：

| 策略名稱 | 處置行為 | 架構意圖與代價 |
|---|---|---|
| **AbortPolicy** (預設) | 直接丟出異常（如 `RejectedExecutionException`） | **快速失敗 (Fail-Fast)**。通知上游調用者當前系統已飽和，由上游決定降級或重試。 |
| **CallerRunsPolicy** | **由提交任務的主執行緒親自執行該任務！** | **最優雅的自動背壓機制！** 提交任務的主執行緒（如接收網路請求的 I/O 執行緒）被迫親自去執行業務邏輯，這會導致主執行緒暫時無法讀取新的網路請求，從而在 TCP 滑動視窗層面**自然迫使客戶端減速**，形成向上的反壓。 |
| **DiscardPolicy** | 靜默丟棄當前新任務，不丟出任何錯誤 | 極端危險！除非該任務純粹是無關痛癢的統計採樣，否則會造成資料無聲無息遺失。 |
| **DiscardOldestPolicy** | 丟棄佇列中排隊最久（最靠前）的老任務，騰出空間給新任務 | 適用於即時性高但歷史資料過期無價值的場景（如即時股價行情推送）。 |

## 生產環境的兩大致命陷阱

### 1. 無界佇列 (Unbounded Queue) 引發的 OOM 崩潰
若在建立執行緒池時使用了沒有長度上限的佇列（如無參數的 `LinkedBlockingQueue`），這意味著**工作佇列永遠不會被塞滿**。
- **後果**：
  1. `maxPoolSize` 參數**徹底失效**，執行緒數永遠卡在 `corePoolSize`，無法動態擴容非核心執行緒；
  2. 當突發流量持續湧入時，幾百萬個任務會在記憶體中無限堆積，最終觸發 `java.lang.OutOfMemoryError: Java heap space` 導致進程當場暴斃。
- **鐵律**：生產環境**必須永遠使用有界佇列 (Bounded Queue)**，並明確設定容量上限。

### 2. 執行緒飢餓死鎖 (Thread Starvation Deadlock)
這是在微服務與非同步管線中極易被忽視的架構死鎖：

```java
// 致命示範：父任務與子任務共用同一個固定大小為 4 的執行緒池
ExecutorService pool = Executors.newFixedThreadPool(4);

void processOrder() {
    pool.submit(() -> {
        // 父任務開始執行...
        // 內部向「同一個執行緒池」提交子任務並等待結果：
        Future<PaymentResult> f1 = pool.submit(new PaymentTask());
        Future<StockResult> f2 = pool.submit(new StockTask());

        // 同步等待子任務回傳
        f1.get(); // 💥 若父任務佔滿了全部 4 個執行緒，子任務在佇列排隊永遠無法被執行！
        f2.get();
    });
}
```

當 4 個訂單請求同時抵達，4 個父任務剛好佔滿了執行緒池的全部 4 個執行緒。父任務緊接著向佇列提交 `PaymentTask`，但因為沒有多餘執行緒，子任務只能在佇列中苦苦排隊；而父任務在呼叫 `f1.get()` 同步等待子任務回傳。
- **結果**：**全體父任務佔著執行緒等子任務，全體子任務佔著佇列等執行緒釋放**，系統永久死鎖！

> **防禦法則：執行緒池必須按業務領域物理隔離！**
> 絕對不可將具有相依等待關係的父子任務、或將慢速 I/O 任務與核心運算任務混用在同一個執行緒池中。必須為高優先權任務、相依任務劃分獨立專屬的執行緒池。
