# 訊息佇列與事件驅動架構：內容規劃

2026-11-04 選定為下一個優先主題。本工作從已合併 PR #10 的 `217649e` 開始；首批完成 01–04，本次已接續完成 05–12，全系列 12 篇均已撰寫；完成狀態由[公開索引](../event-driven-architecture/README.md)維護。

## 主題邊界

本主題要回答：同步呼叫改成訊息傳遞之後，誰擁有工作、如何確認進度，以及如何讓不同消費者安全演進與恢復？

讀者需理解請求與回應、基本資料庫交易。不要求先讀完分散式系統的全部主線；該主題尚未完成的文章不能作為必要閱讀入口。

- [API](../api/README.md)維護對外操作、非同步狀態與 Webhook 契約；本主題深入 broker、producer 與 consumer 的責任。
- [AWS 的 SQS／SNS／EventBridge](../aws/sqs-sns-and-eventbridge.md)維護產品組合；本主題以通用問題安排閱讀，再對照產品，不重寫服務清單。
- [分散式系統](../distributed-systems/README.md)維護故障、冪等副作用、背壓與因果的共通基礎。本主題簡短回顧所需保證，再著重確認、offset、消費順序、重播與契約演進；Outbox 等跨邊界議題引用共同來源，後續文章完成後再建立互連。

## 貫穿案例

沿用文章匯出服務：先把「產生匯出檔」交給 worker；完成後產生事實事件，讓通知、搜尋索引與統計各自消費。每次增加元件都要指出原本流程遇到的具體問題。

意圖識別、單次 request ID、工作 ID 與事件 ID 分開。相同匯出工作可以產生多個不同事實事件；同一事件也可以被多次投遞，不把所有識別混成一個欄位。

以下為 12 篇閱讀順序。01–04 為首批正文，05–12 已接續完成；必要先備只指向前文已介紹的概念。

| --- | --- | --- | --- |
| 01 | 同步呼叫與非同步工作邊界 | 匯出為何要交給背景 worker？接受工作、開始處理與完成如何分開？ | 追蹤一次請求從接受到完成，列出引入訊息後新增的狀態與失敗點，不把非同步直接等同更可靠 |

| 04 | 發布確認與消費確認 | Broker 收到、consumer 收到、業務效果完成，各有什麼證據？ | 逐一分析 publish confirm、ack／delete、visibility timeout 與停止點；標出可能遺失或重複的邊界 |
| 05 | 消費並行、分區與順序 | 如何擴大吞吐又避免同一工作的狀態倒退？ | 分開發生、進入分區、投遞、處理與提交順序；說明 key／group／partition 的保證範圍 |
| 06 | 重試、死信與安全重送 | 壞訊息如何隔離？修正後能否直接重播？ | 設計可恢復錯誤與永久錯誤的處理；重送保留事件身分、避免重試風暴，並列 DLQ 保留與排序代價 |
| 07 | 資料庫與訊息的原子缺口 | 完成狀態與完成事件如何一致地保存？ | 分析雙寫故障窗口、Outbox relay 重送及消費去重；明確限制本地交易與外部副作用範圍 |
| 08 | 事件封套、Schema 與相容演進 | 舊消費者如何讀取新事件？欄位名稱相同是否代表語意相容？ | 設計事件類型、來源、識別、資料版本與敏感欄位；用新增／刪除／改義歷程檢查相容性 |
| 09 | 訂閱拓樸、路由與隔離 | 通知失敗為何不該拖住搜尋與統計？ | 安排獨立訂閱、過濾、租戶／權限與容量邊界；指出 fanout 可能造成的成本與資料暴露 |
| 10 | 重播、投影與歷史資料 | 重建搜尋索引和重寄通知能否用同一段歷史？ | 區分 replay 與新的業務意圖；處理保留期、offset、schema、刪除資料及外部副作用，說明事件驅動不必等於 event sourcing |
| 11 | 積壓、觀測與故障驗證 | 訊息數量下降是否代表工作真的完成？ | 定義進度、lag／年齡、重複率、死信與端到端完成證據；用回應遺失、consumer 暫停及壞事件測試推演 |
| 12 | 整合案例：匯出完成後的多下游處理 | 如何把工作佇列與完成事件組成可恢復的流程？ | 列出狀態轉移、契約、故障矩陣、補救與不保證事項；從最小版本擴充，不為每個問題都引入新服務 |

主線先建立責任與傳遞模型（01–03），再處理確認、順序與恢復（04–07），接著處理長期契約與獨立消費者（08–10），最後以觀測與整合檢查端到端承諾（11–12）。

串流的 event time、watermark、視窗及遲到資料先留作後續方向，避免把訊息整合與完整串流運算課題塞進同一輪。
