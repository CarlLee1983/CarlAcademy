# 訊息佇列與事件驅動架構：來源證據

查核日期：2026-11-04。以下 10 份來源皆已讀相關條文；RabbitMQ 網站顯示 4.4，Kafka 固定 4.1、CloudEvents 1.0.2、Avro 1.12.0、AsyncAPI 3.0.0；AWS、Google Cloud 為當日線上文件。不是最新版本清單，未執行部署、效能或故障測試。

## 傳遞拓樸與保存方式

1. **Queue 與 log。**RabbitMQ queue 是有順序的訊息集合；單 channel 的發布順序、broker 出列順序、並行 consumer 完成順序不能混為一談。多 channel、優先權、重送都會影響可觀察順序；同產品的 stream 則是帶 offset 的 append-only log。來源：[RabbitMQ：Queues](https://www.rabbitmq.com/docs/queues)，Message ordering。產品不是互斥分類，不能寫成「RabbitMQ 只能 queue，Kafka 只能 pub/sub」。
2. **Pub/sub 的分流單位。**Google Pub/Sub 每個 subscription 各自接收 topic 的訊息；同 subscription 的多個 subscriber 分攤工作。獨立訂閱與同訂閱內競爭消費可以並存。來源：[Google Cloud：Pub/Sub overview](https://docs.cloud.google.com/pubsub/docs/pubsub-basics)，Core concepts、Choose a publish and subscribe pattern。這是該產品模型，不能外推所有名為 topic 的元件都相同。
3. **保留與順序。**Kafka 事件追加到 partition；消費不會刪除事件，資料保存受 topic 政策限制；順序保證在 partition 內，沒有自動的跨 partition 全域順序。來源：[Kafka 4.1：Introduction](https://kafka.apache.org/41/getting-started/introduction/)，Topics、Partitions。案例若說「同業務 key 保序」，需明訂 partition 路由及 consumer 處理方式，不能由 key 名稱直接推論副作用完成順序。

## 確認、重送與重播

4. **兩種 ack 的邊界。**RabbitMQ publisher confirm 確認 publisher 與 broker 的互動；consumer acknowledgment 表示 consumer 告知 broker 該投遞已處理，兩者互不知情。未 ack 的投遞在 channel／connection 關閉後可重排入佇列。來源：[RabbitMQ：Consumer Acknowledgements and Publisher Confirms](https://www.rabbitmq.com/docs/confirms)，Are Publisher Confirms Related…、Automatic Requeueing。甚至 unroutable 訊息也可能收到 confirm；若需知道未路由，要看 `mandatory`／`basic.return`。confirm 不代表業務寫入成功，consumer ack 也不會與外部資料庫自動組成交易。
5. **Visibility timeout。**SQS receive 後訊息仍在 queue，只是暫時不可見；處理後需刪除，期限內未完成並刪除會再次可見。standard queue 不能藉 visibility timeout 宣稱絕無重複投遞；舊 worker 也不會被 broker 強制停止。來源：[SQS：Visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)，Understanding visibility timeout、Handling failures。最後一項是依「再次投遞不終止程序」作的邊界推論，非遠端撤銷功能。
6. **DLQ。**SQS redrive policy 的 `maxReceiveCount` 控制移入 dead-letter queue 前的接收次數；DLQ 用來隔離、診斷及後續 redrive，不證明業務沒有發生。把 FIFO 訊息移出亦可能破壞原工作序列。來源：[SQS：Using dead-letter queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html)。教學應交代誰檢查、修復及安全重送，不能把 DLQ 當作問題已解決。
7. **Offset 與 replay。**Kafka consumer 以 offset 指定讀取位置，可倒回重新消費；位置提交和業務效果之間的 crash window 仍要分析。Kafka 內部讀取、處理、寫入 topic 的 exactly-once 依交易與 consumer 設定成立，外部目的系統通常需要配合。來源：[Kafka 4.1：Design](https://kafka.apache.org/41/design/design/)，The Consumer、Message Delivery Semantics、Using Transactions。replay 受資料仍在保留範圍內限制；重播通知或付款不能直接等同重建純讀取投影。

## 事件識別、格式與契約

8. **CloudEvents envelope。**1.0.2 要求 `id`、`source`、`specversion`、`type`；`source + id` 識別不同事件，重送同事件可使用同 id。`specversion` 在本版為 `1.0`，不是業務 payload 版本。來源：[CloudEvents 1.0.2 specification](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md)，Required Attributes。事件識別不自動等於一次網路 request、整個 operation 的冪等鍵或 tracing correlation；這些關聯需另訂契約。envelope 不提供 broker、排序或業務去重實作。
9. **Schema evolution。**Avro 用 writer schema 與 reader schema 做 resolution：writer 多出的欄位可忽略；reader 所需欄位若 writer 沒有，需 reader 的 default，否則錯誤。數值提升亦有方向限制。來源：[Avro 1.12.0 specification](https://avro.apache.org/docs/1.12.0/specification/)，Schema Resolution。相容性要列出「新 reader 讀舊資料」或反向，不能只說加欄位一定安全；格式可讀也不代表金額單位、事件含義等語意相容。
10. **非同步 API 契約。**AsyncAPI 描述 application 的 operations、channels、messages、payload schema、bindings 及 correlation ID；3.0 `send`／`receive` 應由被描述 application 的視角解讀。來源：[AsyncAPI 3.0.0 specification](https://www.asyncapi.com/docs/reference/specification/v3.0.0)，Overview、Operation Object、Message Object、Correlation ID Object。文件可描述契約，不代表 broker 會自動強制所有敘述；AsyncAPI 版本也不是事件業務版本。

## 首批四篇正文的補充查核

同日追加；上方 10 項初步紀錄保留。下列是已實讀的章節及可支持的範圍，部分補足上節缺口；其餘缺口仍有效。RabbitMQ 使用當日頁首標示 **4.4** 的 `/docs/` 文件（不是永久鎖版 URL）；Kafka 固定 **4.1**，RFC 固定 **9110（2022-06）**，Azure、Google Cloud 與 AWS 為線上文件。

11. **01：接受與完成分開。**[RFC 9110 §15.3.3：202 Accepted](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)明定已接受處理但尚未完成，最終也可能不執行；回應內容應描述目前狀態並指向或包含狀態監視方式。202 本身不保證排入 broker、工作開始或日後成功。案例的 `accepted → running → succeeded / failed` 是本系列自訂狀態模型，不是 RFC 強制流程；各狀態的保存點與查詢契約需在正文交代。
12. **02：命令與事實事件是設計責任。**[Kafka 4.1 Introduction：Main Concepts and Terminology](https://kafka.apache.org/41/getting-started/introduction/#main-concepts-and-terminology)把事件描述為發生過的事實。[Azure EDA：Architecture、broker／mediator topology](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/event-driven#architecture)區分廣播事件與向指定 channel 發送、期待 consumer 處理的命令。據此採用「`GenerateExport` 要求執行；`ExportCompleted` 陳述已完成」作為本系列教學模型；命名、單一工作責任及 ID 配置不是 broker 自動強制的規範。同頁 When to use / Challenges 列明非同步錯誤處理、運作成本與最終一致性代價，可支持第 01 篇不把非同步直接寫成更可靠。
13. **03：RabbitMQ 路由與競爭消費。**[Exchanges：Fanout、Topic、Direct](https://www.rabbitmq.com/docs/exchanges)說明 exchange 依 bindings 路由：fanout 向每個綁定目的地送一份、忽略 routing key；direct 精確比對，topic 依 pattern 比對。[Consumers：Priority、Single Active Consumer](https://www.rabbitmq.com/docs/consumers)說明一般 active consumers 輪流分攤同 queue 投遞，優先權、prefetch 與 SAC 會改變分配；不等於每個 worker 都收一份，也不保證業務只執行一次。[Streams：Use Cases、Data Retention](https://www.rabbitmq.com/docs/streams)則支持多 consumer 非破壞讀取、指定 log 位置及按大小／年齡淘汰資料。比較時將 classic／quorum queue 與 stream 分列，避免把 RabbitMQ 當成只有一種保存模型。
14. **03：獨立下游的進度單位。**[Google Pub/Sub overview：Core concepts、Choose a Pub/Sub publish and subscribe pattern](https://docs.cloud.google.com/pubsub/docs/pubsub-basics)的兩 subscription 範例各收 A、B，一個 subscription 內兩 subscriber 分攤；這是無額外過濾設定的模型，獨立下游應以不同 subscription 表達。Life of a message / Status of a message 說明 ack deadline 到期可再投遞；分攤不代表免除重送。
15. **03–04：Kafka 保存、group 與 offset 的範圍。**[Kafka 4.1 Introduction：Main Concepts and Terminology](https://kafka.apache.org/41/getting-started/introduction/#main-concepts-and-terminology)說明消費不刪除事件、保存由 topic 設定控制；[Design：The Consumer、Consumer position、Message Delivery Semantics、Share groups](https://kafka.apache.org/41/design/design/)說明 fetch offset 可倒回、傳統 consumer group 內每 partition 同時由一 consumer 消費，各 group 的位置分開。這個 partition 分工模型限定 **traditional consumer group**；4.1 同頁把 **share group** 列為 preview，允許一 partition 分配多 consumer，逐筆確認。不能寫成所有 Kafka group／client 協定都具相同獨佔語意。先存位置再做效果可漏處理，先做效果再存位置可重做；offset commit 是恢復位置，不是外部資料庫效果證明。本文只涵蓋保存政策概念，不推導 retention 數值、compaction 或 rebalance 細節。
16. **04：RabbitMQ confirm、return 與 ack 的證據。**[Confirms：Are Publisher Confirms Related…、Consumer Acknowledgement Modes、When Will Published Messages Be Confirmed…、Automatic Requeueing](https://www.rabbitmq.com/docs/confirms)的具體方法限定 **AMQP 0-9-1**。confirm 與 consumer ack 互不知情；可路由訊息在所有目標 queue 接受後 confirm。未路由也可 confirm；`mandatory` 訊息先 `basic.return` 再 `basic.ack`，不能只等 confirm 判斷路由成功。manual ack 允許 broker 移除投遞；未 ack 而 channel／connection 關閉會重排，效果後 ack 前中斷可重做；auto ack 在送出時即視為成功，有遺失風險。這些訊號不檢查外部資料庫，業務完成要由應用在效果提交後另行記錄。
17. **04：durable、persistent 與 quorum 不是同一開關。**[Queues：Durability](https://www.rabbitmq.com/docs/queues#durability)區分 queue metadata 與訊息 delivery mode：durable queue 重啟恢復 persistent 訊息，transient 訊息會丟棄。[Confirms：When Will Published Messages Be Confirmed…](https://www.rabbitmq.com/docs/confirms#when-will-published-messages-be-confirmed-by-the-broker)把 persistent 訊息送 durable queue 的 confirm 界定為落盤，quorum queue 則需 quorum replicas 接受並確認。[Quorum Queues：Overview、Data Safety、Availability](https://www.rabbitmq.com/docs/quorum-queues)說明這是 Raft 複寫 queue；已 confirm 訊息的安全前提是多數成員未永久失去，運作也需要 quorum。durable 不自動等於複寫；上述保證不包含 consumer 副作用，也不涵蓋任意永久節點損毀。
18. **04：SQS 的 receive／delete 界線。**[Visibility timeout：Setting and adjusting、Understanding visibility timeout in standard and FIFO queues、Handling failures](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)明示 receive 只讓訊息暫時不可見，未及時 delete 會再次可見，可由相同或不同 consumer 取得；standard queue 在 timeout 內仍不能保證沒有重複。效果前 delete 有漏做窗口，效果後 delete 前失敗有重做窗口，這是依文件行為作的故障推論。延長 visibility 不構成外部寫入鎖，也不證明舊 worker 已停止；正文不延伸成 FIFO 去重或外部效果 exactly-once 保證。

首批可據上述證據撰寫；後續篇章仍需另查 RabbitMQ DLX 可靠性、Kafka 詳細保留／清理與重平衡設定、SQS FIFO 與 redrive 身分、schema registry 及治理。此次僅文件查核，未測試 broker、SDK、重啟或故障注入。

19. **01：佇列緩衝的前提。**[Azure：Queue-Based Load Leveling，Solution、Problems and considerations](https://learn.microsoft.com/en-us/azure/architecture/patterns/queue-based-load-leveling)已讀：佇列緩衝不同速率，consumer 仍需控制處理速率；平均流入高於流出會持續增加積壓，保存、容量及重複處理仍需設計。正文的每秒 12／10 個與一分鐘 120 個為自訂算例，非產品效能測試。

## 05–12 正文的補充查核

同日追加，保留 1–19 原紀錄；下列已實讀相關條文，補足前述部分缺口。Kafka 使用 **4.1 系列**文件，其中 `/41/javadoc/` 當日頁面標示 **clients 4.1.2**；RabbitMQ 線上文件頁首 **4.4**；CloudEvents **1.0.2**、Avro **1.12.0**、AsyncAPI **3.0.0** 固定版本。AWS、Google Cloud、Azure 均為 2026-11-04 線上查核，未部署或故障注入。

20. **05：分區順序不等於完成順序。**[Kafka 4.1 Introduction：Main Concepts and Terminology](https://kafka.apache.org/41/getting-started/introduction/#main-concepts-and-terminology)說明同 key 寫同 partition、consumer 依寫入順序讀；[KafkaConsumer：Multi-threaded Processing](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)明示把消費與 worker pool 分開後，早批次可能晚完成，提交須協調該 partition 的處理完成情況。案例的 key 路由需固定前提，不能把改 partition 配置或自訂路由後的行為直接套入。若 offset 100 尚未完成、101 已完成，提交 102 會令恢復跳過 100，是依「提交下一個讀取位置」作的推演；安全進度須覆蓋之前所有已交付記錄，不是取完成 offset 最大值，也不能假定 offset 數字無缺口。
21. **05：傳統 group 的重平衡與執行所有權。**同份 [KafkaConsumer：Consumer Groups、Detecting Consumer Failures、Offsets and Consumer Position](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)已讀：加入、退出及新增 partition 可導致重新分派；長時間不 poll 可失去 group 身分，commit 也可能失敗。手動提交不能領先實際完成位置；可 pause partition 並持續 poll。本文限定 traditional consumer group，不含前述 share group preview。重分派本身不撤銷舊程序已送往外部系統的寫入，是設計邊界推論；需要以應用原子去重／版本條件保護，不能靠 rebalance 當 fencing。
22. **05–06：SQS FIFO group 的批次邊界。**[FIFO delivery logic：Sending、Receiving、Additional notes](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/FIFO-queues-understanding-logic.html)已讀：保序範圍為同 `MessageGroupId`，不同 group 可並行；同一批 receive 可以包含多筆同 group 訊息，後續 receive 要等已取訊息刪除或再次可見。故應用若要求同工作效果順序，仍須按序執行批次；visibility 到期也不保證舊 worker 停止。後兩點是依投遞邊界作的推論。單一 group 限制並行；broker 到達順序亦不等於不同 producer 在真實世界的事實發生順序。
23. **06：FIFO 去重的時間與識別範圍。**[SQS SendMessage：MessageDeduplicationId](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/APIReference/API_SendMessage.html)已讀：相同 dedup ID 的成功送出在 **5 分鐘**內會被接受但不再投遞；超過窗口後無法偵測回應遺失造成的重送。內容去重只 hash body，不含 attributes；刪除後仍追蹤窗口內 ID。[SetQueueAttributes：DeduplicationScope](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/APIReference/API_SetQueueAttributes.html)另區分 queue／messageGroup scope。這是 producer 傳送去重，不能替代 consumer 資料庫效果去重；正文不可從官方頁面的 exactly-once 用語推成任意外部副作用只執行一次。
24. **06：DLQ 保存期與 redrive 身分。**[SQS DLQ：Understanding message retention periods](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html)已讀：standard 移入 DLQ 保留原 enqueue timestamp 計算到期；FIFO 移入時重設。兩者 DLQ oldest-age 指標都從移入 DLQ 算起，故不等於原事件年齡。FIFO 使用 DLQ 可能破壞精確操作順序。[DLQ redrive：頁首 notes、Velocity control](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-configure-dead-letter-queue-redrive.html)明示 redrive 重設 retention，分配新 `messageID`／`enqueueTime`；FIFO 入 DLQ 時 dedup ID 改為原 message ID；重送流可與新發布交錯。redrive 不支援途中修改或過濾內容，應從小速率開始觀察。因此保留應用 `source + eventId` 是本例恢復契約，不能依 broker ID 去重。
25. **06：重試負載與 RabbitMQ DLX 限制。**[Amazon Builders’ Library：Timeouts, retries, and backoff with jitter，Introduction／Retries and backoff／Jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)已讀：逾時不證明副作用未發生，重試會加負載，backoff 與 jitter 分別拉開間隔及分散同步尖峰。錯誤分類、次數／時間預算及 redrive 速率是本例設計。[RabbitMQ 4.4 DLX：Safety、Re-Publishing with Publisher Confirms](https://www.rabbitmq.com/docs/dlx#safety)明示預設轉送沒有內部 publisher confirms，目標不可用可能遺失；不能把 DLX 當保證可靠的存放區。[Quorum Queues：Activating at-least-once Dead-Lettering、Limitations、Caveats](https://www.rabbitmq.com/docs/quorum-queues#dead-lettering)要求來源 quorum queue、`dead-letter-strategy=at-least-once`、`overflow=reject-publish`、DLX 及必要 feature flag；來源保留至目標確認，佔用資源，重試仍可重複。正文若不展開配置，只保留此限制，不提供未驗證部署步驟。
26. **07：Outbox 只封住本地雙寫缺口。**[AWS Transactional outbox：Motivation、Issues and considerations、Using an outbox table](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)已讀：業務表與 outbox 同交易提交，另一服務讀已提交記錄並發布，事件處理服務仍可能重送，consumer 要追蹤已處理訊息。[Making retries safe with idempotent APIs：Reducing client complexity](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)要求 token 記錄與相關修改具備 ACID 原子性。沿用[分散式系統證據](distributed-systems-sources.md)：本例 consumer 的「唯一鍵插入 processed-event＋投影修改」需同一本地交易；relay 發布成功但未記完成可再次發布。通知 API 不在該交易內，仍須下游冪等契約或對帳，不能靠 processed 記錄先寫或後寫消除兩個失敗窗口。這是文件原子性條件的應用推演。
27. **08：封套版本與 payload schema 分開。**[CloudEvents 1.0.2：Required Attributes、dataschema、Privacy and Security](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md)已讀：不同事件必須有不同 `source + id`，同事件重送可同 id；必要欄位為 `id/source/specversion/type`，本版 `specversion=1.0`。`dataschema` 是可選 URI，不相容 schema 變動 SHOULD 使用不同 URI；敏感資料不應放 context attributes，中介可檢查與記錄它們。它沒有定義本案例 `jobId`、`intentId` 或 payload 業務版本，也不自動驗證消費端。正文 envelope 的自訂欄位與 CloudEvents 必填欄位應分清。
28. **08：Avro 相容性有讀寫方向。**[Avro 1.12.0：Records、Enums、Schema Resolution](https://avro.apache.org/docs/1.12.0/specification/#schema-resolution)已讀：reader 忽略 writer 多出的欄位；reader 需要而 writer 沒有的欄位用 reader default，無 default 則錯。default 不使欄位在寫入時可省略。writer 的 enum symbol 不在 reader 內，reader 有 enum default 才能回退，否則錯。新 reader 讀舊資料與舊 reader 讀新資料必須分別列出。相同整數欄位從秒改毫秒仍可能通過 resolution，卻改變意義；這是自創語意反例，不是 Avro 自動檢查單位的保證。
29. **08：AsyncAPI 以被描述應用為視角。**[AsyncAPI 3.0.0：Introduction、Operation Object、Message Object](https://www.asyncapi.com/docs/reference/specification/v3.0.0)已讀：operation `send` 表示該 application 發送，`receive` 表示該 application 接收；不能將另一端文件機械反轉。channels、messages、payload schema、correlation 與 bindings 描述契約，不會自行實作 broker 權限或資料驗證。規格版號與事件業務版本分開；本系列不引入 schema registry 產品相容政策。
30. **09：過濾、訂閱與權限分開設計。**[Pub/Sub Filter messages：頁首、Update the filter for a subscription](https://docs.cloud.google.com/pubsub/docs/subscription-message-filter)已讀：每 subscription 可不同 filter，只依 attributes 過濾，不檢查 data；未匹配訊息由服務自動 ack；filter 建立後不可修改，替換需遷移。自動 ack 的訊息仍有文件列明的 delivery／seek storage 費用，不能寫成過濾就零成本。[IAM：Overview、Required permissions、Cross-project communication](https://docs.cloud.google.com/pubsub/docs/access-control)已讀：發布、消費及建立／附加 subscription 權限分列，跨專案也需雙方相關授權。租戶 filter 不是授權邊界；能建立額外 subscription 的角色可能另收資料，這是依權限模型的設計推論。獨立 subscription 亦不自動隔離共用資料庫／worker 容量。
31. **10：Kafka 可重播歷史受清理政策限制。**[Kafka 4.1 Topic Configs：cleanup.policy、retention.ms／bytes、segment.bytes](https://kafka.apache.org/41/configuration/topic-configs/)已讀：delete 依時間／大小移除舊 segment；compact 留每 key 最新值；可同時設兩者，此時留存 segment 仍受刪除政策限制。[Design：Log Compaction Basics、What guarantees does log compaction provide?](https://kafka.apache.org/41/design/design/#log-compaction)已讀：compaction 移除舊記錄而不重排或改 offset；key 搭配 null payload 是 tombstone，之後自身也會清掉。落後超過 `delete.retention.ms` 的 reader 可能錯過刪除標記。故 compact topic 不是完整事實歷史；已有投影不能無條件靠任意晚到的增量重播得知所有刪除。實際保存需查 topic 配置，不能把文件預設當案例現況。
32. **10：重播位置與狀態權威不同。**[Pub/Sub replay：Snapshot and seek overview、Seek to a timestamp、Seek with filters](https://docs.cloud.google.com/pubsub/docs/replay-overview)已讀：snapshot 保存 subscription 的 ack state，並非永久應用資料備份；重播已 ack 訊息需要 topic retention、保留已 ack 的 subscription，或預先建立的有效 snapshot。seek 後投遞不立即完全一致，timestamp 依 broker publication time 而非業務發生時間；filter 仍限制重送。[Azure Event Sourcing：Solution、Issues and considerations](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)已讀：event store 是權威資料來源，重播重建 entity／投影；錯誤歷史與 schema 演進仍要處理。由此區分「有完成事件及 replay 功能」與「用事件作 system of record」。重建搜尋與重新寄信分流、刪除資料遮罩及人工核准重寄是本例設計，非 seek 自動撤銷副作用。
33. **11–12：broker 指標不是完成證據。**[SQS CloudWatch metrics：Amazon SQS metrics](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-available-cloudwatch-metrics.html)已讀：多項計數是 approximate；Visible 是可取、NotVisible 是已取未刪除／到期、Delayed 是尚未到可取時間。standard 的 poison pill 可從 oldest-age 排除，DLQ age 從移入計；delete 計數含相同訊息多次成功刪除，不等於唯一完成數。[Kafka 4.1 Monitoring：consumer-fetch-manager-metrics／records-lag-max](https://kafka.apache.org/41/operations/monitoring/)明定該指標依 current offset 而非 committed offset；配合第 20 項可知讀完不等於效果提交。本例因此另記 job 終態、各下游效果、重複抑制與事件最初時間；lag 歸零、queue 下降或 trace 存在都不能單獨證明匯出與通知完成。故障矩陣仍是推演，沒有宣稱執行實驗。

本次補足 05–12 所需保證；仍不涵蓋 schema registry 治理、Kafka partition 擴充遷移程序、完整 rebalance protocol 差異或任何實際部署配置。舊段落的「尚待深入」是當時紀錄，已補範圍以上方逐項查核為準。

34. **11：追蹤關聯與積壓恢復。**[OpenTelemetry Context propagation：Context、Propagation、Traces、Logs](https://opentelemetry.io/docs/concepts/context-propagation/)已讀：trace／span context 跨程序傳遞以關聯活動，不能由關聯紀錄推論去重、交易或授權保證；缺少遙測不證明沒有執行是觀測完整性限制。[AWS：Avoiding insurmountable queue backlogs，The duplicitous nature of queues、Sending backpressure upstream](https://aws.amazon.com/builders-library/avoiding-insurmountable-queue-backlogs/)已讀：積壓可能增加故障恢復時間；不合理流入可向上游施加拒絕／限制。11 的 600／8／10 與 300 秒是明列假設的淨排空算例，非部署量測。
