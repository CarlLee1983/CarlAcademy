# 測試套件精簡

Status: in-progress

## Problem Statement

CarlAcademy 是純內容型文件站，但每次 CI 仍要約 166 秒（4 個 shard，最慢 shard 的測試本身 87.8 秒），本機 `pnpm run verify` 約 150 秒。作者大多只是新增或修改文件，卻要等待與內容無關的介面測試反覆建置整站。

成本來自測試設計，而不是驗收範圍本身：完整 suite 除了共用 baseline 外，還做 20 次全站 fresh build，每次複製全部真實內容（130 餘篇文件）；大多數介面測試只是在驗證一個元件，卻在兩種 base 上各跑一次；驗證器的拒絕測試靠多次全站建置來證明一條 HTML 檢查規則；同一流程在多個測試重複驗證。

測試還寫死真實內容：主題清單、文章標題與順序、特定文章的表格、搜尋詞與主題索引的表格數。新增文件時常常得一併修改測試；最近 30 個 commit 中，`site` 測試改了 9 次、`integration` 測試改了 6 次，大多只是跟著內容更新。

## Solution

驗收範圍不縮小，只改驗證方式：每項行為至少在一處、用最便宜而可信的層級驗證，層級由貴到便宜依序是瀏覽器 E2E、全站建置、HTML 層檢查。

- 只有需要完整真實清單的三個檢查繼續使用真實內容：全部文章版面巡檢與搜尋索引對照、全站 SEO 與網站地圖、每篇文件皆有單一標題與正文。
- 其他介面與建置測試改用手寫的小型**範例內容**，建置一次只需數秒。
- 介面行為測試只在子路徑 `/academy/` 驗證；base path 的正確性集中由輸出驗證器（兩種 base 的每次建置都會執行）、直開與重新整理測試，以及全部文章巡檢負責。
- 全部文章巡檢拿掉淺色／深色維度，只保留淺色；外觀切換本身已由外觀測試驗證。
- 驗證器的拒絕規則改為對手寫的小型產物目錄直接檢查；在 Astro 建置階段發生的拒絕，仍以「修改範例內容 → 建置失敗」驗證，同時證明這些檢查確實接在建置流程中。
- 重複的流程測試合併成一處；各元件測試另外加的整頁溢出、字型載入斷言移除，由全部文章巡檢負責。
- 測試不再寫死內容：主題清單一律取自產品既有的主題定義，閱讀順序斷言改為「導覽順序等於主題索引的建議閱讀順序」，預期值從範例內容本身讀出。
- 分層原則寫入網站驗收記錄。最後重新量測，將 CI shard 數調整為達成目標的最小值。

成功標準：CI 牆鐘時間 ≤ 100 秒，本機 `pnpm run verify` ≤ 60 秒，且驗收記錄列出的每項覆蓋都能對應到精簡後的測試。

## User Stories

1. As a 作者, I want 推送後 CI 在 100 秒內完成, so that 我能更快確認變更並合併。
2. As a 作者, I want 本機 `pnpm run verify` 在 60 秒內完成, so that 我願意在每次提交前跑完整驗收。
3. As a 作者, I want 新增文件時不必修改任何測試, so that 寫作流程不被測試維護打斷。
4. As a 作者, I want 新增主題時測試自動涵蓋它, so that 主題清單只在產品的唯一來源維護。
5. As a 作者, I want 修改真實文件的措辭、標題或表格不會讓介面測試失敗, so that 測試失敗只代表網站行為真的壞了。
6. As a 作者, I want 全部公開文章仍在兩種 base 與兩種寬度下巡檢版面不溢出, so that 內容變更不會破壞閱讀版面。
7. As a 作者, I want 搜尋索引仍與完整公開清單完全相等, so that 新文件一定可被搜尋、內部文件一定不被索引。
8. As a 作者, I want 全站 SEO 與網站地圖仍涵蓋所有公開頁面, so that 任何文件都不會缺少摘要、canonical 或分享資訊。
9. As a 作者, I want 每篇公開文件仍被檢查具備單一標題與正文, so that 空白或缺標題的文件不會上線。
10. As a 作者, I want 站內連結與段落錨點仍在兩種 base 的每次建置中驗證, so that 壞連結無法通過建置。
11. As a 作者, I want 驗證器的每條拒絕規則都有直接而快速的測試, so that 規則失效時能立即定位。
12. As a 作者, I want 缺少標題、公開網址衝突、文件未列入主題索引仍會讓建置失敗並指出問題, so that 這些錯誤無法靜默通過。
13. As a 作者, I want 直開、重新整理、標題變更不改網址、內部文件回 404 仍在兩種 base 驗證, so that 部署路徑相關的契約不因精簡而失守。
14. As a 讀者, I want 首頁、主題索引與文章的閱讀起點、前後篇與文件序號仍正確, so that 我能依建議順序閱讀。
15. As a 讀者, I want 外觀切換、可見焦點與跳至內容仍被驗證, so that 我能用偏好的外觀與鍵盤閱讀。
16. As a 讀者, I want 桌面首屏從正文開始、手機保留精簡開場與導言仍被驗證, so that 長導言的文章仍好讀。
17. As a 手機讀者, I want 表格在無 JavaScript 時仍有欄名卡片, so that 窄螢幕也能讀懂表格。
18. As a 讀者, I want 表格可用鍵盤切換卡片與原表格、工具列不跳動、寬表格只在自身捲動, so that 比較資料時版面穩定。
19. As a 讀者, I want 主題索引收合區內的每張表格都有卡片與切換工具, so that 主題說明的表格也能在手機閱讀。
20. As a 讀者, I want 程式碼的精確複製、超寬換行、捲動提示與失敗回饋仍被驗證, so that 我能可靠地複製指令。
21. As a 讀者, I want 框線圖保留原排版且無 JavaScript 時可局部捲動, so that 圖解不被打亂。
22. As a 讀者, I want 固定目錄、目前章節、閱讀進度與手機章節面板仍被驗證, so that 我能掌握長文位置。
23. As a 讀者, I want 閱讀設定的偏好保存、鍵盤操作、毀損值復原與漸進增強仍被驗證, so that 調整字級等設定不會失效。
24. As a 讀者, I want 搜尋能找到中文標題與英文正文、首次載入失敗可重試、較早的查詢不覆蓋目前結果, so that 搜尋可靠。
25. As a 讀者, I want 200% 文字縮放模擬下仍能以鍵盤觸及正文、搜尋與主要流程, so that 放大文字時仍能使用網站。
26. As a 讀者, I want 分享工具在有無正式網址、有無 JavaScript 時都提供正確的連結或提示, so that 分享出去的網址乾淨且可用。
27. As a 作者, I want 未設定正式網域的預覽不產生假的 canonical、社群圖片與網站地圖網址, so that 預覽不會汙染搜尋引擎。
28. As a 維護者, I want 每項行為只在一處驗證, so that 行為變更時只需更新一個測試。
29. As a 維護者, I want 範例內容的每篇文件各自說明它觸發哪些網站功能, so that 新增測試時知道該擴充哪篇範例。
30. As a 維護者, I want 測試的預期值從範例內容讀出而非寫死, so that 調整範例內容不必同步修改多處斷言。
31. As a 維護者, I want 範例內容缺少的主題自動補上最小主題索引, so that 新增主題不需修改範例內容。
32. As a 維護者, I want 驗收記錄寫明測試分層原則, so that 之後的人不會把單一 base、單一配色誤當遺漏而「補回」。
33. As a 維護者, I want 驗收記錄的覆蓋表格對應到精簡後的測試, so that 驗收證據與實際測試一致。
34. As a 維護者, I want 共用 baseline 由 suite 一次準備、測試只讀取, so that 測試不重複建置相同產物。
35. As a 維護者, I want 單獨執行某個測試檔時仍能自行建置所需的 baseline, so that 聚焦重跑一個測試檔仍可行。
36. As a 維護者, I want CI shard 數依精簡後的實測調整為達標的最小值, so that 不浪費 runner 又能達到時間目標。
37. As a 維護者, I want 測試執行時建置輸入不變的保護仍然有效, so that 結果仍綁定目前的來源。

## Implementation Decisions

- **驗收範圍不變**：驗收記錄現有的每項覆蓋，精簡後都要有對應測試。只改驗證層級與重複程度；若之後判斷某項覆蓋不值得保留，另行提出，不在本次刪除。
- **三個接縫，全部沿用既有接縫，產品程式碼不新增接縫**：
  1. 正式建置產物經一般 HTTP 伺服器，由瀏覽器操作，用於所有介面行為。
  2. 測試 harness 的 fixture／baseline 介面，擴充為可選內容來源與正式網址設定。
  3. 既有的輸出驗證器公開函式 `verifyOutput(directory, base)`，供 HTML 層的拒絕測試直接呼叫。
- **共用 baseline 由 2 份增為 4 份**，由 suite 在測試開始前一次準備並透過既有 manifest 交給測試：
  - 真實內容 × `/`
  - 真實內容 × `/academy/`
  - 範例內容 × `/academy/` × 預設正式網域
  - 範例內容 × `/academy/` × `SITE_URL` 為空

  單獨執行測試檔、沒有共用 artifact 時，harness 沿用現行行為，自行建置所需的那份。suite 對 baseline 數量與證據的驗證隨之更新。
- **fixture 介面**：測試可以要求一份可變更的暫存網站副本，並指定使用真實內容或範例內容。範例內容副本以範例文件取代 `docs/`，其餘網站來源照常複製。產品既有主題定義中，範例內容沒有涵蓋的主題，自動補一份只有標題、沒有文件的最小主題索引。
- **範例內容**：手寫，獨立於真實文件，放在測試目錄下。主題代號必須取自產品既有的主題定義。組成如下：
  - Linux 主題索引：含「建議閱讀順序」，以及「主題說明與延伸閱讀」收合區內 2 張表格。
  - 文章 A（長篇）：導言與含粗體的 abstract；3 個以上 `h2` 與巢狀標題；3 欄 3 列表格；4 列且寬度超過 680px 的寬表格；超寬程式碼；框線圖；可搜尋的英文錯誤碼。
  - 文章 B：驗證上一篇／下一篇，含英文標題搜尋詞，並有連結指向 A。
  - 文章 C：閱讀順序的最後一篇。
  - API 主題索引：收合區內 1 張表格，用來驗證不同主題的表格數。

  每篇範例在開頭以註解或說明交代它觸發哪些功能；若現有測試需要清單未列的特徵，在範例內容中補上，不改回真實內容。
- **只有 3 個檢查留在真實內容**：
  - 全部公開頁面 HTTP 開啟、搜尋索引等於公開清單、全部文章在兩種 base × 390／1440 兩種寬度下不溢出且自行託管字型載入。拿掉淺色／深色維度，只跑淺色。
  - 兩種 base 的全站 SEO 與網站地圖。
  - 每篇公開文件都有單一非空 `h1` 與正文。
- **base path 分工**：介面行為測試只跑 `/academy/`。依賴 base 的部分由以下三者負責：輸出驗證器（每次建置）、直開與重新整理測試（兩種 base，改用範例內容各建置一次）、全部文章巡檢（兩種 base）。
- **拒絕測試**：
  - 輸出驗證器的規則（不存在的文章、不存在的段落、目錄網址的段落錨點，以及驗證器其餘拒絕規則），改為對手寫的小型產物目錄呼叫 `verifyOutput`，斷言錯誤訊息能定位問題。
  - 建置階段的規則（缺少標題、公開網址衝突、文件未列入主題索引），保留「修改範例內容 → 建置失敗 → 錯誤指出問題」，只跑一種 base。這 3 個測試同時證明檢查接在建置流程中，取代原本另外保留一個端對端拒絕測試的安排。
- **合併重複流程**：
  - 手機章節面板「展開後點連結」只在閱讀導覽測試驗證。
  - 表格的鍵盤切換只在表格切換測試驗證；主題索引表格測試只驗每張表格都有卡片與切換工具。
  - 無 JavaScript 的表格卡片只在手機表格測試驗證。
  - 「以英文錯誤碼搜尋並導向文章」只在搜尋重試測試驗證；200% 縮放測試保留鍵盤可觸及搜尋，不驗命中哪一篇。
  - 移除元件測試的整頁溢出與字型載入斷言。
- **正式網址設定的測試**：未設網域的 SEO 預覽與分享工具的 3 個測試，改為讀取兩份範例內容 baseline，不再各自建置。原本用自訂測試網域的分享測試改用預設網域；原本只跑根路徑的分享提示測試改跑 `/academy/`。
- **去除寫死內容**：
  - 主題清單一律取自產品既有的主題定義。
  - 閱讀順序斷言改為「導覽順序等於該主題索引的建議閱讀順序」。
  - 主題索引標題錨點的預期值，從主題定義與各主題索引的標題推導。
  - 移除描述內容進度的文字斷言（例如「主線 12 篇已全數撰寫」）。
  - 介面測試的文章路徑、標題、表格數與搜尋詞，從範例內容讀出。
- **內部文件排除**：內部文件回 404 的檢查保留，但清單改用範例副本實際存在的內部檔案，不依賴真實 repo 的特定檔名。
- **驗收記錄**：網站驗收記錄新增「測試分層」一節，寫明四件事：每項行為只在一處驗證、介面測試只跑 `/academy/`、巡檢只跑淺色、拒絕規則在 HTML 層驗。同時更新覆蓋表格與重跑結果。反轉成本低，不另開 ADR。
- **CI shard**：精簡完成後重新量測，把 CI shard 數調整為達成 ≤ 100 秒的最小值。

## Testing Decisions

- **好的測試**：只透過外部可觀察行為驗證，也就是建置產物經 HTTP 在瀏覽器中的表現、建置成敗與錯誤訊息、驗證器對產物目錄的判定。不斷言內部函式呼叫或實作結構。預期值來自內容來源（主題定義、主題索引、範例內容），不寫死。
- **涵蓋的模組**：
  - 測試 harness：fixture、baseline、suite artifact 準備與證據驗證。
  - 範例內容。
  - 輸出驗證器的拒絕規則。
  - 既有 13 個測試檔依上述分工改寫。
- **harness 本身要測**：既有 tooling 測試改為斷言 suite 準備的是四份 baseline 並驗證證據。另新增驗證：範例副本會為缺少的主題補上最小索引，且不含真實文件。
- **前例**：
  - 拒絕測試沿用現行「建置拒絕…並指出問題」的錯誤訊息斷言方式。
  - 介面測試沿用現行的 `serve()` 加 Playwright 模式。
  - SEO 單元測試沿用直接 import 產品工具函式的模式，作為 HTML 層驗證器測試的參考。
- **驗收方式**：每張 ticket 完成時，`pnpm run verify` 全數通過，並記錄本機耗時。最後一張 ticket 以 CI run 證明牆鐘 ≤ 100 秒。並逐項對照驗收記錄的覆蓋表格，確認沒有覆蓋遺失。
- **建置輸入保護**：suite 結束時「建置輸入在測試期間未變」的檢查繼續有效；範例內容也算建置輸入。

## Out of Scope

- 讓產品從 `docs/` 目錄推導主題清單，或改變首頁主題順序的來源。
- 讓同一 workspace 內的測試可以並行。現行 fixture 共用 `node_modules`，平行建置會衝突，本次仍靠 CI shard 並行。
- 改用 Playwright container 或快取瀏覽器、依變更路徑分流 CI 等 CI 層調整，CI shard 數調整除外。
- 新增網站功能、修改產品行為或介面設計。
- 刪除任何現有驗收覆蓋。
- 實機、原生文字縮放與真人試讀等驗收記錄列為尚未驗證的範圍。
